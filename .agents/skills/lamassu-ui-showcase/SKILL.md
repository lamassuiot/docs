# Creating Lamassu documentation animations

Turn the user's requested workflow into an editable OpenShowcase flow JSON. Use OpenShowcase's recorder and player to capture and deliver the demo; do not substitute a hand-built animation or a Playwright-only recording. Reuse an existing flow when updating a demo.

## Input and destination

- Translate the user's task into a short, repeatable sequence of observable UI actions. Explore the actual interface and use its accessible roles and names; do not invent selectors. Ask only for information that blocks the requested flow or access.
- When the user specifies where to insert the demo, integrate it there using the project's existing conventions. Maintain all supported languages, translating the surrounding text and tooltips while sharing media when practical. Respect the site's asset base path. If no insertion destination is specified, deliver the generated demo in a local output folder; do not modify documentation pages.
- Persist the authoritative `.flow.json` alongside the generated demo or in the repository's established source location. Reuse and update it for later changes; do not store credentials or session state in it. Clearly report its location and the output location.

## Runtime and temporary files

- Default all interactions with the ephemeral demo deployment, dashboard and API to **HTTP**, including the flow's `url` and navigation steps. Use HTTPS only when the user explicitly requests it. Do not silently fall back to HTTPS if HTTP is unavailable: diagnose or report the blocker. This default concerns the demo deployment, not npm registries or unrelated services.
- Use an existing authorized demo instance when available. To create the local demo, **clone** `lamassuiot/lamassuiot` into a temporary directory and **check out its `v4` branch**. Monolithic launches the UI container itself: configure its image as `ghcr.io/lamassuiot/lamassu-ui:dev`; do not launch a second UI container. Follow [references/runtime.md](references/runtime.md) for exact setup, port discovery, readiness and cleanup. Do not change an existing checkout, assume an instance is disposable, or alter its authentication.
- Create an isolated temporary working directory outside the documentation repository for OpenShowcase installation, Chromium profile, recordings, browser data, intermediate exports and logs. Keep authentication secrets out of the flow and deliverables. Use `--profile` to point OpenShowcase at a profile in that directory. Clean up only owned temporary resources after completion; retain the persistent flow and requested deliverables.

## Integrated terminal

- For workflows requiring shell commands, use the terminal built into the Lamassu UI. Open it from the terminal icon in the top bar; it appears as a panel below the current page and can be resized, expanded or closed using its controls. Inspect the current UI and use its actual accessible names and selectors.
- Record the dashboard and terminal together in the same UI. Do not deploy WebSSH, SSH Easy, a separate terminal container, or an iframe wrapper for new recordings. When updating an older flow that used them, adapt its URL, selectors, terminal actions and popups to the integrated terminal before inspecting or recording.
- Before recording, verify that the integrated terminal is available, that its environment has the required commands and can reach the target services, and that its output is visible and readable. Use synthetic data and avoid exposing secrets. If a required capability is unavailable, report the blocker rather than assuming the old terminal environment or silently substituting another one.

## OpenShowcase workflow

1. Inspect the installed recorder's `--help` and version; install it in the temporary directory if needed. Use its own Playwright Chromium and extension. Refer to the installed recorder README for the current flow schema and command syntax.
2. Sign in manually if necessary, using the temporary profile; never ask for passwords or tokens in chat. Inspect the target UI and build a valid `.flow.json` with `title`, HTTP `url`, appropriate `viewport`, and `steps`. Wait for a specific visible control or result after navigation or creation; a URL change or a loading placeholder is not proof that the page is ready. Each `inspect` and `record` actually executes the steps and server-side changes persist: use synthetic data, keep repeated runs independent with unique test names or reset only owned demo data, and restrict changes to the requested demo.
3. Run `openshowcase-recorder inspect <flow.json> --profile <temporary-profile>` and confirm all steps complete. Fix observed failures before recording. Record with `openshowcase-recorder record <flow.json> --out <temporary-file.osrec> --profile <temporary-profile>`, then export via `openshowcase-recorder export <temporary-file.osrec> --out <temporary-demo.openshowcase|zip>`. Check actual CLI help for the installed version. Do not assume editor changes are saved back into `.osrec`; export from the editor if the user edited the take there.
   **Every step needs a popup:** give each user action a descriptive `tooltip`, never use `"hotspot": false`, split multi-field forms into one popup per field or group, put a `click` with `tooltip` before every `fill`, and put dropdown-option popups on the click that opens the list (options are not recorded). Follow the "Popup rule" in [references/capture.md](references/capture.md) and run its check on the flow and on every exported locale JSON; do not deliver a demo with silent steps.
   **Every demo also needs a detailed guide** (`guide.<locale>.json`, one entry per popup, in every locale) shown beside the video: follow "Detailed guide beside the video" in [references/capture.md](references/capture.md), using only verified facts.
4. Review the actual result for readable framing, working hotspots, complete page loading and smooth motion. Adjust the flow or capture settings based on evidence. A larger CSS viewport is not necessarily a larger usable output: the tested OpenShowcase 0.6.2 captures and renders at twice the viewport size, which limits recordings to about 21 fps. **Always** apply both temporary patches (1× extension and `--force-device-scale-factor=1`) from "Reach 60 fps without shrinking the UI" in [references/capture.md](references/capture.md), preserving the requested logical viewport; they reached 60 fps at 1600 × 900. Verify the resulting dimensions and actual frame intervals; never claim a target frame rate was achieved without measuring it. Keep experimental tool changes in the temporary directory and report them.
5. Copy only the persistent flow, final player assets and files required by the requested integration to their intended locations. Copy the whole exported `assets/` folder: the `step-N.avif` stills are required, because each popup is drawn over one, so never delete them; only files that no locale JSON references may be removed, and the check in "Export assets: keep the stills" in [references/capture.md](references/capture.md) must report nothing `Missing`. Do not add `node_modules`, profiles, raw recordings, screenshots, local logs or scratch scripts to the documentation repository. The exported demo can contain visible data: review it for secrets or private information before inclusion.
6. Verify the result at the requested destination or in the local output folder. For a docs integration, check asset resolution, localized labels and the project's applicable build/type checks. An ephemeral UI port can change on the next run: preserve the actual HTTP URL in the flow, identify it as runtime-specific, and update it after rediscovering the port. Report what was generated, where the JSON and demo live, what was verified, and any remaining limitations. Ask for review when required by the user or a higher-priority instruction, not as an unconditional gate.
