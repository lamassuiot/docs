Esta guía arranca Lamassu Updates (el OTA Update Service) con Docker Compose, en su modo nativo por defecto, y comprueba que la API responde. Lleva unos diez minutos más la construcción de las imágenes. Cuando funcione, continúa con [Publica y lanza una actualización](/docs/platform/iot-fleets/updates/guides/publish-and-roll-out).

## Antes de empezar

- Docker con el plugin Compose.
- Una instancia de Lamassu IoT en ejecución a la que lleguen los contenedores. El servicio lee los grupos de dispositivos y sus dispositivos desde su Device Manager (`dms_endpoint`) y firma con su KMS (`kms_endpoint`) solo cuando pides construcciones firmadas.
- Una copia del [repositorio `ota`](https://github.com/lamassuiot/ota) con los módulos `core` y `sdk` de Lamassu a su lado. `go.mod` sustituye `lamassuiot/core` y `lamassuiot/sdk` por rutas locales, y la construcción de Docker los copia desde el **directorio padre** de la copia (`context: ..` en `docker-compose.yml`), así que ese directorio debe contener `ota/` y `lamassuiot/`.
- Acceso a la imagen `ghcr.io/lamassuiot/wfx:otaq`, que usa el servicio `custom-wfx`.
- Opcional, para el [modo hawkBit](/docs/platform/iot-fleets/updates/hawkbit-mode): un servidor hawkBit. Compose construye uno desde `docker/hawkbit`: hawkBit 1.1.0 más un plugin de artefactos S3, etiquetado en local como `lamassu/hawkbit-update-server:1.1.0-s3`. Esa imagen se construye en local y no está publicada.
- Opcional, para ejecutar el servicio fuera de Docker: Go 1.26.2 o superior y Python 3.8 o superior con los requisitos de `swugenerator` instalados. La imagen de Docker ya contiene el binario compilado y Python con `swugenerator`.

## Arranca el stack

<Steps>
  <Step>
    ### Clona el repositorio

    ```bash
    git clone https://github.com/lamassuiot/ota.git
    cd ota
    ```
  </Step>
  <Step>
    ### Indica la dirección del host

    El contenedor `updates` llega a Lamassu a través de `host.docker.internal`, que `docker-compose.yml` sustituye por `HOST_IP`. En WSL2, `host.docker.internal` apunta por defecto a la pasarela de Docker Desktop y no al host de WSL, así que indica tu propia dirección:

    ```bash
    cp .env.example .env
    HOST_IP=$(hostname -I | awk '{print $1}')
    sed -i "s/HOST_IP=/HOST_IP=${HOST_IP}/" .env
    ```

    Después comprueba que `dms_endpoint` y `kms_endpoint` de `config-docker.yml` apuntan a la API de tu Lamassu (por defecto son `http://host.docker.internal:8080/api/...`).
  </Step>
  <Step>
    ### Crea la red y arranca

    `docker-compose.yml` se conecta a una red existente llamada `ota-net` y no arranca sin ella.

    ```bash
    docker network create ota-net
    docker compose up --build
    ```
  </Step>
</Steps>

### Servicios

| Servicio | Puerto del host | Qué es |
|---|---|---|
| `updates` | `10090` | La API de Updates, con SymKMS embebido |
| `custom-wfx` | `9080` (cliente), `9081` (gestión) | WFX, el servidor de trabajos que los dispositivos consultan en modo nativo |
| `postgres` | `5000` (contenedor `5432`) | Base de datos. `init.sql` crea las bases `updates` y `hawkbit` en el primer arranque |
| `swupdate-device1` | `80` | Un cliente de dispositivo SWUpdate de ejemplo |
| `hawkbit` | `8090` | Servidor hawkBit, solo para el [modo hawkBit](/docs/platform/iot-fleets/updates/hawkbit-mode) |
| `rustfs` | `9000` (S3), `9001` (consola) | Almacén S3 local, solo con `--profile s3` |

`docker compose --profile s3 up -d` también arranca `rustfs` y `s3-init`, que crea el bucket cifrado `ota-updates` que pueden usar los artefactos, las construcciones y el almacenamiento de artefactos de hawkBit. Sin ese perfil, y con `config-docker.yml`, los artefactos y las construcciones se quedan en el volumen `update_files`.

## Verifica la API

```bash
curl -s localhost:10090/health
# {"status":"ok"}

curl -s localhost:10090/updates/v1/capabilities
```

La segunda llamada informa del backend activo y de lo que admite. En modo nativo se parece a esto (abreviado):

```json
{
  "backend": "native",
  "supported": { "workflows": true, "campaigns": true, "software_module_deliverables": false },
  "unsupported": ["software_module_deliverables", "software_module_replace"]
}
```

`supported` tiene una entrada por cada una de las 22 capacidades. Consulta [Capacidades](/docs/platform/iot-fleets/updates/reference/capabilities) para saber qué significa cada una.

## Ejecuta sin Docker

Arranca el punto de entrada monolítico con un fichero de configuración. Ejecuta juntos la API de Updates y SymKMS.

```bash
OTA_CONFIG_FILE=/path/to/config.yml go run ./cmd/monolithic
```

Si `OTA_CONFIG_FILE` no está definida, el servicio lee `/etc/lamassuiot/config.yml`.

Para construir ficheros `.swu` fuera de Docker, instala `swugenerator` en el entorno de Python al que apunta la configuración (la imagen hace lo mismo desde `swugenerator/requirements.txt`):

```bash
python3 -m venv .venv
.venv/bin/pip install -r swugenerator/requirements.txt
.venv/bin/pip install -e swugenerator
```

El `config.yml` de la raíz del repositorio es un punto de partida para desarrollo local, no un fichero listo para usar:

- Necesita Postgres (`localhost:5000`) y la API de gestión de WFX (`localhost:9081`), que proporciona `docker compose up -d postgres custom-wfx`.
- Contiene valores de una máquina de desarrollo concreta: rutas absolutas `/home/alvaro/...` para el almacenamiento de artefactos y de SymKMS, el script de firma y `swugenerator`, y una IP de la LAN para los endpoints de Lamassu. Edítalos con rutas que el usuario del servicio pueda crear; el servicio se detiene al arrancar si no puede crear sus directorios.
- Guarda artefactos y salidas de construcción en el bucket local de RustFS (`docker compose --profile s3 up -d`). Para usar disco local en su lugar, elimina los bloques `artifacts:` y `builds:`; cuando no están, los artefactos van por defecto a `{update_files_base_dir}/artifacts`.

### Prueba el modo hawkBit

El modo hawkBit sirve la misma API sobre un servidor hawkBit real. Arranca hawkBit y Postgres, espera a que hawkBit responda y arranca el servicio con la configuración de hawkBit:

```bash
docker compose up -d postgres hawkbit

until curl -sf -u admin:admin 'http://localhost:8090/rest/v1/targets?limit=1' >/dev/null; do sleep 2; done

OTA_CONFIG_FILE=./config-hawkbit.yml go run ./cmd/monolithic
curl -s localhost:10090/updates/v1/capabilities   # "backend":"hawkbit"
```

`config-hawkbit.yml` también contiene rutas de una máquina de desarrollo, en los ajustes de construcción de SWU. Un servicio apuntado a un hawkBit sin dispositivos registrados construye y lanza con normalidad, pero nada descarga la actualización, porque en modo hawkBit los dispositivos consultan a hawkBit directamente. Lee el [modo hawkBit](/docs/platform/iot-fleets/updates/hawkbit-mode) antes de usarlo.

## Solución de problemas

| Síntoma | Causa probable |
|---|---|
| `docker compose up` falla por la red | `ota-net` no existe. Ejecuta `docker network create ota-net` |
| El contenedor `updates` no llega a Lamassu | `HOST_IP` está vacío en `.env`, o `dms_endpoint` de `config-docker.yml` apunta a una dirección que el contenedor no alcanza |
| `docker compose up --build` falla al copiar `lamassuiot/core` | El contexto de construcción (el padre de `ota/`) no contiene `lamassuiot/` |
| El servicio termina al arrancar cuando se ejecuta en el host | Un directorio de la configuración (`update_files_base_dir`, `sym_keys_dir`) no se puede crear, o Postgres o WFX no son alcanzables en las direcciones del fichero |
| `capabilities` responde pero los grupos de dispositivos fallan con un error del Device Manager | `dms_endpoint` es incorrecto. La API de Updates lee de él los dispositivos de cada grupo |
