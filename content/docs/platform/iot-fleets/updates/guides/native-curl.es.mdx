---
title: Flujo de actualización con curl, backend native
description: Todas las peticiones de una actualización completa en modo native, desde crear un pack hasta el último dispositivo, con respuestas reales.
---

Una actualización completa, petición a petición: crear un pack, compilarlo, enviarlo a un grupo por lotes, hacer de dispositivo y seguir el progreso. Todos los comandos se ejecutaron contra un stack en modo native, y las respuestas son reales, recortadas cuando son largas, salvo donde una sección indica que no se ejecutó: esos ejemplos solo se comprobaron contra el código.

Si usas el [backend hawkBit](/docs/platform/iot-fleets/updates/guides/hawkbit-curl), el flujo cambia, sobre todo en cómo se compila un pack y en cómo informan los dispositivos. Para las pantallas que hacen lo mismo, consulta la [guía del dashboard](/docs/platform/iot-fleets/updates/guides/dashboard).

## Antes de empezar

- El [stack está en marcha](/docs/platform/iot-fleets/updates/getting-started) en modo native: el servicio, Postgres, WFX y el device manager de Lamassu.
- Existe un grupo de dispositivos en Lamassu con dispositivos dentro. Esta guía usa el grupo `fleet-a` con los dispositivos `dev-001` a `dev-004`.
- Tienes `curl` y `jq` instalados. `jq` solo se usa para extraer valores de las respuestas.

```bash
API=http://localhost:10090/updates/v1
WFX=http://localhost:9080/api/wfx/v1      # WFX client API: what a device talks to
GROUP=fleet-a
```

Estas son las direcciones del stack de Docker Compose del repositorio. A través de un gateway de Lamassu la API suele ser `https://lamassu.example.com/api/updates/v1`, y entonces cada llamada necesita la credencial que exija tu gateway, por ejemplo `-H "Authorization: Bearer $TOKEN"`. El servicio en sí no autentica. Consulta [Seguridad](/docs/platform/iot-fleets/updates/security).

## 1. Comprueba el backend

```bash
curl -s $API/capabilities | jq -c '{backend, unsupported}'
```
```json
{"backend":"native","unsupported":["software_module_deliverables","software_module_replace"]}
```

## 2. Crea el pack

```bash
curl -s -X POST $API/groups/$GROUP/distribution-sets \
  -H 'Content-Type: application/json' \
  -d '{"name":"water-panel","version":"1.0.0","group_id":"fleet-a","type":"rawfile","packaging":"swu"}'
```
```json
{"id":"bb74c7e1-ae3d-450b-bc73-6ed2d761934f","name":"water-panel","version":"1.0.0","group_id":"fleet-a",
 "type":"rawfile","packaging":"swu","status":"draft","uri":"", ...}
```

El pack está en `draft`. Sigue siendo editable hasta que se compila. `name`, `version` (semver) y `group_id` son obligatorios; el nombre debe ser único en el grupo, o la petición responde `409`.

## 3. Sube el sw-description y el artefacto

El sw-description le dice a SWUpdate qué instalar. Este, mínimo, instala una página web. Consulta las reglas del sw-description en [Publicar y desplegar una actualización](/docs/platform/iot-fleets/updates/guides/publish-and-roll-out).

```bash
cat > sw-description <<'EOD'
software =
{
	version = "1.0.0";
	description = "Water panel";
	hardware-compatibility: [ "1.0" ];
	images: (
		{
			filename = "index.html";
			path = "/web/index.html";
			type = "rawfile";
			compressed = "zlib";
			properties: {
				decompressed-size = "52";
			};
		}
	);
}
EOD
printf '<html><body><h1>Water panel v1.0</h1></body></html>\n' > index.html

P=$API/groups/$GROUP/distribution-sets/water-panel

curl -s -X POST $P/descriptor/upload -F file=@sw-description
# {"msg":"Descriptor uploaded successfully"}

ART=$(curl -s -X POST $P/artifact/upload \
  -F file=@index.html -F artifact_name=index.html -F version=1.0.0 | jq -r .artifact.id)
echo $ART
```
```text
31e034d1-9dfa-43d9-ac6b-45fa79e2d51d
```

El nombre del artefacto es global: todos los packs comparten un único catálogo, y un nombre solo se puede reutilizar con una `version` **mayor**. Volver a subir `index.html` como `1.0.0` falla con `version 1.0.0 must be greater than the current latest version`. Un archivo llamado `.swu` o `.tar.gz` debe serlo realmente, o la subida responde `400`.

## 4. Compila el `.swu`

`selected_artifact_ids` es lo que incorpora artefactos a la compilación. Sin él, la compilación falla.

```bash
curl -s -X POST $P/swu -H 'Content-Type: application/json' \
  -d "{\"selected_artifact_ids\":[\"$ART\"]}"
```
```json
{"message":"Update pack executed successfully"}
```

```bash
curl -s $API/groups/$GROUP/distribution-sets | jq -c '.list[] | {name,version,status,uri}'
```
```json
{"name":"water-panel","version":"1.0.0","status":"built","uri":"http://updates:10090/updates/v1/groups/fleet-a/distribution-sets/water-panel/swu/download"}
```

La `uri` empieza por el `update_domain` del servicio. En el stack de Compose es `http://updates:10090/updates/v1/` (`config-docker.yml`), un nombre que solo se resuelve dentro de la red de Compose, porque es la dirección que usan los dispositivos. Desde tu host, llama a la misma ruta en `localhost:10090`, como hace el siguiente comando.

El pack ya está `built`: ya no se pueden añadir ni enlazar artefactos. Puedes descargar el paquete compartido (este no está cifrado):

```bash
curl -s -o water.swu -w '%{http_code} %{size_download} bytes\n' $P/swu/download
# 200 1024 bytes
```

Las descargas admiten `Range` y `HEAD`, así que un cliente puede conocer antes el tamaño y reanudar una transferencia interrumpida, por ejemplo con `curl -C - -o water.swu $P/swu/download`. Con almacenamiento S3 y la firma previa activada, la misma petición puede responder `302` a una URL firmada de corta duración, que `curl -L` sigue.

Si la compilación falla, el pack pasa a `build_failed` y `last_build_error` contiene el motivo. Sigue siendo editable: corrige la causa y compila de nuevo.

## 5. Simula y crea el lanzamiento

Una simulación (dry run) muestra quién recibiría la actualización, sin crear nada:

```bash
curl -s -X POST "$API/groups/$GROUP/launch?dry_run=true" \
  -H 'Content-Type: application/json' \
  -d '{"distribution_set_name":"water-panel","workflow_type":"direct","rollout_type":"fixed","rollout_value":2,"test_device_id":"dev-001"}'
```
```json
{"never_seen_devices":null,"precondition_failures":[],
 "qualifying_devices":["dev-001","dev-002","dev-003","dev-004"],"superseded_devices":null}
```

Créalo. `test_device_id` es el canario: va solo primero y debe tener éxito antes de tocar a ningún otro. `rollout_value` 2 significa lotes de dos dispositivos.

```bash
LAUNCH=$(curl -s -X POST $API/groups/$GROUP/launch -H 'Content-Type: application/json' \
  -d '{"distribution_set_name":"water-panel","workflow_type":"direct","rollout_type":"fixed","rollout_value":2,"test_device_id":"dev-001","name":"water-panel 1.0.0 wave 1"}' \
  | jq -r .launch_id)
echo $LAUNCH
```
```text
98af8db7-b3a0-4802-8cde-269d88e6723e
```

Una pequeña función auxiliar facilita seguir el lanzamiento en los pasos siguientes:

```bash
status() {
  curl -s $API/groups/$GROUP/launch | jq -c --arg id "$LAUNCH" \
    '.list[] | select(.id==$id) | {status,pending_count,active_count,completed_count,failed_count,test_device_status}'
}
```

## 6. Despliega el canario

```bash
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/rollout
# {"message":"Launch history executed successfully"}

status
```
```json
{"status":"","pending_count":3,"active_count":1,"completed_count":0,"failed_count":0,"test_device_status":"active"}
```

Un `status` vacío significa en ejecución. Solo el canario está activo. El servicio creó un job de WFX para `dev-001`:

```bash
curl -s $API/launch/$LAUNCH/jobs | jq -r '.list[] | "\(.clientId) \(.status.state)"'
# dev-001 INSTALL
```

## 7. Haz de dispositivo

Un dispositivo real hace esto por sí mismo. Estos comandos son lo que envía a WFX, de modo que puedes manejar a mano un dispositivo de prueba. Primero el dispositivo le pide su job a WFX:

```bash
curl -s "$WFX/jobs?clientId=dev-001&state=INSTALL" | jq '.content[0] | {id, state: .status.state, definition}'
```
```json
{
  "id": "35bf5512-1aa3-46e6-9a72-2096560e8bf0",
  "state": "INSTALL",
  "definition": {
    "artifacts": [
      {"name": "water-panel",
       "uri": "http://updates:10090/updates/v1/groups/fleet-a/distribution-sets/water-panel/swu/download/dev-001"}
    ],
    "groupID": "fleet-a",
    "launchID": "98af8db7-b3a0-4802-8cde-269d88e6723e",
    "type": ["rawfile"],
    "version": "1.0.0"
  }
}
```

El dispositivo descarga la `uri`, la instala e informa de cada paso:

```bash
JOB=$(curl -s "$WFX/jobs?clientId=dev-001&state=INSTALL" | jq -r '.content[0].id')
# A device resolves "updates" itself; from the host, swap in localhost
curl -s -o water-dev-001.swu "$(curl -s $WFX/jobs/$JOB | jq -r '.definition.artifacts[0].uri' | sed 's#//updates:#//localhost:#')"

for state in INSTALLING INSTALLED; do
  curl -s -X PUT $WFX/jobs/$JOB/status -H 'Content-Type: application/json' -d "{\"state\":\"$state\"}"
done
curl -s $WFX/jobs/$JOB | jq -r .status.state      # ACTIVATE: WFX moved it on by itself

for state in ACTIVATING ACTIVATED; do
  curl -s -X PUT $WFX/jobs/$JOB/status -H 'Content-Type: application/json' -d "{\"state\":\"$state\"}"
done
```

El workflow `direct` es `INSTALL → INSTALLING → INSTALLED → ACTIVATE → ACTIVATING → ACTIVATED`. El propio WFX da el paso `INSTALLED → ACTIVATE`. Para informar de un fallo, mueve un job a `TERMINATED`.

El servicio se entera de cada cambio por WFX a través de su flujo de eventos y actualiza el lanzamiento. Tarda un instante, así que si `status` aún muestra el dispositivo como activo, vuelve a ejecutarlo al cabo de un segundo:

```bash
sleep 2; status
```
```json
{"status":"","pending_count":3,"active_count":0,"completed_count":1,"failed_count":0,"test_device_status":"completed"}
```

## 8. Despliega el resto

El canario ha pasado. Cada llamada a `rollout` envía ahora el siguiente lote de dos:

```bash
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/rollout
curl -s $API/launch/$LAUNCH/jobs | jq -r '.list[] | select(.status.state=="INSTALL") | .clientId'
# dev-003
# dev-004
```

Haz pasar a esos dispositivos por pasos como los del paso 7 y vuelve a llamar a `rollout` para el último dispositivo. Cuando no queda nada pendiente ni activo, el lanzamiento se completa solo:

```json
{"status":"completed","pending_count":0,"active_count":0,"completed_count":4,"failed_count":0}
```

`completed_count` cuenta solo los éxitos: un dispositivo fallido se cuenta en `failed_count`. Un lanzamiento se marca como `completed` cuando no queda nada pendiente ni activo, aunque algunos dispositivos hayan fallado, así que comprueba `failed_count` antes de dar la actualización por buena.

## 9. Comprueba el resultado

```bash
# What a device carries now, with its artifacts
curl -s $API/devices/dev-001/distribution-set-inventory | jq -c '.list[] | {distribution_set_name,version,installed_at}'
# {"distribution_set_name":"water-panel","version":"1.0.0","installed_at":"2026-10-21T07:35:49.434581+02:00"}

# The history of update attempts
curl -s $API/devices/dev-001/distribution-set-updates | jq -c '.list[] | {version_from,version_to,status}'
# {"version_from":"","version_to":"1.0.0","status":"success"}
```

Para seguir la deriva, declara la versión en la que deben estar los dispositivos y lee después la conformidad:

```bash
PACK=$(curl -s $API/groups/$GROUP/distribution-sets | jq -r '.list[] | select(.name=="water-panel") | .id')
curl -s -X PUT $API/groups/$GROUP/latest-distribution-sets/$PACK \
  -H 'Content-Type: application/json' -d '{"version":"1.0.0"}'
curl -s $API/groups/$GROUP/version-status | jq -c '.rows[] | {device_id,current_version,latest_version,in_sync}'
curl -s $API/groups/$GROUP/version-compliance
# {"group_id":"fleet-a","devices":[]}      no device is out of date
```

La vista de toda la flota con el último intento por dispositivo y pack, incluidos los intentos ajenos a cualquier lanzamiento, es una sola llamada. No se ejecutó aquí; los corchetes de un filtro necesitan `curl -g`:

```bash
curl -sg "$API/devices/distribution-set-updates/latest?filter=status[eq]failed" | jq -c '.list[] | {device_id,distribution_set_name,version_to,status}'
```

## Variaciones

### Deja que el servicio libere los lotes

Con `auto` activado, el servicio envía por sí mismo el siguiente lote cuando ha tenido éxito una parte suficiente del actual. `approval_threshold` es el porcentaje del lote que debe tener éxito (0 o 100 significan todo el lote). `error_threshold` se aplica a todos los lanzamientos, con `auto` o sin él: el lanzamiento se cancela cuando el número de dispositivos fallidos alcanza ese porcentaje de **todos** los dispositivos, redondeado hacia arriba. Con 4 dispositivos al 75 %, el tercer fallo lo cancela.

Este ejemplo usa un segundo pack, `valve-panel`, creado y compilado como `water-panel` (pasos 2 a 4). Los nombres de artefacto son globales y un nombre que ya existe debe recibir una versión mayor, así que dale a este su propio nombre de archivo:

```bash
PV=$API/groups/$GROUP/distribution-sets/valve-panel
curl -s -o /dev/null -X POST $API/groups/$GROUP/distribution-sets -H 'Content-Type: application/json' \
  -d '{"name":"valve-panel","version":"1.0.0","group_id":"'$GROUP'","type":"rawfile","packaging":"swu"}'
cp index.html valve.html
sed 's/index.html/valve.html/' sw-description > sw-valve
curl -s -o /dev/null -X POST $PV/descriptor/upload -F file=@sw-valve
AV=$(curl -s -X POST $PV/artifact/upload -F file=@valve.html -F artifact_name=valve.html -F version=1.0.0 | jq -r .artifact.id)
curl -s -X POST $PV/swu -H 'Content-Type: application/json' -d "{\"selected_artifact_ids\":[\"$AV\"]}"

LAUNCH=$(curl -s -X POST $API/groups/$GROUP/launch -H 'Content-Type: application/json' \
  -d '{"distribution_set_name":"valve-panel","workflow_type":"direct","rollout_type":"fixed","rollout_value":2,
       "auto":true,"approval_threshold":50,"error_threshold":75,"name":"valve auto"}' | jq -r .launch_id)
```

Llama a `rollout` una vez para empezar. Una segunda llamada se rechaza:

```bash
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/rollout
```

```text
{"err":"Failed to execute launch history: operation not valid in the current state: launch 72afe5f7-... rolls out automatically: its next batch is released once the current one meets the approval threshold"}   [400]
```

Si un dispositivo del primer lote falla (`TERMINATED`) y el otro tiene éxito, el 50 % de éxitos cumple el umbral y el siguiente lote se despacha solo.

### Pausar, reanudar, reintentar y cancelar

```bash
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/pause     # {"message":"Launch paused","status":"paused"}
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/resume    # {"message":"Launch resumed","status":"running"}
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/retry-failed
curl -s -X POST $API/groups/$GROUP/launch/$LAUNCH/cancel    # {"message":"Launch cancelled","status":"cancelled"}
```

Una pausa deja terminar el lote en curso y retiene el siguiente. `retry-failed` devuelve los dispositivos fallidos al conjunto de pendientes y libera el siguiente lote. Ese lote se saca al azar de todos los dispositivos pendientes, así que también puede incluir dispositivos a los que nunca se envió nada, y si han fallado más dispositivos de los que caben en un lote, solo sale un lote. Responde `400` cuando no ha fallado nada, y reabre un lanzamiento completado o cancelado (`"status":"running"`). Un canario fallido pausa el lanzamiento por sí mismo, y `resume` vuelve entonces a enviar el canario. Un lanzamiento cancelado no se puede reanudar, y los dispositivos en curso terminan su job actual.

### Programar un lanzamiento

No se ejecutó aquí. `scheduled_at` (RFC 3339) retrasa el primer lote. El servicio busca lanzamientos pendientes aproximadamente cada 30 segundos, así que el inicio puede retrasarse hasta ese tiempo. Una llamada a `rollout` antes de la hora no hace nada.

```bash
curl -s -X POST $API/groups/$GROUP/launch -H 'Content-Type: application/json' \
  -d '{"distribution_set_name":"water-panel","workflow_type":"direct","rollout_type":"fixed","rollout_value":2,
       "scheduled_at":"2026-12-01T03:00:00Z","name":"night wave"}'
```

La programación sobrevive a un reinicio y la ejecuta la réplica que tenga en cada momento el rol de líder, de modo que un lanzamiento programado se despacha una sola vez aunque haya varias réplicas.

### Exigir una versión antes de actualizar

No se ejecutó aquí. Un pack puede exigir que un dispositivo ya tenga otro pack, o un módulo, en una versión mínima. La regla vive en el pack que lanzas. Los dispositivos que no la cumplen se dejan fuera, y la simulación los lista:

```bash
curl -s -X PUT $P/preconditions -H 'Content-Type: application/json' \
  -d '{"preconditions":[{"required_distribution_set_name":"base-os","min_version":"1.0.0"}]}'
curl -s -X POST "$API/groups/$GROUP/launch?dry_run=true" -H 'Content-Type: application/json' \
  -d '{"distribution_set_name":"water-panel","workflow_type":"direct","rollout_type":"fixed","rollout_value":2}' | jq -c .precondition_failures
```

Cada fallo indica el `device_id`, el `distribution_set_name` (y `module_key` en una regla de módulo), la `current_version` que tiene el dispositivo (vacía si no tiene ninguna) y la restricción `required`, por ejemplo `>=1.0.0`. Usa `required_module_key` con un valor `type:name` para exigir un módulo en su lugar. `force_preconditions: true` en el cuerpo del lanzamiento despliega a todos los dispositivos de todos modos y registra los fallos.

### Actualizar un dispositivo a una versión

No se ejecutó aquí. `force-version` lanza un solo dispositivo a una versión exacta de un pack, fuera de cualquier campaña, y responde `202`. El dispositivo debe ser miembro del grupo del pack:

```bash
curl -s -X POST $API/devices/dev-002/force-version -H 'Content-Type: application/json' \
  -d "{\"distribution_set_id\":\"$PACK\",\"version\":\"1.0.0\",\"group_id\":\"$GROUP\",\"workflow\":\"direct\"}"
# {"status":"dispatched","device_id":"dev-002","distribution_set_id":"...","version":"1.0.0"}
```

Sin `workflow`, un pack `swu` usa `phased`. Solo se puede forzar la versión actual del pack, salvo que el pack se haya creado con `allow_previous_version_download`.

### Una nueva versión

```bash
curl -s -X POST $P/new -H 'Content-Type: application/json' -d '{"version":"1.1.0"}'
```

La versión debe ser mayor que la actual, y el pack conserva su id. La nueva versión empieza como `draft`. Los enlaces de artefactos y la composición de módulos se heredan, pero el sw-description no: súbelo de nuevo. Después compila con `selected_artifact_ids` (una compilación sustituye los enlaces heredados por los que selecciones), tras subir una nueva versión del artefacto si el archivo cambió.

### Cifrar con una clave compartida

Una sola clave cifra el `.swu` para todos los dispositivos. El sw-description debe marcar los archivos que se cifran con `encrypted = true;`. Usa un pack distinto para cada variante de cifrado: una nueva versión hereda los ajustes de cifrado de la anterior, y una compilación sin cifrado no los borra. Recompilar un pack ya compilado con otros ajustes también deja campos obsoletos. Consulta [Limitaciones](/docs/platform/iot-fleets/updates/limitations).

Esta función auxiliar crea un pack, sube un sw-description que marca su archivo con `encrypted = true;` y sube el artefacto. Imprime el id del artefacto.

```bash
new_enc_pack() {
  local name=$1 p=$API/groups/$GROUP/distribution-sets/$1
  curl -s -o /dev/null -X POST $API/groups/$GROUP/distribution-sets -H 'Content-Type: application/json' \
    -d "{\"name\":\"$name\",\"version\":\"1.0.0\",\"group_id\":\"$GROUP\",\"type\":\"rawfile\",\"packaging\":\"swu\"}"
  sed "s/index.html/$name.html/; s/compressed = \"zlib\";/&\n\t\t\tencrypted = true;/" sw-description > sw-$name
  curl -s -o /dev/null -X POST $p/descriptor/upload -F file=@sw-$name
  cp index.html $name.html
  curl -s -X POST $p/artifact/upload -F file=@$name.html -F artifact_name=$name.html -F version=1.0.0 | jq -r .artifact.id
}
```

```bash
SK=http://localhost:10090/symkms/v1
ARTE=$(new_enc_pack water-panel-enc)
PE=$API/groups/$GROUP/distribution-sets/water-panel-enc

KEY=$(openssl rand -hex 32)
curl -s -X POST $SK/ -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"ops\",\"algorithm\":\"AES-256-GCM\",\"key\":\"$KEY\",\"id\":\"fleet-a-shared\"}"
# {"id":"fleet-a-shared","user_id":"ops","algorithm":"AES-256-GCM","created_at":"..."}

curl -s -X POST $PE/swu -H 'Content-Type: application/json' \
  -d "{\"user\":\"ops\",\"encryption_key_name\":\"fleet-a-shared\",\"encryption_alg_name\":\"AES-256-GCM\",\"selected_artifact_ids\":[\"$ARTE\"]}"
```

El pack informa entonces `"encryption_mode":"shared"`. El dispositivo necesita la misma clave y el mismo algoritmo. Consulta [Firma y cifrado](/docs/platform/iot-fleets/updates/signing-and-encryption).

### Cifrar por dispositivo

Cada dispositivo recibe su propio paquete y su propia clave. Es otro pack, compilado con la misma función auxiliar. El sw-description debe marcar un archivo con `encrypted = true;`, o la compilación se rechaza.

```bash
ARTP=$(new_enc_pack water-panel-pd)
PP=$API/groups/$GROUP/distribution-sets/water-panel-pd

for d in dev-001 dev-002 dev-003 dev-004; do
  curl -s -X POST $SK/ -H 'Content-Type: application/json' \
    -d "{\"user_id\":\"ops\",\"algorithm\":\"AES-256-GCM\",\"key\":\"$(openssl rand -hex 32)\",\"id\":\"pd-$d\"}"
  curl -s -X POST $SK/inventory/$d/keys/pd-$d -H 'Content-Type: application/json' \
    -d '{"purpose":"firmware-encryption"}'
done

curl -s -X POST $PP/swu -H 'Content-Type: application/json' \
  -d "{\"encryption_alg_name\":\"AES-256-GCM\",\"selected_artifact_ids\":[\"$ARTP\"]}"
curl -s $API/groups/$GROUP/distribution-sets | jq -c '.list[] | select(.name=="water-panel-pd") | {status,encryption_mode,built_device_count,total_device_count}'
# {"status":"built","encryption_mode":"per-device","built_device_count":4,"total_device_count":4}

curl -s -o dev-001.swu $PP/swu/download/dev-001     # each device downloads its own file
```

Si un dispositivo no tiene clave en el momento de la compilación, la compilación termina bien y el pack registra el hueco. Si **ningún** dispositivo tiene clave, la compilación falla.

```json
{"encryption_mode":"per-device","built_device_count":3,"total_device_count":4,
 "uncovered_devices":[{"device_id":"dev-004","reason":"no firmware-encryption key assigned"}]}
```

Un lanzamiento sobre ese pack se rechaza, simulaciones incluidas, y `force_preconditions` no lo anula:

```text
{"err":"Cannot create launch: update pack \"water-panel\" is per-device encrypted and only 3 of 4 devices have a package. The rest would fail to download. Missing: dev-004 (no firmware-encryption key assigned). Fix those devices and regenerate the SWU."}   [400]
```

La cobertura se registra cuando se compila el pack, así que asignar la clave que falta no basta. Compila el pack de nuevo (una nueva versión) con una clave para cada dispositivo.

### Firmar el paquete

Añade los campos de firma con KMS al cuerpo de la compilación. Necesitan una clave de firma y un certificado en el KMS de Lamassu, con `kms_endpoint` y `sign_script_path` configurados. Esta petición no se ejecutó aquí, porque necesita un KMS. Consulta [Firma y cifrado](/docs/platform/iot-fleets/updates/signing-and-encryption).

```bash
jq -n --arg art "$ART" --arg cert "$(cat signer.pem)" '{
    selected_artifact_ids: [$art],
    signature_key_id: "<kms key id>",
    signature_alg_name: "RSASSA_PSS_SHA_256",
    signature_certificate: $cert }' \
  | curl -s -X POST $P/swu -H 'Content-Type: application/json' -d @-
```

## Solución de problemas

| Síntoma | Causa y solución |
|---|---|
| `409` en `artifact/upload` o `artifact/link` | La versión del pack ya está `built`. Crea una nueva versión con `POST .../new` |
| `409` en `POST .../distribution-sets` | Ya existe un pack con ese nombre en el grupo |
| `400 version ... must be greater than the current latest version` | El nombre de un artefacto es global y su versión debe aumentar. Sube con una `version` mayor |
| La compilación falla con un directorio de binarios vacío | La compilación no recibió `selected_artifact_ids` |
| `400` al crear un lanzamiento: el pack no se ha compilado | Compílalo primero. Un pack en `build_failed` tampoco se puede lanzar |
| `400 ... is per-device encrypted and only N of M devices have a package` | Algunos dispositivos no tienen clave `firmware-encryption`. Asigna claves y compila una nueva versión |
| `rollout` responde `400` con `rolls out automatically` | El lanzamiento tiene `auto` activado y ya ha empezado. Espera al umbral de aprobación, o páusalo |
| `rollout` responde `400` con `test device ... failed` | El canario falló. Reanuda el lanzamiento para reintentarlo, o cancélalo |
| `413` en una subida | El archivo supera `max_artifact_size_mb` (10 GiB por defecto), o el límite del gateway o del ingress que hay delante del servicio es menor |
| `501` en una ruta de módulo | El modo native no tiene entregables por módulo. Compila el pack en su lugar |
