Referencia de la API HTTP de Lamassu Updates, tal como la implementa el servicio en `internal/updates/httpapi` (compartido por los backends native y hawkBit). Úsala para consultar una ruta, un campo de un cuerpo o un código de estado. Para ejemplos completos, sigue la guía de curl con el backend [native](/docs/platform/iot-fleets/updates/guides/native-curl) o con [hawkBit](/docs/platform/iot-fleets/updates/guides/hawkbit-curl).

## Convenciones

La API de Updates se sirve bajo `/updates/v1` y SymKMS bajo `/symkms/v1`. Las rutas de esta página son relativas a `/updates/v1`, salvo las que empiezan por `/health` o `/symkms`. Detrás del gateway de Lamassu el prefijo suele ser `/api/updates/v1`, que es lo que llama el dashboard.

`:groupID` es un grupo de dispositivos de Lamassu. `:name` es el nombre de un pack. `:moduleKey` es `type:name` (por ejemplo `os:water-panel`), literal o codificado en porcentaje. En las rutas un pack es un recurso `distribution-sets` (consulta [Conceptos](/docs/platform/iot-fleets/updates/concepts)).

| Tema | Comportamiento |
|---|---|
| Cuerpos | JSON, salvo las subidas, que son `multipart/form-data` con el archivo en el campo `file` |
| Errores | El cuerpo es `{"err":"<mensaje>"}` |
| Health | `GET /health` devuelve `{"status":"ok"}`, fuera de `/updates/v1` |
| Autenticación | Ninguna en el servicio: no autentica a quien llama. En un despliegue de Lamassu lo hace el gateway que tiene delante. Consulta [Seguridad](/docs/platform/iot-fleets/updates/security) |
| Límite de subida | Un archivo puede tener hasta `max_artifact_size_mb` MiB, 10240 (10 GiB) por defecto. Uno mayor responde `413` |
| Timeouts | Una petición puede leer o escribir hasta 6 horas; una conexión inactiva se cierra a los 5 minutos. Las subidas se escriben en disco en streaming, no se mantienen en memoria |
| CORS | Se permite cualquier origen y cualquier cabecera de petición |

El ingress o el gateway que tiene delante el servicio necesita sus propios límites elevados en consonancia: consulta [Configuración](/docs/platform/iot-fleets/updates/reference/configuration).

### Códigos de estado

| Código | Significado |
|---|---|
| `200` | Correcto |
| `201` | Creado: packs, módulos, lanzamientos, subidas de artefactos independientes |
| `202` | Aceptado: `sync-to-latest` y `force-version` |
| `204` | Eliminado, sin cuerpo: artefactos, archivos preparados, registros de última versión, archivos de módulo |
| `206`, `416` | Contenido parcial, o rango no satisfacible, en las descargas |
| `207` | `sync-to-latest` despachó algunos dispositivos y falló en otros |
| `302` | Una descarga redirigida a una URL firmada de corta duración |
| `400` | Entrada no válida, u operación no válida en el estado actual (por ejemplo, cambiar la composición de módulos de un pack ya compilado) |
| `403` | Prohibido por política (por ejemplo, descargar una versión anterior que el pack no permite) |
| `404` | El recurso no existe |
| `409` | Conflicto: la versión del pack ya está compilada (subida o enlace de artefacto, subida de un entregable precompilado), el nombre del pack ya existe, u otra petición está trabajando sobre el mismo recurso |
| `413` | Un archivo subido supera el límite de tamaño |
| `501` | El backend activo no admite la operación. Consulta [Capabilities](/docs/platform/iot-fleets/updates/reference/capabilities) |

### Descargas

Las rutas de descarga transmiten el archivo y permiten reanudar:

- `HEAD` funciona en todas las rutas de descarga y devuelve el tamaño y `Accept-Ranges: bytes`.
- `Range: bytes=...` con un único rango responde `206` con `Content-Range`. Un rango que no se puede satisfacer responde `416`. Una petición con varios rangos recibe el archivo completo.
- Con almacenamiento S3 y la firma previa (presign) activada, un `GET` puede responder `302` a una URL firmada del almacén de objetos, con `Cache-Control: no-store`. Primero se autoriza al que llama; el almacén solo comprueba después la firma. Un `HEAD` nunca se redirige. El modo native firma las salidas de compilación (`.swu` y paquetes); el modo hawkBit firma los objetos del plugin S3 de artefactos de hawkBit. Si falla la firma, el servicio transmite el archivo directamente.
- `Content-Disposition: attachment` lleva el nombre del archivo.

### Endpoints de listado

Las rutas que devuelven colecciones comparten estos parámetros de consulta:

| Parámetro | Significado |
|---|---|
| `page_size` | Elementos por página. Por defecto `25`, como máximo `500` |
| `bookmark` | Cursor opaco de la página anterior |
| `sort_by`, `sort_mode` | Un campo filtrable, y `asc` (por defecto) o `desc`. Un `sort_by` que no sea un campo filtrable se ignora |
| `filter` | `field[operand]value`, repetible |

Los operandos del filtro dependen del tipo de campo:

| Tipo de campo | Operandos |
|---|---|
| String | `eq`, `ne`, `ct` (contiene), `nc` (no contiene), cada uno con una variante `_ic` que no distingue mayúsculas |
| Fecha | `bf` (antes), `eq`, `af` (después) |
| Número | `eq`, `ne`, `lt`, `le`, `gt`, `ge` |
| Enum | `eq`, `ne` |

Por ejemplo `GET /groups/g1/distribution-sets?filter=name[ct]firmware&sort_by=name&sort_mode=desc`.

Los listados paginados devuelven `{"next": "<bookmark>", "list": [...]}`. Pasa `next` como `bookmark` para obtener la página siguiente; `next` está vacío en la última. Campos filtrables por listado:

| Listado | Campos filtrables |
|---|---|
| Packs: `.../distribution-sets`, `/distribution-sets` | `group_id`, `name`, `version`, `packaging` (enum), `created_at` |
| Lanzamientos: `/groups/:groupID/launch` | `group_id`, `status` (enum), `workflow_type`, `created_at`, `distribution_set_id` |
| Instantáneas de versión: `.../versions`, `/distribution-sets/:id/versions` | `version` (número), `created_at` |
| Catálogo de artefactos de la flota: `GET /artifacts` | `name`, `version`, `checksum`, `uploaded_at` |
| Versiones de pack e inventario de dispositivos: `/devices/distribution-sets`, `/devices/:deviceID/distribution-sets`, `.../distribution-set-inventory` | `device_id`, `distribution_set_id`, `distribution_set_name`, `group_id`, `version` (número), `packaging` (enum), `installed_at` |
| Historial de actualizaciones de dispositivo: `/devices/:deviceID/distribution-set-updates`, `/devices/distribution-set-updates/latest` | `device_id`, `group_id`, `distribution_set_name`, `distribution_set_id`, `launch_id`, `job_id`, `status` (enum), `packaging` (enum), `source` |
| Últimas versiones: `.../latest-distribution-sets` | `group_id`, `distribution_set_id`, `distribution_set_name`, `version` (string), `updated_at` |

Algunos listados no paginan ni filtran:

- Los listados de jobs (`/groups/:groupID/device/:deviceID/jobs`, `.../history`, `/launch/:launchID/jobs`) solo respetan `page_size` y `bookmark`. El bookmark es un desplazamiento numérico.
- Los listados de módulos, `/updatable-distribution-sets`, el `.../artifact-catalog` de un pack, `/version-compliance`, `/version-status` y `/workflows` devuelven todo.
- `GET /devices/distribution-set-updates/latest` devuelve todo, tras aplicar los filtros.
- En modo hawkBit ningún listado pagina (`next` siempre está vacío). Solo `/devices/distribution-sets` y `/devices/distribution-set-updates/latest`, de ámbito flota, aplican `filter`.

Algunas rutas existen en un solo backend o se comportan de forma distinta. Consulta antes [Capabilities](/docs/platform/iot-fleets/updates/reference/capabilities).

### Descriptor, artefactos y precondiciones

| Método | Ruta (tras `/groups/:groupID/distribution-sets/:name`) | Descripción |
|---|---|---|
| `POST` | `/descriptor/upload` | Sube el sw-description (campo de archivo `file`, hasta 1 MiB en modo native). Modo hawkBit: `400`, usa la ruta del catálogo |
| `GET` | `/descriptor` | Lo lee, como `text/plain` |
| `POST` | `/artifact/upload` | Sube un artefacto global y lo enlaza al pack (campos `file`, `artifact_name`, `version`). `409` si el pack ya está compilado, lo cual ocurre siempre en modo hawkBit |
| `POST` | `/artifact/link` | Enlaza un artefacto global ya subido (cuerpo `{"artifact_id":"..."}`). `409` si el pack está compilado |
| `DELETE` | `/artifact?artifact=<nombre de archivo>` | Elimina un archivo preparado del directorio de compilación. No desenlaza un artefacto del catálogo. Responde `204`. Modo hawkBit: `400` |
| `GET` | `/artifacts` | Nombres de los archivos preparados en el directorio de compilación, como array simple |
| `GET` | `/artifacts/:artifactName` | Descarga un archivo preparado por nombre |
| `GET` | `/artifact-catalog` | Artefactos a los que hace referencia el pack |
| `GET` | `/preconditions` | Lee las precondiciones de lanzamiento del pack. Responde con el pack completo, con `preconditions` |
| `PUT` | `/preconditions` | Sustituye las precondiciones de lanzamiento del pack. Una lista vacía las borra. Responde con el pack |

### Compilación y descarga

| Método | Ruta (tras `/groups/:groupID/distribution-sets/:name`) | Descripción |
|---|---|---|
| `POST` | `/swu` | Compila el `.swu` (cuerpo: consulta [Cuerpos de las peticiones](#cuerpos-de-las-peticiones)). Modo hawkBit: `501`, compila los módulos |
| `POST` | `/package` | Compila el `.tar.gz` de un pack `non-swu`. Modo hawkBit: `501` |
| `POST` | `/swu/upload`, `/package/upload` | Adjunta un entregable compilado externamente (campo de archivo `file`, `user` opcional). Ambas rutas son una sola operación: el empaquetado del pack decide qué archivo se espera. Solo native (`501` en modo hawkBit) |
| `GET` | `/swu/download` | Descarga el `.swu` compartido actual. Modo hawkBit: `400` para un pack con varios módulos, así que usa `/modules/:moduleKey/artifact/download` |
| `GET` | `/swu/download/:deviceID` | Descarga el `.swu` de un dispositivo. En un pack con cifrado por dispositivo es el archivo propio de ese dispositivo; en otro caso, el compartido |
| `GET` | `/swu/download/version/:version` | Descarga una versión anterior. Modo native: `403` salvo que el pack tenga `allow_previous_version_download`, y `404` si no hay instantánea registrada. El modo hawkBit sirve cualquier versión |
| `GET` | `/package/download`, `/package/download/:deviceID` | Lo mismo, para packs `non-swu` (`application/gzip`) |
| `GET` | `/artifacts-archive` | `.tar.gz` con los artefactos de la versión actual |
| `GET` | `/signature` | Manifiesto firmado de la versión actual |

### Cuerpos de las peticiones

| Ruta | Cuerpo |
|---|---|
| Crear pack | Obligatorios: `name`, `version` (semver `x.y.z`), `group_id`. Opcionales: `type` (`rawfile` o `firmware`), `packaging` (`swu`, el valor por defecto, o `non-swu`), `allow_previous_version_download`, `modules`, `preconditions`. Cada entrada de `modules` es un módulo nuevo (`type`, `name`, y opcionalmente `version` y `delivery_intent`) o uno existente (`source_module_id`). El modo hawkBit solo acepta entradas `source_module_id`, de módulos **compilados** |
| `POST .../new` | `{"version":"x.y.z"}`: semver y mayor que la versión actual, o `400` |
| `PUT .../preconditions` | `{"preconditions":[{"required_distribution_set_name":"...","min_version":"1.2.0"}]}`. Usa `required_module_key` (`type:name`) en lugar del nombre del pack para apuntar a un módulo. Exactamente uno de los dos por entrada, y `min_version` debe ser `x.y.z`. Un dispositivo debe cumplir todas las entradas |
| `POST .../swu`, `.../package` | `user`, `encryption_key_name`, `encryption_alg_name`, `sw_desc_encrypted`, `signature_key_id`, `signature_alg_name`, `signature_certificate` (PEM), `selected_artifact_ids`. Todos opcionales, pero `user` es obligatorio junto con `encryption_key_name`. Un cuerpo solo con `encryption_alg_name` solicita cifrado por dispositivo. Un cuerpo vacío o no válido compila sin cifrado. Consulta [Firma y cifrado](/docs/platform/iot-fleets/updates/signing-and-encryption) |

Los artefactos llegan a una compilación solo mediante `selected_artifact_ids`; sin ellos normalmente no hay nada preparado y la compilación falla. Una compilación sustituye los enlaces de artefactos heredados del pack por los seleccionados.

### Respuestas

- Las rutas de creación responden `201` con el objeto: un pack, un módulo o, en un lanzamiento, el ID del lanzamiento y el resultado de las precondiciones. `modules` es una entrada de la creación del pack y no se devuelve en las lecturas.
- `DELETE` de un pack responde `200` con `{"message": "..."}`. `POST .../new`, `.../swu` y `.../package` responden `200` con `{"message": "..."}`.
- Las subidas de artefactos responden `{"msg": "...", "artifact": {...}}`: `201` para `POST /artifacts`, `200` para las subidas de ámbito pack y de ámbito módulo.
- Las subidas de descriptor sobre un pack o sobre un módulo de un pack responden `{"msg": "..."}`.
- Los listados de módulos responden `{"modules": [...]}`. El listado `.../artifacts` de un pack responde un array simple.
- Una compilación fallida deja el pack en estado `build_failed`, con el motivo en `last_build_error`. Sigue siendo editable y se puede volver a compilar.

## Objetos

Las definiciones de los campos están en `pkg/models/updates.go` del [repositorio](https://github.com/lamassuiot/ota). Estos son los campos que más leen los clientes.

### Pack

| Campo | Significado |
|---|---|
| `id`, `name`, `version`, `group_id` | Identidad. La versión es semver |
| `type` | `rawfile` o `firmware` |
| `packaging` | `swu` o `non-swu` |
| `status` | `draft`, `built` o `build_failed` |
| `uri` | URI de descarga del entregable compilado. Vacía hasta que se compila |
| `sw-descriptor` | El texto del sw-description (la clave lleva guion) |
| `encryption_mode` | Vacío, `shared` o `per-device` |
| `encryption_key_name`, `encryption_alg_name`, `encryption_iv`, `sw_desc_encrypted` | Ajustes de cifrado de la última compilación |
| `signature_key_id`, `signature_alg_name`, `signature_certificate` | Ajustes de firma de la última compilación |
| `built_device_count`, `total_device_count`, `uncovered_devices` | Solo en compilaciones por dispositivo: cobertura, y los dispositivos sin paquete con su `reason` |
| `allow_previous_version_download` | Si se pueden descargar versiones anteriores |
| `preconditions` | Las precondiciones de lanzamiento del pack |
| `last_build_error` | Por qué falló la última compilación |
| `locked` | Modo hawkBit: el backend congeló la composición porque el pack se envió a dispositivos |
| `created_at`, `updated_at` | Marcas de tiempo |

### Lanzamiento

Un lanzamiento lleva `id`, `group_id`, `name`, `description`, `version`, `exec_date`, `scheduled_at`, `status`, los campos de la estrategia (`workflow_type`, `rollout_type`, `rollout_value`, `test_device_id`, `auto`, `approval_threshold`, `error_threshold`, `weight`), `distribution_set_id`, `distribution_set_name`, los contadores `pending_count`, `active_count`, `completed_count`, `failed_count`, `total_devices`, `completed_in_batch`, `test_device_status`, `aborted`, `forced_preconditions` y `precondition_failures`.

`status` es `running` (vacío en un lanzamiento native que aún no ha cambiado de estado, lo que también significa en ejecución), `paused`, `cancelled` o `completed`. `test_device_status` es `pending`, `active`, `completed`, `failed` o `cancelled`.

### Módulo de software

| Campo | Significado |
|---|---|
| `id`, `key` | ID del catálogo y clave `type:name` |
| `type`, `name`, `version` | `type` es `os` o `application` |
| `delivery_intent` | `undecided`, `swu-build`, `swu-prebuilt` o `raw` |
| `built`, `locked` | Si existe su entregable, y si está congelado porque una versión suya ya se ha entregado |
| `artifacts` | Los archivos del módulo |
| `encrypted`, `encryption_mode`, `encryption_key_name`, `encryption_alg_name`, `sw_desc_encrypted`, `signature_key_id`, `signature_alg_name` | Cómo se compiló |
| `release_notes` | El registro de cambios del operador |
| `uri`, `created_at`, `updated_at` | URI de descarga, marcas de tiempo |

### Artefacto

`id`, `name`, `version`, `filename`, `checksum` (SHA-256 del archivo), `size` en bytes y `uploaded_at`. El listado de toda la flota añade `distribution_sets`: los packs que lo referencian, cada uno con `distribution_set_id`, `distribution_set_name`, `distribution_set_version` y `group_id`. Un archivo cuyo nombre termina en `.swu` o `.tar.gz` debe serlo realmente, o la subida responde `400`.

## Módulos dentro de un pack

| Método | Ruta (tras `/groups/:groupID/distribution-sets/:name`) | Descripción |
|---|---|---|
| `GET` | `/modules` | Lista los módulos del pack |
| `POST` | `/modules` | Añade un módulo (cuerpo: `type`, `name`, y opcionalmente `version`, `delivery_intent`). Responde `201`. Modo hawkBit: `400`, crea el módulo en el catálogo |
| `GET` | `/modules/reusable` | Módulos de otros packs, ofrecidos para importar. Cada uno informa `shared` y su pack de origen |
| `POST` | `/modules/import` | Compone a partir de un módulo existente. Responde `201` |
| `PUT` | `/modules/:moduleKey` | Sustituye el módulo por otra versión de sí mismo (cuerpo `{"source_module_id":"<id del catálogo>"}`). Native: `501` |
| `DELETE` | `/modules/:moduleKey` | Quita un módulo del pack |
| `PUT` | `/modules/:moduleKey/release-notes` | Establece el registro de cambios del operador (cuerpo `{"notes":"..."}`; vacío lo borra). Permitido en versiones compiladas |
| `POST` | `/modules/:moduleKey/artifact/upload` | Sube un binario a un módulo (campos `file`, `artifact_name`, `version`). Modo hawkBit: se rechaza, un módulo enlazado está congelado |
| `POST` | `/modules/:moduleKey/artifact/link` | Enlaza un artefacto global al módulo (cuerpo `{"artifact_id":"..."}`). Modo hawkBit: se rechaza |
| `POST` | `/modules/:moduleKey/descriptor/upload` | El sw-description propio de un módulo. Native: `501`. Modo hawkBit: `400`, usa `POST /softwaremodules/by-id/:moduleID/descriptor` |
| `POST` | `/modules/:moduleKey/build` | Compilación de un módulo desde el pack. Siempre se rechaza: `501` en modo native y `400` en modo hawkBit. Usa `POST /softwaremodules/by-id/:moduleID/build` |
| `GET` | `/modules/:moduleKey/artifact/download` | Descarga el entregable de un módulo. Native: `501` |

Cuerpo de importación: `source_module_id`, o `source_distribution_set_name` y `module_key` (con `source_group_id` y `source_distribution_set_version` opcionales). La intención de entrega de un módulo debe estar decidida y ser compatible con el empaquetado del pack antes de poder importarlo.

## Catálogo de módulos de software

Módulos que existen con independencia de cualquier pack. Crea uno con `POST /softwaremodules`, indicando `type`, `name`, `version` y, opcionalmente, `delivery_intent` (por defecto `undecided`). Usa el `id` devuelto en las rutas `by-id`.

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/softwaremodules` | Catálogo de toda la flota, con el pack de origen |
| `POST` | `/softwaremodules` | Declara un módulo sin pack todavía. Responde `201`. `type`, `name` y `version` son obligatorios |
| `DELETE` | `/softwaremodules/:moduleKey/versions/:version` | Elimina un módulo que ningún pack retiene. `400` si algún pack todavía lo retiene |
| `GET` | `/softwaremodules/by-id/:moduleID` | Lee un módulo |
| `PUT` | `/softwaremodules/by-id/:moduleID` | Actualiza `delivery_intent` y `release_notes`. Envía al menos uno |
| `POST` | `/softwaremodules/by-id/:moduleID/artifacts` | Sube un archivo (campo `file`). Responde `201` con el artefacto |
| `GET` | `/softwaremodules/by-id/:moduleID/artifacts/:artifactID/download` | Descarga un archivo almacenado |
| `DELETE` | `/softwaremodules/by-id/:moduleID/artifacts/:artifactID` | Quita un archivo. Responde `204` |
| `POST` | `/softwaremodules/by-id/:moduleID/descriptor` | Sube el sw-description que lee la compilación (campo `file`). Responde con el módulo |
| `POST` | `/softwaremodules/by-id/:moduleID/build` | Compila el entregable de este módulo. Solo modo hawkBit (`501` en native). El comportamiento depende de `delivery_intent`. El cuerpo es opcional y admite `user`, `encryption_key_name`, `encryption_alg_name`, `sw_desc_encrypted`, `signature_key_id`, `signature_alg_name`, `signature_certificate` |

Se aceptan archivos mientras la entrega es `undecided`. Un módulo `swu-build` admite entradas de compilación y rechaza un `.swu`; un módulo `swu-prebuilt` admite exactamente un `.swu`. Elige una intención de entrega compatible antes de importar el módulo con `source_module_id`. Una vez que un módulo se ha entregado (lo retiene una versión de pack publicada, o hawkBit lo bloqueó) queda bloqueado: su contenido está protegido, mientras que las notas de versión siguen siendo editables. En modo native el pack compila un único `.swu` a partir de las entradas de todos sus módulos, y un SWU precompilado se sube al pack completo en lugar de importarse como entrada de un módulo.

### Cuerpos de las peticiones

| Ruta | Cuerpo |
|---|---|
| `POST .../modules`, `POST /softwaremodules` | `type` (`os` o `application`), `name` (sin `/` ni `:`), `version`, `delivery_intent` |
| `POST .../modules/import` | `source_module_id`, o `source_distribution_set_name` y `module_key` |
| `PUT /softwaremodules/by-id/:moduleID` | `delivery_intent` y/o `release_notes` |
| Subidas | `multipart/form-data` con el archivo en `file`. Las subidas de artefactos de ámbito pack (`.../artifact/upload`, `.../modules/:moduleKey/artifact/upload`) admiten además `artifact_name` y `version`. `POST /artifacts` admite `name` y `version`. `POST /softwaremodules/by-id/:moduleID/artifacts` solo admite el archivo |

## Artefactos globales

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/artifacts` | Sube un artefacto independiente (campos `file`, `name`, `version`). Modo hawkBit: solo queda preparado (se descarta a los 30 minutos, en la siguiente subida) y no se puede asociar a un módulo, así que usa `POST /softwaremodules/by-id/:moduleID/artifacts` |
| `GET` | `/artifacts` | Catálogo de toda la flota, con las referencias de los packs |
| `GET` | `/artifacts/:id` | Un artefacto |
| `GET` | `/artifacts/:id/download` | Descarga el binario |
| `DELETE` | `/artifacts/:id` | Elimina. Responde `204` |

`name` y `version` son opcionales al subir. `name` toma por defecto el nombre del archivo sin su extensión. Una `version`, si se indica, debe ser `x.y.z` y mayor que cualquier versión existente de ese nombre, o la subida responde `400`.

## Campañas de lanzamiento

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/groups/:groupID/launch` | Crea un lanzamiento. Con `?dry_run=true`, solo evalúa |
| `GET` | `/groups/:groupID/launch` | Historial de lanzamientos |
| `POST` | `/groups/:groupID/launch/:id/rollout` | Despacha el siguiente lote |
| `POST` | `/groups/:groupID/launch/:id/pause` | Pausa. El lote en curso termina |
| `POST` | `/groups/:groupID/launch/:id/resume` | Reanuda un lanzamiento en pausa |
| `POST` | `/groups/:groupID/launch/:id/retry-failed` | Vuelve a encolar los dispositivos fallidos y los despliega. `400` si no hay ninguno fallido |
| `POST` | `/groups/:groupID/launch/:id/cancel` | Cancela de forma permanente |
| `POST` | `/groups/:groupID/launch/:id/complete` | Marca como completado. Modo hawkBit: `501` |
| `GET` | `/groups/:groupID/launch/:id/strategy` | Lee la estrategia |
| `POST` / `PUT` | `/groups/:groupID/launch/:id/strategy` | Actualiza la estrategia. Modo hawkBit: `501`. El pack lanzado no se puede cambiar |

Un lanzamiento de otro grupo responde `404`, como si no existiera.

Cuerpo de creación:

| Campo | Obligatorio | Significado |
|---|---|---|
| `distribution_set_name` | Sí | El pack que se lanza. Debe estar compilado |
| `workflow_type` | Sí | `direct` o `phased`. Se aceptan los nombres completos de WFX (`wfx.workflow.dau.direct`). Modo hawkBit: `phased` crea una acción soft, cualquier otro valor una forzada |
| `rollout_type` | Sí | `fixed` (un número de dispositivos) o `percentage` |
| `rollout_value` | Sí | Mayor que 0 |
| `test_device_id` | No | El canario: va solo primero y debe tener éxito antes que el resto |
| `auto` | No | Libera el siguiente lote automáticamente. Por defecto `false` |
| `approval_threshold` | No | Porcentaje de un lote que debe tener éxito antes del siguiente, de 0 a 100. 0 significa todo el lote |
| `error_threshold` | No | Porcentaje de todos los dispositivos que pueden fallar antes de cancelar el lanzamiento, de 0 a 100. 0 significa sin límite |
| `force_preconditions` | No | Despliega a todos los dispositivos aunque fallen las precondiciones. Los fallos se registran igualmente |
| `scheduled_at` | No | Hora de inicio en RFC 3339. Native: el servicio inicia el lanzamiento unos 30 segundos después, como mucho. Modo hawkBit: lo inicia el planificador de hawkBit |
| `name`, `description` | No | Nombre visible (por defecto, el nombre del pack) y notas del operador |
| `weight` | No | Una pista de prioridad almacenada, de 0 a 1000. Nada la aplica |

El cuerpo de actualización de la estrategia admite `workflow_type`, `rollout_type`, `rollout_value` (mayor que 0), `test_device_id`, `auto`, `approval_threshold` y `error_threshold`. Sustituye todos ellos: un campo omitido vuelve a su valor cero, así que envía la estrategia completa.

Una creación responde `201` con `launch_id`, `precondition_failures`, `forced`, `superseded_devices` y `never_seen_devices`. Una simulación (dry run) responde `200` con `qualifying_devices`, `precondition_failures`, `superseded_devices` y `never_seen_devices`. Los dos últimos solo se rellenan en modo hawkBit: dispositivos con una actualización en curso, que la creación del lanzamiento cancela, y dispositivos que nunca han contactado con hawkBit.

Un lanzamiento se rechaza con `400` cuando el pack no está compilado, o cuando un pack con cifrado por dispositivo tiene dispositivos sin paquete (simulaciones incluidas, y `force_preconditions` no lo anula).

## Conformidad de versiones y últimas versiones

Declara la versión en la que deben estar los dispositivos, y luego informa y corrige la deriva.

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/groups/:groupID/latest-distribution-sets` | Las últimas versiones declaradas de un grupo |
| `PUT` | `/groups/:groupID/latest-distribution-sets/:distributionSetID` | Declara la última versión de un pack (cuerpo `{"version":"1.2.0"}`) |
| `DELETE` | `/groups/:groupID/latest-distribution-sets/:distributionSetID` | Quita la declaración. Responde `204` |
| `GET` | `/devices/:deviceID/latest-drift` | La deriva de un dispositivo respecto a las últimas versiones de su grupo. `?groupID=` opcional |
| `POST` | `/devices/:deviceID/sync-to-latest` | Fuerza al dispositivo a coincidir. Responde `202` con la deriva |
| `POST` | `/devices/:deviceID/force-version` | Lanza un solo dispositivo a una versión. Responde `202` |
| `GET` | `/groups/:groupID/version-compliance` | Dispositivos que no están en la última versión, como `{"group_id", "devices": [...]}` |
| `GET` | `/groups/:groupID/version-status` | La matriz completa por dispositivo, conformes y desactualizados, como `{"group_id", "rows": [...]}` |

`sync-to-latest` admite un cuerpo opcional con `groupID` (también aceptado como `?groupID=`), `distribution_set_ids` para limitar los packs y `workflow`. Si algunos dispositivos no se pudieron despachar responde `207`, o `400` si no se despachó ninguno, con `{"err": "...", "drift": {...}}`.

`force-version` admite `distribution_set_id` y `version` (obligatorios), `group_id` y `workflow`. El dispositivo debe ser miembro del grupo del pack. En un pack `swu`, `workflow` toma por defecto `phased`, y en un pack `non-swu`, `download-install`. El modo native solo acepta la versión actual del pack salvo que el pack tenga `allow_previous_version_download`, y `sync-to-latest` tiene el mismo límite. El modo hawkBit ignora `workflow` en ambas rutas.

Una entrada de deriva tiene `distribution_set_id`, `distribution_set_name`, `current_version`, `latest_version`, `in_sync` y `missing`. Una fila de `version-status` tiene `device_id`, `distribution_set_id`, `distribution_set_name`, `current_version`, `latest_version`, `in_sync` y, cuando es más reciente que la declarada, `newest_version`.

## Descarga de artefactos por el dispositivo, modo hawkBit

En modo hawkBit el servicio también sirve la URL de artefactos de dispositivo de hawkBit, de modo que un gateway puede publicarla en el mismo host que el resto de la API:

| Método | Ruta | Descripción |
|---|---|---|
| `GET`, `HEAD` | `<prefix>/:tenant/controller/v1/:controllerId/softwaremodules/:softwareModuleId/artifacts/:filename` | El artefacto de un módulo, o su archivo auxiliar `.MD5SUM` como `text/plain` |

`<prefix>` es la ruta de `hawkbit.ddi_url`, por ejemplo `/api/hawkbit-ddi`. La ruta solo se registra en modo hawkBit. Responde únicamente para módulos del conjunto asignado o instalado del dispositivo, y `404` en otro caso, y `:tenant` debe ser el tenant configurado. Con la firma previa activada responde `302` como las demás descargas.

## SymKMS

Se sirve en `/symkms/v1` desde el mismo proceso cuando SymKMS está configurado. Almacena claves simétricas y las asocia a dispositivos. Los cuerpos y formatos de cifrado, descifrado y MAC están en [Firma y cifrado](/docs/platform/iot-fleets/updates/signing-and-encryption). Los errores usan el mismo cuerpo `{"err":"..."}`.

| Método | Ruta | Descripción |
|---|---|---|
| `POST` | `/symkms/v1/` | Almacena una clave. Cuerpo `user_id`, `algorithm`, `key` (hex o Base64), `id` opcional. Responde `201` con `id`, `user_id`, `algorithm`, `created_at` |
| `GET` | `/symkms/v1/?user_id=` | Lista las claves de un usuario. `user_id` es obligatorio. Paginado, filtrable por `user_id`, `algorithm`, `created_at` |
| `DELETE` | `/symkms/v1/:keyID?user_id=` | Elimina una clave. `user_id` es obligatorio y debe ser su propietario |
| `GET` | `/symkms/v1/:keyID/raw?user_id=` | Material de clave en bruto (`key_id`, `key_hex`, `algorithm`). Privilegiada |
| `POST` | `/symkms/v1/encrypt`, `/decrypt` | Cifra o descifra con una clave almacenada |
| `POST` | `/symkms/v1/mac`, `/mac/verify` | Calcula o verifica un MAC (cuerpo JSON) |
| `POST` | `/symkms/v1/mac/file`, `/mac/verify/file` | Lo mismo, con los datos como `file` subido |
| `POST` | `/symkms/v1/inventory/:deviceID/keys/:keyID` | Asigna una clave a un dispositivo. Cuerpo opcional `purpose`, `expires_at` (RFC 3339). Responde `201` con la asociación |
| `DELETE` | `/symkms/v1/inventory/:deviceID/keys/:keyID` | Revoca una clave de un dispositivo |
| `GET` | `/symkms/v1/inventory/:deviceID` | Las asociaciones de claves de un dispositivo. Paginado, filtrable por `purpose`, `status`, `assigned_at` |
| `GET` | `/symkms/v1/inventory/by-key/:keyID` | Los dispositivos a los que está asignada una clave, como `key_id` y `device_ids` |
| `GET` | `/symkms/v1/inventory/:deviceID/key?purpose=` | La clave en bruto del dispositivo para un propósito, por defecto `firmware-encryption`. Privilegiada. `404` si no hay asociación |

Un `purpose` vacío es un comodín que coincide con cualquier consulta, y un propósito concreto se compara de forma exacta. Las rutas que devuelven material de clave en bruto confían en que el gateway autentique a quien llama: no las expongas sin mTLS o tokens con ámbito. Consulta [Seguridad](/docs/platform/iot-fleets/updates/security).
