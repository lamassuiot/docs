A CRL is an issuer-signed list of revoked certificates. This guide is for an operator publishing lists and an integrator using them locally. You need the issuing CA certificate, its SKI and access to the published endpoint. The client must maintain a current copy: offline operation still requires refreshing evidence.

## VA role and per-CA configuration

The VA role stores configuration and metadata for the latest list published for a CA’s SKI. Generation requires a usable issuer key; do not assume an imported CA without a key has an available CRL.

| `crl_options` field | Purpose | Backend initial value |
|---|---|---|
| `validity` | Time from `thisUpdate` to `nextUpdate`. | 7 days. |
| `refresh_interval` | Time since publication that triggers scheduled renewal. | 6 days and 23 hours. |
| `regenerate_on_revoke` | Request regeneration on revocation or reactivation from `CertificateHold` events. | `true`. |
| `signer_certificate_serial_number` | Serial number of the existing certificate that signs the CRL. | Serial number of the CA’s current certificate. |

The signer must be an existing certificate with the `cRLSign` key usage and the same subject and public key as the CA. Certificates from before a reissue qualify. A delegated signer is not supported: a certificate with the CA’s subject but a different key is rejected.

When a CA is reissued, the role keeps pointing at the previous certificate. CRLs remain valid because both certificates share subject and key, but the previous certificate cannot be deleted while the role uses it. To retire it, update the role’s signer.

<Callout type="warn" title="Cases in which the role can no longer be edited">
  When a CA is deleted, its VA role is kept and cannot be removed through the API: it can be read but not updated (the API returns 404). Adjust validity, interval and signer before deleting it.

  A CA whose certificate lacks `cRLSign` cannot generate its CRL or edit its role (400 error). Since 4.0 the VA requires this usage. Check before importing with `openssl x509 -noout -ext keyUsage` and, if it is missing, obtain a certificate for the same CA and key that includes it.
</Callout>

`latest_crl` contains version, validity start and end. Versions are kept as PEM in object storage at `pki/va/crl/{subject_key_id}/{version}.crl`; the public endpoint returns DER.

## CAs that share a key

The VA identifies each CRL by the CA’s SKI, and the SKI is derived from its key. Two CAs with the same key have the same SKI and share a single VA role and a single CRL. This happens when a CA is created on an existing KMS key, or when a CA is imported whose certificate declares an SKI already in use. Lamassu takes the SKI of an imported certificate as-is and does not check that it corresponds to its public key. The first CA creates the role and the others keep it.

The certificates of all of them point to `/crl/{ski}`, but the published list has the first CA as issuer and only includes its revocations. A verifier compares the CRL issuer with the issuer of the certificate it validates (RFC 5280, §6.3.3) and rejects the list if they differ. Depending on its policy, the certificate is blocked (*hard-fail*) or accepted even though it is revoked (*soft-fail*). Revocations of the secondary CAs do not appear in any list.

If the first CA is deleted, CRL generation for the remaining one fails because the configured signer no longer matches a CA with that name. Until the role’s signer is updated to a certificate of the remaining CA, the last published list keeps being served until it expires (7 days by default).

To detect the problem, compare the SKI of the CAs in the inventory: two with the same SKI are affected. To fix it, create a CA with its own key and reissue its certificates; those already issued keep the old URL and are not corrected until reissued. Also restrict the permission to import CAs, because a CA imported with a colliding SKI can leave the legitimate one without a CRL.

## Periodic and automatic regeneration

The scheduled job requests another list when `refresh_interval` is reached or when the list approaches expiration within the configured watch period. This depends on working jobs, storage and signing; it does not guarantee renewal during a service failure.

With `regenerate_on_revoke`, the event handler requests a new CRL upon revocation or reactivation from `CertificateHold` to `ACTIVE`. This happens after the status change and has its own failure paths. Confirming revocation does not establish that the new CRL is already published or that all clients have downloaded it.

Compare CRL numbers and timestamps before and after a change. Monitor expired lists and generation failures; clients must apply policy when current evidence is unavailable.

## CRL contents

Each entry contains serial number, revocation time and reason. The generator queries certificates in `REVOKED` state for the selected CA. A reactivated certificate disappears when the list is recalculated; an earlier downloaded copy retains its contents.

The list contains a critical *Issuing Distribution Point* (OID `2.5.29.28`) with configured distribution URLs. Check that your client interprets this extension and that it matches the list’s scope. If rejected, investigate format and scope; ignoring a critical extension is not successful validation.

## Public download endpoint

The VA service exposes `GET /crl/{subject_key_id}` without management authorization. Use the **issuing CA’s** SKI, not the end-entity certificate’s SKI or serial. First inspect the certificate’s CDP:

```bash
openssl x509 -in device.crt -noout -text
```

Replace the following URL with the CDP URL and review exposure in [Deployment](/docs/deployment/self-hosted/networking):

```bash
CRL_URL='http://pki.example.com/crl/REPLACE_WITH_ISSUER_SKI'

curl --fail --show-error --silent --max-time 15 \
  "$CRL_URL" -o ca.crl.der

openssl crl -inform DER -in ca.crl.der \
  -outform PEM -out ca.crl.pem

openssl crl -in ca.crl.pem -noout \
  -issuer -lastupdate -nextupdate -crlnumber

openssl crl -in ca.crl.pem -noout -text
openssl crl -in ca.crl.pem -noout -verify -CAfile issuer.pem
```

You need OpenSSL 3.x and `issuer.pem` containing the direct issuer’s certificate. Require a valid signature, current timestamps and the expected issuer. For a root that issues directly:

```bash
openssl verify -CAfile roots.pem -CRLfile ca.crl.pem \
  -crl_check -purpose sslclient device.crt
```

`roots.pem` contains deliberately trusted roots. For intermediates, add `-untrusted intermediates.pem` before the `device.crt` argument. `-crl_check` checks the end-entity certificate’s revocation against the local list; it does not download other lists or establish the status of the whole chain. A complete chain check needs the corresponding CRLs and a policy requiring them.

The test should accept an allowed certificate absent from the list and reject it with `certificate revoked` after publishing and using the list containing its serial.

## VA role management API

The following paths are relative to the VA service; confirm the public prefix in the Gateway. They are not the URLs of the public OCSP and CRL endpoints.

| Method | Relative path | Operation |
|---|---|---|
| `GET` | `/v1/roles/{ca-ski}` | Read `crl_options` and `latest_crl`. |
| `PUT` | `/v1/roles/{ca-ski}` | Replace CRL configuration. |

You need authentication and role read or update permissions. Consult your installation’s [API reference](/docs/api-reference) and [Access control](/docs/platform/administration/access-control). Read current configuration before updating and send the full object expected by the contract: the backend replaces `crl_options`; it does not merge omitted fields.

After a change, check saved configuration and the next list actually published. Updating the role alone does not establish regeneration or client acceptance.

## From the interface

The CA view lets you inspect and download the available list. Compare version, issuer and timestamps with the copy downloaded from the public endpoint. Diagnose differences using [PKI troubleshooting](/docs/platform/pki/troubleshooting).
