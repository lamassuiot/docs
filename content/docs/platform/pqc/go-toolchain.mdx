Go 1.27 includes ML-DSA in `crypto/mldsa` and in X.509 and TLS, but it has no composite or SLH-DSA certificates, no related certificates and no composite TLS signature schemes. Lamassu therefore builds its backend and its TLS proxy with a fork of Go, maintained on the `release-branch.go1.27` branch. This page describes what the fork adds, for developers who build Lamassu or write a client that must talk to it.

<Callout type="warn" title="Not standard Go">
The fork exposes APIs that do not exist in the official Go distribution. Code that uses them compiles only with this toolchain, and a binary built with it must not be assumed to follow the Go compatibility promise for those APIs.
</Callout>

## What the fork adds

**Composite ML-DSA in X.509.** The `x509` package gains `CompositePublicKey` and `CompositePrivateKey`, which implement `crypto.Signer`, and 15 `CompositeAlgorithm` values (for example `x509.MLDSA65_ECDSA_P384_SHA512`) that can generate keys, sign and verify. Certificates, certificate requests and revocation lists signed with these keys parse, marshal and verify like any other. PKCS#8 encoding of composite private keys is supported. The [algorithms page](/docs/platform/pqc/algorithms) lists the identifiers.

**SLH-DSA in X.509.** The `x509.SLHDSA` public key algorithm and twelve `PureSLHDSA...` signature algorithms are available for parsing and verifying certificates and keys. The implementation is the vendored `circl` library of Cloudflare. It is the least tested part of the fork: it has no x509 tests of its own and no TLS support.

**Related certificates (RFC 9763).** The fork provides `x509.CreateBoundCertificate`, which adds the `id-pe-relatedCert` extension (`1.3.6.1.5.5.7.1.36`) to a certificate, `x509.VerifyRelatedCertificate`, and the helpers to build and check the `relatedCertRequest` attribute of a certificate request (`1.2.840.113549.1.9.16.2.60`). `x509.CertificateRequest` gains an `ExtraAttributes` field for carrying it. [Related certificates](/docs/platform/pqc/related-certificates) explains how Lamassu uses them.

**Composite signature schemes in TLS.** The `tls` package adds 15 `SignatureScheme` constants, one per composite algorithm, advertised by default after the native ML-DSA schemes. They work only with TLS 1.3 and are tested with mutual authentication. See below for their code points.

## TLS code points

IANA has assigned no code points to the composite TLS signature schemes, so the fork uses the private-use range `0xFE00` to `0xFE0E`, in the order of the composite table: `0xFE00` is `MLDSA44-RSA2048-PSS-SHA256` and `0xFE0E` is `MLDSA65-Ed25519-SHA512`. A client or server built with a standard TLS library does not recognize them and will fall back to another scheme or fail the handshake. Interoperability is therefore limited to peers built from this fork, or to the native ML-DSA schemes (`0x0904` to `0x0906`) that standard Go 1.27 implements.

The three variants that use RSA PKCS#1 v1.5 (`MLDSA44-RSA2048-PKCS15-SHA256`, `MLDSA65-RSA3072-PKCS15-SHA512` and `MLDSA65-RSA4096-PKCS15-SHA512`) are announced only in the `signature_algorithms_cert` extension, so they can appear in a certificate chain but a leaf certificate with such a key cannot sign the handshake.

| Code point | Algorithm |
| --- | --- |
| `0xFE00` | MLDSA44-RSA2048-PSS-SHA256 |
| `0xFE01` | MLDSA44-RSA2048-PKCS15-SHA256 |
| `0xFE02` | MLDSA65-RSA3072-PSS-SHA512 |
| `0xFE03` | MLDSA65-RSA3072-PKCS15-SHA512 |
| `0xFE04` | MLDSA65-RSA4096-PSS-SHA512 |
| `0xFE05` | MLDSA65-RSA4096-PKCS15-SHA512 |
| `0xFE06` | MLDSA87-RSA3072-PSS-SHA512 |
| `0xFE07` | MLDSA87-RSA4096-PSS-SHA512 |
| `0xFE08` | MLDSA44-ECDSA-P256-SHA256 |
| `0xFE09` | MLDSA65-ECDSA-P256-SHA512 |
| `0xFE0A` | MLDSA65-ECDSA-P384-SHA512 |
| `0xFE0B` | MLDSA87-ECDSA-P384-SHA512 |
| `0xFE0C` | MLDSA87-ECDSA-P521-SHA512 |
| `0xFE0D` | MLDSA44-Ed25519-SHA512 |
| `0xFE0E` | MLDSA65-Ed25519-SHA512 |

The key exchange is unchanged from upstream Go. Hybrid groups such as `X25519MLKEM768`, `SecP256r1MLKEM768`, `SecP384r1MLKEM1024` and the pure `MLKEM1024` are those of the Go 1.27 standard library.

| Group | Composition |
| --- | --- |
| `X25519MLKEM768` | X25519 + ML-KEM-768 |
| `SecP256r1MLKEM768` | P-256 + ML-KEM-768 |
| `SecP384r1MLKEM1024` | P-384 + ML-KEM-1024 |
| `MLKEM1024` | ML-KEM-1024 alone |

The connection stays protected while at least one component of a hybrid group is secure. The key exchange is independent of the certificate type, so a connection can use a classical certificate and still have a post-quantum key exchange.

## A minimal example

The following program creates a self-signed composite certificate and uses it as the server certificate of a TLS 1.3 configuration. Error handling is omitted.

```go
alg := x509.MLDSA65_ECDSA_P384_SHA512
pub, priv, _ := alg.GenerateCompositeKey(rand.Reader)

tmpl := &x509.Certificate{
    SerialNumber:          big.NewInt(1),
    Subject:               pkix.Name{CommonName: "example.com"},
    NotBefore:             time.Now().Add(-time.Hour),
    NotAfter:              time.Now().Add(24 * time.Hour),
    KeyUsage:              x509.KeyUsageDigitalSignature,
    BasicConstraintsValid: true,
    DNSNames:              []string{"example.com"},
}
der, _ := x509.CreateCertificate(rand.Reader, tmpl, tmpl, pub, priv)
keyDER, _ := x509.MarshalPKCS8PrivateKey(priv)

cert, _ := tls.X509KeyPair(
    pem.EncodeToMemory(&pem.Block{Type: "CERTIFICATE", Bytes: der}),
    pem.EncodeToMemory(&pem.Block{Type: "PRIVATE KEY", Bytes: keyDER}),
)
cfg := &tls.Config{
    Certificates: []tls.Certificate{cert},
    MinVersion:   tls.VersionTLS13,
}
```

A composite key can also sign a message directly, with an optional context of at most 255 bytes:

```go
sig, _ := priv.Sign(rand.Reader, msg, x509.CompositeSignerOpts{Context: ctx})
ok := alg.CompositeVerify(pub, msg, ctx, sig)
```

## Discarded approaches

The first iterations of the fork implemented Chameleon certificates, defined in `draft-bonnell-lamps-chameleon-certs`. The idea is to pair two certificates for the same subject, for example a classical one and a post-quantum one, by issuing the first with an extension that encodes only the differences to the second. A relying party that understands the extension can rebuild the paired certificate from it and validate that one, so a single issued certificate carries both identities without changing the path validation rules of RFC 5280.

The work was dropped because the draft expired without becoming a standard and is no longer being pursued, so there was no stable specification to interoperate with. Nothing in the current implementation depends on it.

## Building the toolchain and the images

The fork is built in CI by a workflow that runs the Go test suite and then publishes a multi-architecture image, `ghcr.io/lamassuiot/golang-pqc`, tagged `go1.27` and, for the `release-branch.go1.27` branch, `latest`. The image contains the toolchain under `/usr/local/go-pqc` with `GOROOT` pointing at it.

To build the toolchain from source instead, use the `release-branch.go1.27` branch and the standard Go source build:

```bash
git clone --branch release-branch.go1.27 https://github.com/lamassuiot/go.git
cd go/src
./make.bash
```

The resulting `bin/go` command is used like any other Go toolchain.

Lamassu consumes the toolchain in two ways. The backend images (CA, KMS, VA, alerts, device manager, DMS manager and the monolithic build) use `ghcr.io/lamassuiot/golang-pqc:latest` as their builder image. The backend CI workflow installs the same toolchain through a custom setup action in place of `actions/setup-go`, and the backend requires `go 1.27.3` in its module file. Traefik is not built from the image: its `build.sh` script expects a compiled checkout of the fork in a sibling directory and produces the binary outside a container. See [TLS front proxy with Traefik](/docs/platform/pqc/tls-front-proxy).
