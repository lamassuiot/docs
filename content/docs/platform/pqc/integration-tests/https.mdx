---
title: HTTPS integration tests
description: Results of testing a Lamassu HTTPS endpoint with OpenSSL and curl using post-quantum key exchange and post-quantum and composite certificates.
---

This test connects to a Lamassu API endpoint over HTTPS from an OpenSSL client and checks that the post-quantum handshake, the certificate chain and the application request all succeed. The [overview](/docs/platform/pqc/integration-tests/overview) explains the clients, the test matrix and what each check proves.

## Scenario

The client requests `GET /api/ca/health` through the Traefik front proxy, which forwards it to Envoy Gateway and the CA service. The server certificate and the CA that signed it were created outside Lamassu and loaded into the front proxy for each case. For each case the proxy was configured with the key exchange groups and the certificate of that row and column of the matrix.

<Callout type="info" title="Test PKI">
The CAs and certificates are test material made outside Lamassu, valid for a short period and with the server name as their subject alternative name. They are not issued by the Lamassu CA service.
</Callout>

## Results

All nine combinations of key exchange and certificate passed, and so did the three additional composite certificates.

| Key exchange ↓ / Certificate → | **T**: ECDSA P-256 | **PQ**: ML-DSA-65 | **PQ/T**: `MLDSA65-RSA3072-PSS-SHA512` |
| --- | --- | --- | --- |
| **T** | ✅ `X25519`, `ecdsa_secp256r1_sha256` | ✅ `X25519`, `mldsa65` | ✅ `X25519`, `mldsa65_rsa3072_pss` |
| **PQ** | ✅ `MLKEM1024`, `ecdsa_secp256r1_sha256` | ✅ `MLKEM1024`, `mldsa65` | ✅ `MLKEM1024`, `mldsa65_rsa3072_pss` |
| **PQ/T** | ✅ `X25519MLKEM768`, `ecdsa_secp256r1_sha256` | ✅ `X25519MLKEM768`, `mldsa65` | ✅ `X25519MLKEM768`, `mldsa65_rsa3072_pss` |

Each cell shows the negotiated group and the signature scheme of the handshake. In every case the chain verified, the request returned `200` and both negative checks were rejected with `handshake_failure`.

| Additional composite | Signature scheme | Result |
| --- | --- | --- |
| `MLDSA44-ECDSA-P256-SHA256` | `mldsa44_ecdsa_p256` | ✅ with `X25519MLKEM768` |
| `MLDSA65-ECDSA-P256-SHA512` | `mldsa65_ecdsa_p256` | ✅ with `X25519MLKEM768` |
| `MLDSA65-Ed25519-SHA512` | `mldsa65_ed25519` | ✅ with `X25519MLKEM768` |

With a single server configuration that holds the ECDSA, ML-DSA-65 and composite certificates at once and accepts all three key exchange classes, a client that offered one group and one signature scheme negotiated each of the nine combinations. `curl` returned `200` when it trusted the three CAs.

<Callout type="warn" title="Trust every class of CA you expect to be served">
A server with certificates of several classes serves the first that matches the client's signature preference. A default OpenSSL 3.5 or later client prefers ML-DSA, so a client that trusts only the ECDSA CA fails with `unable to get local issuer certificate`, even though the connection itself worked. Give clients the CAs of every class the server may present.
</Callout>

## Reproduce a case

You need OpenSSL 3.5 or later. For composite certificates, also the `hybrid-provider` module with code points that match the Go PQC toolchain, loaded through `OPENSSL_CONF`. Use the CA file of the case as `ca.pem`.

<Steps>
  <Step>
    ### Connect offering one group and one signature scheme

    This example tests PQ/T key exchange with the composite certificate, and prints the negotiated values:

    ```bash
    openssl s_client -connect <LAMASSU_HOST>:443 -servername <LAMASSU_HOST> \
      -tls1_3 -groups X25519MLKEM768 -sigalgs mldsa65_rsa3072_pss \
      -CAfile ca.pem -verify_hostname <LAMASSU_HOST> -verify_return_error \
      < /dev/null 2>&1 | grep -E 'Negotiated TLS1.3 group|Peer signature type|Verify return code'
    ```

    Expected output:

    ```text
    Peer signature type: mldsa65_rsa3072_pss
    Negotiated TLS1.3 group: X25519MLKEM768
    Verify return code: 0 (ok)
    ```
  </Step>

  <Step>
    ### Send a request

    Replace the `grep` with an HTTP request to confirm that the application layer works through the proxy:

    ```bash
    printf 'GET /api/ca/health HTTP/1.1\r\nHost: <LAMASSU_HOST>\r\nConnection: close\r\n\r\n' | \
      openssl s_client -connect <LAMASSU_HOST>:443 -servername <LAMASSU_HOST> \
      -tls1_3 -groups X25519MLKEM768 -sigalgs mldsa65_rsa3072_pss \
      -CAfile ca.pem -verify_hostname <LAMASSU_HOST> -verify_return_error -quiet
    ```

    The response starts with `HTTP/1.1 200 OK`. With `curl` and a bundle that contains the CAs of the classes the server presents, `curl --cacert ca-bundle.pem https://<LAMASSU_HOST>/api/ca/health` returns `200` as well.
  </Step>

  <Step>
    ### Check that a wrong offer is rejected

    Offer only classical groups to a server configured for PQ key exchange:

    ```bash
    openssl s_client -connect <LAMASSU_HOST>:443 -servername <LAMASSU_HOST> \
      -tls1_3 -groups X25519 -CAfile ca.pem < /dev/null
    ```

    The handshake fails with a `handshake failure` alert. Offering every signature scheme except the certificate's gives the same result.
  </Step>
</Steps>
