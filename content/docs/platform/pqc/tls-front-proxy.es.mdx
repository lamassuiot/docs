---
title: Proxy TLS con Traefik
description: El fork de Traefik que termina el TLS de los dispositivos con certificados clásicos y poscuánticos para el mismo host, cómo elige certificado y cómo se compila.
---

Los dispositivos se conectan a Lamassu por TLS, y el enrolamiento EST se apoya en TLS mutuo. Para aceptar un certificado poscuántico o composite en esa conexión, el endpoint TLS debe compilarse con el [toolchain de Go PQC](/docs/platform/pqc/go-toolchain). Lamassu lo hace con un fork de Traefik, basado en Traefik 3.7.15, situado delante de Envoy Gateway. El fork añade dos comportamientos: puede servir varios certificados para el mismo host y elegir entre ellos según el cliente, y permite que un listener de Gateway API haga referencia a una opción TLS de Traefik.

## Varios certificados para el mismo host

Traefik original conserva un certificado por conjunto de nombres. Si existen un certificado ECDSA clásico y un certificado ML-DSA para `lab.example.com`, solo se conserva el primero. El fork almacena cada certificado distinto (los duplicados se detectan comparando el certificado hoja) y elige uno en cada handshake.

La elección sigue los algoritmos de firma que anuncia el cliente:

1. Se normaliza el nombre de servidor del cliente y se reúnen los certificados cuyos nombres coinciden, con los nombres exactos por delante de los comodines. Un certificado con solo Common Name sigue coincidiendo.
2. Si ningún certificado coincide, la conexión se cierra en modo SNI estricto, o se sirve el certificado por defecto.
3. Si coincide exactamente un certificado, se sirve sin más comprobaciones.
4. En otro caso, el proxy toma los esquemas de firma del cliente en el orden en que los envió y, para cada esquema, devuelve el primer certificado cuya clave permiten el esquema, la versión de TLS y el tipo de clave. Así se contrasta la clave hoja con `signature_algorithms`, los esquemas que el cliente acepta para la firma del handshake; las firmas del resto de la cadena son una comprobación distinta, frente a `signature_algorithms_cert`.
5. Si el cliente no anuncia ningún esquema, se devuelve el primer certificado compatible. Si ninguno es compatible, se devuelve el primer candidato y el handshake falla con el error subyacente.

Prevalece el orden de preferencia del cliente: un cliente que lista ML-DSA primero recibe el certificado poscuántico y uno que lista ECDSA primero recibe el clásico, aunque también soporte ML-DSA. Un cliente sin soporte poscuántico nunca anuncia esos esquemas y recibe el certificado clásico. TLS 1.2 nunca selecciona certificados ML-DSA ni composite. El servidor no puede configurarse con un orden de preferencia propio.

## Opciones TLS en listeners de Gateway API

Traefik lee su configuración de Gateway API desde Kubernetes. El fork lee la opción de listener `traefik.io/tls-options`, cuyo valor nombra la opción TLS que se aplica a ese listener: `default`, o un nombre cualificado como `traefik-system-pqc@kubernetescrd`. Funciona en listeners HTTPS y en listeners TLS en modo `Terminate` que sirven un `TLSRoute`. Se ignora en modo passthrough.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: traefik-gw
spec:
  gatewayClassName: traefik
  listeners:
    - name: https
      protocol: HTTPS
      port: 8443
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: edge-cert
        options:
          traefik.io/tls-options: default
```

En una opción TLS se establecen los grupos de intercambio de claves soportados y el modo de autenticación de cliente. Cuando varios listeners comparten un router padre y nombran opciones distintas, el proxy registra una advertencia y usa valores por defecto aislados para cada uno. Sin el fork, Traefik ignora la anotación, aplica sus propios valores por defecto y los ajustes no se pueden controlar; los dispositivos que necesitan TLS mutuo fallan entonces.

El fork añade además `mlkem1024` a los nombres de grupo aceptados en `curvePreferences`, junto a los grupos híbridos que Traefik ya reconoce.

## TLS mutuo

La autenticación de cliente es el mecanismo estándar de Traefik, configurado en la opción TLS. Con `RequireAndVerifyClientCert` y un fichero de CA de cliente, el proxy valida la cadena, y la verificación de la firma del cliente la realiza la pila TLS del fork de Go, que se ha probado con certificados de cliente composite en un handshake TLS 1.3. Con `RequestClientCert`, que es lo que establece el chart de Lamassu en su opción por defecto, el proxy comprueba que el cliente posee la clave del certificado que presenta, pero no valida la cadena; la decisión se delega en el backend, que recibe el certificado en una cabecera (véase [Despliegue con el Helm chart](/docs/platform/pqc/deployment)). Ninguna prueba de Traefik cubre el TLS mutuo poscuántico, y una cadena de cliente firmada por una CA composite o poscuántica depende del código x509 del fork.

## Compilación del proxy

El fork no se compila desde la imagen de Go. El script `build.sh` exige una copia ya compilada del fork de Go, por defecto en `../go`, y comprueba que es el fork antes de forzar `GOROOT` y `GOTOOLCHAIN=local`. Compila el binario con `CGO_ENABLED=0`, genera la interfaz web salvo que se indique `SKIP_WEBUI=1` y empaqueta el binario en una imagen Alpine con `docker buildx`. La imagen por defecto es `ghcr.io/lamassuiot/traefik:pqc-3.7.15`.

| Variable | Finalidad |
| --- | --- |
| `GO_FORK_ROOT` | Ubicación del fork de Go compilado. |
| `PLATFORMS` | Plataformas de destino; por defecto `linux/amd64`. |
| `SKIP_WEBUI` | Omite la generación de la interfaz web con el valor `1`. |
| `IMAGE`, `PUSH` | Nombre de la imagen y si se publica. Las compilaciones multiplataforma requieren `PUSH=1`. |

Las etiquetas `pqc-*` son mutables y se han reconstruido sobre sí mismas, por lo que en entornos próximos a producción conviene fijar el digest.

<Callout type="info" title="Aún no validado con certificados composite">
Las pruebas de selección del fork usan ML-DSA-65 puro junto con ECDSA P-256. La selección de un certificado composite depende de que la pila TLS del fork conozca la clave composite, algo que ocurre, pero el proxy no tiene ninguna prueba para ello.
</Callout>
