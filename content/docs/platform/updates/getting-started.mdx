---
title: Get started with Lamassu Updates
description: Run Lamassu Updates and its dependencies locally with Docker Compose and check that the API answers.
---

This guide starts Lamassu Updates (the OTA Update Service) with Docker Compose, in its default native mode, and checks that the API answers. It takes about ten minutes plus the image build. When it works, continue with [Publish and roll out an update](/docs/platform/updates/guides/publish-and-roll-out).

## Before you begin

- Docker with the Compose plugin.
- A running Lamassu IoT instance that the containers can reach. The service reads device groups and their devices from its Device Manager (`dms_endpoint`), and signs with its KMS (`kms_endpoint`) only when you ask for signed builds.
- A checkout of the [`ota` repository](https://github.com/lamassuiot/ota) with the Lamassu `core` and `sdk` modules next to it. `go.mod` replaces `lamassuiot/core` and `lamassuiot/sdk` with local paths, and the Docker build copies them from the **parent directory** of the checkout (`context: ..` in `docker-compose.yml`), so that directory must contain both `ota/` and `lamassuiot/`.
- Access to the `ghcr.io/lamassuiot/wfx:otaq` image, which the `custom-wfx` service uses.
- Optional, for [hawkBit mode](/docs/platform/updates/hawkbit-mode): a hawkBit server. Compose builds one from `docker/hawkbit`: hawkBit 1.1.0 plus an S3 artifact plugin, tagged `lamassu/hawkbit-update-server:1.1.0-s3` locally. That image is built locally and not published.
- Optional, to run the service outside Docker: Go 1.26.2 or newer, and Python 3.8 or newer with the `swugenerator` requirements installed. The Docker image already contains the compiled binary and Python with `swugenerator`.

## Start the stack

<Steps>
  <Step>
    ### Clone the repository

    ```bash
    git clone https://github.com/lamassuiot/ota.git
    cd ota
    ```
  </Step>
  <Step>
    ### Set the host address

    The `updates` container reaches Lamassu through `host.docker.internal`, which `docker-compose.yml` overrides with `HOST_IP`. On WSL2 the default `host.docker.internal` points at the Docker Desktop gateway, not at the WSL host, so set your own address:

    ```bash
    cp .env.example .env
    HOST_IP=$(hostname -I | awk '{print $1}')
    sed -i "s/HOST_IP=/HOST_IP=${HOST_IP}/" .env
    ```

    Then check that `dms_endpoint` and `kms_endpoint` in `config-docker.yml` point at your Lamassu API (they default to `http://host.docker.internal:8080/api/...`).
  </Step>
  <Step>
    ### Create the network and start

    `docker-compose.yml` attaches to an existing network named `ota-net` and refuses to start without it.

    ```bash
    docker network create ota-net
    docker compose up --build
    ```
  </Step>
</Steps>

### Services

| Service | Host port | What it is |
|---|---|---|
| `updates` | `10090` | The Updates API, with SymKMS embedded |
| `custom-wfx` | `9080` (client), `9081` (management) | WFX, the job server that devices poll in native mode |
| `postgres` | `5000` (container `5432`) | Database. `init.sql` creates the `updates` and `hawkbit` databases on first start |
| `swupdate-device1` | `80` | A sample SWUpdate device client |
| `hawkbit` | `8090` | hawkBit server, only for [hawkBit mode](/docs/platform/updates/hawkbit-mode) |
| `rustfs` | `9000` (S3), `9001` (console) | Local S3 store, only with `--profile s3` |

`docker compose --profile s3 up -d` also starts `rustfs` and `s3-init`, which creates the encrypted bucket `ota-updates` that artifacts, builds and hawkBit's artifact storage can use. Without that profile, and with `config-docker.yml`, artifacts and builds stay on the `update_files` volume.

## Verify the API

```bash
curl -s localhost:10090/health
# {"status":"ok"}

curl -s localhost:10090/updates/v1/capabilities
```

The second call reports the active backend and what it supports. In native mode it looks like this (shortened):

```json
{
  "backend": "native",
  "supported": { "workflows": true, "campaigns": true, "software_module_deliverables": false },
  "unsupported": ["software_module_deliverables", "software_module_replace"]
}
```

`supported` has one entry for each of the 22 capabilities. See [Capabilities](/docs/platform/updates/reference/capabilities) for what each one means.

## Run without Docker

Start the monolithic entry point with a config file. It runs the Updates API and SymKMS together.

```bash
OTA_CONFIG_FILE=/path/to/config.yml go run ./cmd/monolithic
```

If `OTA_CONFIG_FILE` is not set, the service reads `/etc/lamassuiot/config.yml`.

To build `.swu` files outside Docker, install `swugenerator` into the Python environment that the config points at (the image does the same from `swugenerator/requirements.txt`):

```bash
python3 -m venv .venv
.venv/bin/pip install -r swugenerator/requirements.txt
.venv/bin/pip install -e swugenerator
```

The `config.yml` at the repository root is a starting point for local development, not a ready-made file:

- It needs Postgres (`localhost:5000`) and the WFX management API (`localhost:9081`), which `docker compose up -d postgres custom-wfx` provides.
- It contains values for one developer machine: absolute `/home/alvaro/...` paths for artifact and SymKMS storage, the signer script and `swugenerator`, and a LAN IP for the Lamassu endpoints. Edit them to paths the service user can create; the service stops at start-up if it cannot create its directories.
- It stores artifacts and build outputs in the local RustFS bucket (`docker compose --profile s3 up -d`). To use local disk instead, remove the `artifacts:` and `builds:` blocks; when they are absent, artifacts default to `{update_files_base_dir}/artifacts`.

### Try hawkBit mode

hawkBit mode serves the same API on top of a real hawkBit server. Start hawkBit and Postgres, wait until hawkBit answers, then start the service with the hawkBit config:

```bash
docker compose up -d postgres hawkbit

until curl -sf -u admin:admin 'http://localhost:8090/rest/v1/targets?limit=1' >/dev/null; do sleep 2; done

OTA_CONFIG_FILE=./config-hawkbit.yml go run ./cmd/monolithic
curl -s localhost:10090/updates/v1/capabilities   # "backend":"hawkbit"
```

`config-hawkbit.yml` also contains developer-machine paths, in the SWU build settings. A service pointed at a hawkBit with no registered devices builds and launches normally, but nothing downloads the update, because in hawkBit mode devices poll hawkBit directly. Read [hawkBit mode](/docs/platform/updates/hawkbit-mode) before using it.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `docker compose up` fails on the network | `ota-net` does not exist. Run `docker network create ota-net` |
| The `updates` container cannot reach Lamassu | `HOST_IP` is empty in `.env`, or `dms_endpoint` in `config-docker.yml` points at an address the container cannot reach |
| `docker compose up --build` fails while copying `lamassuiot/core` | The build context (the parent of `ota/`) does not contain `lamassuiot/` |
| The service exits at start-up when run on the host | A directory in the config (`update_files_base_dir`, `sym_keys_dir`) cannot be created, or Postgres or WFX is not reachable at the addresses in the file |
| `capabilities` answers but device groups fail with a Device Manager error | `dms_endpoint` is wrong. The Updates API reads every group's devices from it |
