The Lamassu dashboard is the web interface for the Updates API. This guide follows the same update as the curl guides ([native](/docs/platform/updates/guides/native-curl) and [hawkBit](/docs/platform/updates/guides/hawkbit-curl)) through the screens. Names in bold are the labels shown in the dashboard.

The dashboard is a separate project (`lamassu-dashboard`). This guide describes it from its source and has no screenshots, so a label can differ in a newer version. The dashboard has no translations: its labels are in English.

## Before you begin

- Lamassu Updates is running and the dashboard can reach it. See [Connect it to the service](#connect-it-to-the-service).
- A Lamassu IoT **device group** that contains the devices to update (**Device Groups** under **IoT**). A group's members are the devices that match its criteria.
- For an SWU build with signing or encryption: a signing key in **Asymmetric Keys** or a symmetric key in **Symmetric Keys** (both under **KMS**), and, for per-device encryption, keys assigned to the devices in **Device Key Inventory** (under **IoT**).

## Connect it to the service

The dashboard talks to the Updates API at the address in `LAMASSU_UPDATES_API`, in its `public/config.js`. In the container image it comes from the environment variable of the same name.

```js
LAMASSU_UPDATES_API: "http://localhost:10090"
```

- The dashboard appends `/updates/v1` and `/symkms/v1` to it. A trailing `/updates/v1` is accepted and stripped.
- If it is empty, the dashboard uses `LAMASSU_API`.
- When authentication is on, every call carries the user's bearer token. The service ignores it, so put a gateway that checks it in front. See [Security](/docs/platform/updates/security).
- It must point at the service instance that runs the backend you want to use. A service runs either native or hawkBit mode, never both: to use both at once you run two instances, each on its own port, and point the dashboard at one of them.

The dashboard reads `GET /updates/v1/capabilities` once, after you sign in, and hides what the backend cannot do. That is why the same screens look different in native and hawkBit mode. [What changes with the backend](#what-changes-with-the-backend) lists the differences. If the capabilities request fails, the dashboard assumes everything is supported and hides nothing.

To compare both backends, the user menu has an **Updates backend** switch with the options **Auto**, **native** and **hawkbit**. It appears only in development builds, or when the dashboard container runs with `DEV_OPTIONS_ENABLED=true`. Choosing native or hawkbit overrides `LAMASSU_UPDATES_API` for that browser, shows an editable **Updates API base URL** field and reloads the page. The defaults are `http://localhost:10090` (native) and `http://localhost:10091` (hawkbit) on localhost, and `<origin>/api` and `<origin>/api/hawkbit` on any other host.

## Where things are

The sidebar group **OTA UPDATES MANAGER** has:

| Item | Route | What it is |
|---|---|---|
| **Dashboard** | `/updates/dashboard` | Page title **OTA Dashboard**: rollout health, campaigns requiring attention, version distribution and the upcoming schedule |
| **OTA Devices** | `/updates/devices` | Every device with its installed and target version |
| **OTA Device Groups** | `/updates/device-groups` | Groups, with how many devices are behind |
| **Distribution Set** | `/package-inventory` | The update packs of every group |
| **Software Modules** | `/updates/software-modules` | The module catalog |
| **Campaigns** | `/updates` | Launches: list, create, run |

The group **IoT** has **Devices**, **Device Groups** (the Lamassu device registry and its groups), **Device Key Inventory** and **Platform Integrations**. The **JOB MANAGER** group (**Jobs**, **Workflows**) lists raw WFX jobs and workflows. It does not use the Updates API and does not create launches.

In the dashboard, a pack is a **distribution set** and a launch is a **campaign**.

## 1. Create a distribution set

Open **Distribution Set**. The list shows every group's packs, with filters for device group and status, a search box and a **Refresh** button. Press **New Distribution Set**.

| Field | Notes |
|---|---|
| **Name** | At least 3 characters, no spaces. Use underscores. Native mode also accepts only letters, digits, `.`, `_` and `-` |
| **Version** | Semver, default `1.0.0` |
| **Device Group** | Required. A pack belongs to one group and can only be launched to its devices |
| **Type** | **Raw File** (no restart), **Firmware** (restart), **Both** or **Other Type** |
| **Driver** | Native: **SWU** builds one signed image (signing is optional), **Generic** delivers files as they are. hawkBit: **SWU** accepts only SWU modules, **Generic** accepts binaries and other files. Fixed once created |
| **Allow previous-version download** | Lets devices download older versions of this pack |
| **Compatibility** | Optional launch preconditions (collapsed): devices must already carry another distribution set, or a software module, at a minimum version |

Press **Create Distribution Set**. You land on the pack's page. The preconditions stay editable there, in **Launch Preconditions** on the **Overview** tab (**Save preconditions**).

In hawkBit mode the form has one more section, **Software modules**. A hawkBit set links built modules, so tick at least one built module there, and at most one OS module. The table lists only modules that fit the **Driver**: an SWU set hides modules delivered as raw files, and a Generic set hides modules delivered as a prebuilt SWU. If nothing fits, it says "No built module fits this driver", and you build one first (see [hawkBit: build a module first](#hawkbit-build-a-module-first)).

On the native backend, the **Driver** also decides which workflow can install the pack: SWU packs need **Direct** or **Phased** and Generic packs need **Download-Install**. A mismatch leaves the update looking stuck after the device finishes.

## 2. Add files and build (native)

On the pack's page (`/updates/pack-details`) open the **Software Modules** tab. A native pack starts with one OS module named like the pack ("Not composed"). Open its row menu and choose **Add files**, drop your file, and upload it. The artifact name defaults to the file name without its extension, and the version is optional (semver). To compose the pack from more modules, use **Add module** (a new application module) or **Import module** (copy an existing one); the pack still builds one SWU.

Then press **Generate SWU** in the header. The sheet **SWU deliverable** has two tabs.

**Build here** builds the package from the pack's artifacts:

| Part | What to do |
|---|---|
| **Artifacts to include** | Checkboxes, all selected by default |
| **sw-descriptor** | Required. Load the file or type it in the editor. A checklist shows each file the description declares, and a file that is declared but not selected blocks the build |
| **Signing** | **Signing key**: none (unsigned) or a KMS key. With a key, pick a **Method** and a **Certificate** |
| **Encryption**, **Mode** | None, **Shared (one key for all devices)** or **Per-device (key per device)** |

For shared encryption choose a **Symmetric key** and whether to encrypt the descriptor (**Encrypt the descriptor**) and all files (**Encrypt all files**), or tick individual files. For per-device encryption choose an **Algorithm** (default `Ascon-128a`). Each device then uses its own key from the device key inventory. If you choose no security the sheet says "No security selected".

Press **Generate SWU**. The sheet uploads the sw-description, then builds. The badge becomes **Built** and the header button now reads **Regenerate SWU**. **Download SWU** appears next to it, except for a per-device pack: there is no download of the whole set, and each device's package is downloaded per device.

**Upload pre-built** attaches a `.swu` you built elsewhere, up to the service's `max_artifact_size_mb` (10 GiB by default). It is stored and served unchanged, nothing is signed or encrypted for you, and the version becomes built and immutable.

A **non-swu** pack has **Generate Package** instead. It builds a `.tar.gz` of the selected artifacts, with optional signing and optional shared or per-device encryption (the cipher is AES-GCM), and it has an **Upload pre-built** tab too. **Download Package** fetches the result.

To change a built pack, create a new version: use **New Version** in the pack list's row menu (the dialog has **Create Version**), or **New Version to Edit** on the pack's **Artifacts** tab. The new version must be higher than the current one, and it clears the built package.

### hawkBit: build a module first

In hawkBit mode a pack's files live in modules, built in the catalog.

1. Open **Software Modules** and press **New module**. Fill in **Module name** (it cannot contain `/` or `:`), **Type** (**Application** or **OS / base image**), **Version**, the **Distribution set** (leave **Catalog only — no set** to link it later) and the **Delivery intent**:

   | Delivery intent | Means |
   |---|---|
   | **Build SWU from inputs** | You provide files and a sw-description, and the service builds a `.swu` |
   | **Upload prebuilt SWU** | You upload a finished `.swu` |
   | **Deliver files unchanged** | The files are delivered as they are, and the module counts as built after a build step that can optionally encrypt and sign them |
   | **Decide later** | Not usable yet |

2. Add the files and, for **Build SWU from inputs**, the sw-description. The security cards offer signing and shared encryption. For **Build SWU from inputs** the switch **Build this module now** is on by default: turn it off to only store the files and build later from the row menu **Files and build**. For **Upload prebuilt SWU** there is no switch: the module is built as soon as the `.swu` is stored. For **Deliver files unchanged** the switch is **Build now**.
3. Press **Create Module**.
4. Create the distribution set and tick the built module.

A module linked into a set is frozen. Unlink it to change it, or add a new version from **Upgrade to a new version** in its catalog row menu. See [hawkBit mode](/docs/platform/updates/hawkbit-mode).

The catalog also works on the native backend: it lists the modules of every pack, and **New module** can leave a module in **Catalog only — no set** until you add it to a pack with **Import module**. Native import copies the module, while hawkBit linking shares it.

## 3. Start a campaign

Press **Start Campaign** in the pack's row menu in **Distribution Set** (enabled once the pack is built), or **New Campaign** on the **Campaigns** page. The form, **Create campaign**, is at `/updates/new`.

| Section | Fields |
|---|---|
| **Campaign basics** | **Campaign name (optional)**, **Distribution set**. **Device group** and **Driver** are inherited and read-only. **Workflow**: on native, every registered WFX workflow (Direct, Phased, Download-Install...), with a warning when it does not fit the driver. On hawkBit the field is **Install mode**: **Forced** (the device installs as soon as it polls) or **Soft** (the device may confirm or postpone) |
| **Schedule** | **Start as soon as it is executed** or **Start at a planned time** (date and time, in your browser's time zone) |
| **Batching & rollout** | **Batch mode** (**Fixed count** or **Percentage**), the batch size or percentage, and the switch **Auto rollout** |
| **Safety controls** | Only with Auto rollout on: **Approval threshold** (%) and **Error threshold** (%) |
| **Optional** | **Test device** (the canary, updated first), the set's **Preconditions** (read-only), **Notes**, **Weight** |

There is no device picker. A campaign targets every device of the pack's group, and the **Campaign summary** panel shows how many match and the estimated number of batches.

If the pack has preconditions, the dashboard first runs a dry run and shows **Campaign preconditions**: how many devices qualify, who does not and why. Tick **Force deploy to non-qualifying devices (not recommended)** to send to them anyway, then **Confirm campaign**.

Press **Create campaign**. The campaign is created but nothing is sent yet: you return to **Campaigns**.

## 4. Run and watch the campaign

On **Campaigns** (`/updates`) each row has the progress, the status (such as **Scheduled**, **Rolling Out**, **Paused**, **Completed**, **Cancelled**) and the batch progress. The tiles at the top (**Active campaigns**, **Scheduled**, **Rolling out**, **Requires attention**, **Completed**) filter the list. The page refreshes every four seconds while anything is moving.

The row's main button releases a batch:

- **Send to test device** sends the canary first.
- **Execute next batch** sends the next batch.

It is hidden when the campaign is completed or cancelled, paused, scheduled for later, has nothing pending, or is an **Auto rollout** campaign that is already running. While the canary is being tested or has failed, it stays visible but disabled. A failed canary pauses a native campaign: use **Resume** to retry it. A scheduled campaign starts by itself at its planned time.

The row menu has **Open details**, **Resume**, **Pause**, **Retry N failed** and **Cancel campaign** (it asks "Cancel Campaign?"). **Pause** stops further batches while devices already in flight finish; **Resume** continues. There is no button for marking a campaign complete: a native campaign completes by itself when no device is pending or in progress.

Below the table, a panel shows the selected campaign's **Batches** and a **Device progress** table. It follows the first active row until you select another. Open **View** for `/updates/details`:

- **Overview**: identity, preconditions, and the **Rollout Configuration** (workflow or install mode, rollout type and value, auto mode, test device). **Edit** on the rollout value works only where the backend supports editing a running strategy.
- **Device Jobs**: one row per device with its job state, a **Refresh Jobs** button and, per row, a **Workflow** button that opens the device's timeline. For the Phased workflow, a **Next** button and a strip of transitions let you confirm steps, which is how a `phased` campaign moves on.

The page header repeats the main button (**Execute Campaign**, or **Send to Test Device** before the canary) and **Retry N failed device(s)**. It has no pause, resume or cancel: those are in the list's row menu. On hawkBit, **Pause** is hidden until the campaign has started dispatching.

## 5. Follow devices

Open **Devices** (under **IoT**) and pick a device. The page has more tabs than the update-related ones listed here:

| Tab | Shows |
|---|---|
| **Information** | The distribution sets it carries, and **Up to date** or **Outdated** against the declared target |
| **Update Status** | Native: the WFX event workflow. hawkBit: the current update with Assigned, Installing and Installed steps |
| **Package Inventory** | **Installed Distribution Sets** with their artifacts, and the **Pack Update History** |
| **Jobs** | The device's WFX jobs |

Use **Launch Update...** in the device's actions menu to send one version to one device. The dialog **Launch update for device** asks for the device group (when the device is in several), the distribution set, the version and the workflow (or install mode), and creates one job. The pack's own actions menu has **Targeted Update**, which does the same for devices you tick in a list, always with the `direct` workflow, and it is enabled once the pack is built. On **OTA Devices**, select devices of one group and press **Update** to do it for many devices; the button is disabled when the selection spans several groups.

**OTA Dashboard**, **OTA Devices** and **OTA Device Groups** show version compliance: which devices are up to date, behind a declared target, or have no target. A group's page also lists the version each device runs against the group's released version, with an **Update to vX** button for the outdated ones. Without version-compliance support on the backend they still list devices and campaigns, but target versions show as **No target** or an em dash, with the alert "Target versions unavailable on this backend".

## What changes with the backend

| Screen | Native | hawkBit |
|---|---|---|
| Pack list | Status, packaging and **Built / Not built / Build failed** tiles | Those tiles, the status filter and column are hidden. A set has no build state of its own: it is ready when all its modules are built, and **Start Campaign** stays disabled until then |
| New pack | No modules section | Required **Software modules** section |
| Pack page header | **Generate SWU** and **Download SWU** (or **Generate Package** and **Download Package**) | A **Software modules** button instead: build in the catalog |
| Pack page tabs | **Overview**, **Software Modules**, **Contents**, **Manifest**, **Version History** (composition is supported, so there is no pack-level **Artifacts** tab) | The same. The **Artifacts** tab appears instead only if the hawkBit server lacks the module types |
| Security | On the **Generate SWU** sheet | Per module |
| Campaign form | **Workflow**: Direct, Phased or any registered WFX workflow | **Install mode**: **Forced** or **Soft** |
| Error threshold | The campaign is cancelled once this % of all its devices have failed | The campaign stops when more than this % of a batch fails |
| **Update Status** tab | WFX event workflow | hawkBit action steps |
| Edit a running rollout | Supported | Not supported |
| Module catalog | Modules are created without a set or added to a pack, and import copies them | Modules are built in the catalog, and a pack links them |

The **Manifest** tab (the signed version manifest) appears only when the backend supports artifact signatures.

## Not in the dashboard

These API features have no screen: marking a campaign complete (`/complete`), syncing all of a device's sets to the group's latest versions at once (`/sync-to-latest`), and declaring a group's latest version. Use the [API](/docs/platform/updates/reference/api) for them. To push one set to one device, **Launch Update...** and the per-device **Update to vX** button on a group's page do it.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Screens or buttons that should exist are missing | The capabilities request succeeded and the backend does not support them. Check **Updates backend** in the user menu (development builds) or `GET /updates/v1/capabilities` |
| Update screens fail to load or show errors | `LAMASSU_UPDATES_API` points at the wrong service or port, or your gateway does not route `/updates/v1` |
| **Start Campaign** is disabled | The pack is not built (native), or not every module is built (hawkBit) |
| No device group is offered when creating a pack | No device group exists yet. Create one under **Device Groups** |
| A campaign looks stuck in **Rolling Out** after devices finished | The workflow does not match the pack's driver. SWU packs need **Direct** or **Phased**; Generic packs need **Download-Install** |
