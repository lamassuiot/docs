This page collects what is unsupported, partial or surprising, so you can check it before you design a rollout. Each item points to the page that explains it.

## Security

- The service has no authentication, authorization, TLS or mTLS. Use a gateway. See [Security](/docs/platform/updates/security).
- The `app.server.cert_file`, `key_file` and `authentication.mutual_tls.*` keys have no effect.
- The connection to Postgres always uses `sslmode=disable`. In `native` mode the service does not verify the TLS certificate of the KMS, and the SWU signer script calls `curl -k`.
- The service sends the fixed identity `X-Principal-ID: admin-mode` to the Device Manager and the KMS, and its SymKMS calls carry no credential.
- There is no rate limiting.

## Backends

- The two backends differ in features. See [Capabilities](/docs/platform/updates/reference/capabilities). Notably, `hawkbit` mode has no per-device encryption, no custom workflows, no editing of a launch strategy after creation, no early completion of a campaign, no adding devices to a running campaign, no push events and no set-level prebuilt upload. A `swu-prebuilt` catalog module does accept a finished `.swu`. `native` mode builds one deliverable per pack and has no per-module deliverables.
- In `hawkbit` mode, a pack with several modules installs as several independent SWUpdate transactions. SWUpdate cannot roll back across several `.swu` files.
- hawkBit reserves the name and version of a module that was ever assigned to a device. Bump the version.
- In `hawkbit` mode a module build replaces the module's input files with the deliverable, so a module cannot be built twice: release a new version.
- hawkBit rollouts are created static: devices added to a group after a launch is created are not picked up by that launch.
- `hawkbit` mode reads a launch's strategy back from the rollout's groups, so a launch created with a fixed batch can read back as a percentage.
- A first `hawkbit` launch with a `test_device_id` fails until the group's devices exist in hawkBit. See [Troubleshooting](/docs/platform/updates/troubleshooting#api-calls).
- `POST /updates/v1/artifacts` in `hawkbit` mode holds the whole file in memory and in Postgres for 30 minutes and cannot be linked to a pack. Upload through the catalog route instead. See [hawkBit mode](/docs/platform/updates/hawkbit-mode#what-lives-where).
- hawkBit's own artifact limits (1 GiB per file, 20 GiB in total) apply unless you use the image of this repository or raise them. The image with the S3 artifact plugin is built from `docker/hawkbit` and is not published to a registry.

## Packs and versions

- **A new `native` pack version inherits the previous version's encryption settings for `.swu` builds.** `POST .../new` copies them, and a `.swu` build with no encryption fields does not clear them. After a per-device build, every later version of that pack still reports `per-device`, keeps the old `uncovered_devices`, and device downloads fail with `404` (`SWU not available for device ...`). Use a separate pack for each encryption variant. (`.../package` builds reset these fields.)
- `POST .../new` does not carry the pack's sw-description over: each version needs its own upload.
- **Artifact names are global.** A name can only be reused with a higher `version`, and the API answers a violation with `500`, not a `4xx`.
- A built version is immutable. To change it, create a new version.

## Scaling and resources

- With local storage on one `ReadWriteOnce` volume, only one `native` replica can run. Move `artifacts`, `builds` and `symkms` to S3 to scale out. See [Operations](/docs/platform/updates/operations#scale-out).
- SymKMS keys also default to local storage: point `symkms.storage` at S3, or share a volume, or they are lost.
- Per-device builds are CPU bound and grow with the number of devices. See [Signing and encryption](/docs/platform/updates/signing-and-encryption#set-up-per-device-encryption).
- Encrypting needs the file in memory (`swugenerator`, AES-GCM packages and raw modules, and any store with at-rest encryption), so very large encrypted files need proportionally large memory. Signing a raw module streams the file.
- Each in-flight upload needs free temporary disk as large as the file.

## Signing and encryption

- Signing needs a KMS that returns CMS (`PKCS7 SignedData`). The service refuses a non-CMS answer when it signs manifests and raw-module checksums, but the SWU signer script does not check it: with a KMS without CMS support a `.swu` build can succeed and still be rejected by a device that sets `public-key-file`. See [Signing and encryption](/docs/platform/updates/signing-and-encryption#signing).
- `non-swu` packages and raw modules are always AES-GCM, whatever algorithm name you send, and an Ascon-80pq key is refused for them.
- SymKMS does not enforce key purposes: any purpose is accepted and an empty one is a wildcard (an intentional placeholder). It refuses a caller-supplied IV for GCM, CTR and Ascon.
- Algorithm names are not normalised end to end: SymKMS ignores case and `_` versus `-`, but `swugenerator` needs hyphens (`aes-256-gcm`), and `ascon128a` is not `ASCON-128A`.

## Deployment and configuration

- `app.server.protocol`, `app.server.log_level`, `app.server.health_check` and the `health_check_logging` of the examples are accepted but not read. The request log is always on.
- The database is always named `updates`, and the service does not create it.
- The example configuration files contain developer-machine values and development secrets.
- The Helm chart's `config.update_domain` default (`http://updates:10090/v1/`) lacks the `/updates` prefix: the value must be the full API base ending in `/updates/v1/`, or the download URLs do not resolve.
- The Helm chart declares `postgresql.*` and `ingress.*` values but deploys no PostgreSQL and has no ingress template. It always uses the `Recreate` strategy, renders all of `config` (passwords included) into a ConfigMap, and has no value to add environment variables, volumes or an existing Secret.
- The container image does not drop privileges, and it ships a developer `config.yml`: mount your own.
- To build the Docker image yourself, the build context must contain the `lamassuiot/core` and `lamassuiot/sdk` checkouts next to `ota/`.
- `GET /health` does not check the database, WFX or hawkBit.

## Observability

- The service exports no traces, metrics or logs, and has no metrics endpoint. See [Operations](/docs/platform/updates/operations#observability).
