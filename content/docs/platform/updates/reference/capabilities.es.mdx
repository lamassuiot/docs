---
title: Capabilities
description: Las 22 capacidades de Lamassu Updates, qué admite cada backend y cómo las lee un cliente.
---

`GET /updates/v1/capabilities` indica a un cliente qué backend está activo (`native` o `hawkbit`) y cuáles de las 22 funciones admite. Léela una vez y oculta lo que no aplique. Una operación que el backend no implementa responde **`501 Not Implemented`**, nunca `500`; un `501` es una propiedad permanente del despliegue, así que reintentar no sirve de nada. La única excepción es `GET /workflows`, que en modo hawkBit responde una lista vacía.

## Lee las capacidades

La ruta no recibe parámetros y no tiene efectos secundarios. El servicio la sirve sin autenticación, igual que `/health`; un gateway delante de él puede seguir exigiendo un token.

```bash
curl -s https://lamassu.example.com/api/updates/v1/capabilities \
  -H "Authorization: Bearer $TOKEN"
```

La respuesta tiene tres campos:

| Campo | Tipo | Significado |
|---|---|---|
| `backend` | string | `native` o `hawkbit` |
| `supported` | objeto | Un booleano por capacidad. Siempre incluye las 22 claves, así que una clave ausente indica una diferencia de versión entre cliente y servidor, no que esté admitida |
| `unsupported` | array de strings | Las capacidades en `false`, repetidas por comodidad, en el orden de la tabla siguiente |

Un ejemplo para un despliegue native:

```json
{
  "backend": "native",
  "supported": {
    "latest_versions": true,
    "version_compliance": true,
    "artifact_signatures": true,
    "artifact_encryption": true,
    "per_device_encryption": true,
    "artifact_download_by_name": true,
    "workflows": true,
    "launch_strategy_update": true,
    "launch_complete": true,
    "launch_device_assignment": true,
    "scheduled_launch": true,
    "push_events": true,
    "launch_preconditions": true,
    "campaigns": true,
    "canary_device": true,
    "device_inventory": true,
    "artifact_catalog": true,
    "prebuilt_deliverable": true,
    "software_module_composition": true,
    "software_module_deliverables": false,
    "standalone_software_modules": true,
    "software_module_replace": false
  },
  "unsupported": ["software_module_deliverables", "software_module_replace"]
}
```

## Soporte por backend

«Sí» significa admitido. «Condicional» significa que depende de la configuración o del servidor hawkBit; consulta las notas tras la tabla.

| Capacidad | native | hawkbit |
|---|---|---|
| `latest_versions`: declarar la última versión por grupo, más la deriva por dispositivo y la sincronización forzada | Sí | Sí |
| `version_compliance`: informes de conformidad y estado de versión de todo el grupo | Sí | Sí |
| `artifact_signatures`: manifiestos de versión firmados y el archivo de artefactos | Sí | Sí |
| `artifact_encryption`: cifrado con clave compartida y firma con KMS durante la compilación | Sí | Condicional |
| `per_device_encryption`: un entregable por dispositivo, cada uno con su propia clave | Sí | **No** |
| `artifact_download_by_name`: descargar un archivo preparado de un pack por nombre | Sí | Sí |
| `workflows`: elegir el workflow de WFX por lanzamiento | Sí | **No** |
| `launch_strategy_update`: editar la estrategia tras crear el lanzamiento | Sí | **No** |
| `launch_complete`: marcar un lanzamiento como completado antes de tiempo | Sí | **No** |
| `launch_device_assignment`: añadir dispositivos a un lanzamiento tras crearlo (una operación del servicio sin ruta HTTP) | Sí | **No** |
| `scheduled_launch`: iniciar un lanzamiento en un momento futuro | Sí (el servicio sondea) | Sí (el planificador propio de hawkBit) |
| `push_events`: estado de los jobs enviado por el servidor | Sí | **No** (sondeo) |
| `launch_preconditions`: acotar los dispositivos desplegables según las versiones instaladas | Sí | Sí |
| `campaigns`: planificar, iniciar, pausar, reanudar, cancelar y reintentar los fallidos | Sí | Sí |
| `canary_device`: el primer lote es un dispositivo concreto | Sí | Sí |
| `device_inventory`: qué versión de pack tiene un dispositivo y su historial de actualizaciones | Sí | Sí |
| `artifact_catalog`: catálogo de artefactos de toda la flota y listado por pack | Sí | Sí |
| `prebuilt_deliverable`: adjuntar a un pack un archivo compilado externamente | Sí | **No** |
| `software_module_composition`: un pack es una composición de módulos tipados | Sí | Condicional |
| `software_module_deliverables`: cada módulo tiene su propio entregable | **No** | Sí |
| `standalone_software_modules`: crear un módulo sin pack | Sí | Condicional |
| `software_module_replace`: sustituir un módulo por otra versión de sí mismo | **No** | Condicional |

### Capacidades condicionales en modo hawkBit

- **`artifact_encryption`** se informa como no admitida solo cuando no está configurado ninguno de `swugenerator_path`, `symkms_endpoint` y `kms_endpoint`. Cada opción de compilación sigue necesitando su propia configuración: consulta [Firma y cifrado](/docs/platform/updates/signing-and-encryption).
- **`software_module_composition`, `standalone_software_modules` y `software_module_replace`** dependen de que el servidor hawkBit tenga los tipos de módulo preinstalados `os` y `application` y el tipo de conjunto `os_app` o `app`. El servicio lo sondea con un timeout de 5 segundos, guarda el resultado unos cinco minutos y asume que hay soporte cuando hawkBit no responde. Si el sondeo falla, las tres capacidades se informan juntas como no admitidas.
- **`software_module_deliverables`** siempre se informa como admitida en modo hawkBit. Compilar un módulo `swu-build` sigue necesitando un `swugenerator_path`; sin él, la compilación responde `501`.
- **`prebuilt_deliverable`**: un pack de hawkBit nunca se compila directamente. Un módulo `swu-prebuilt` del catálogo acepta en su lugar un `.swu` terminado.

### Capacidades cuyo significado cambia

Ambos backends informan `software_module_composition`, pero importar un módulo lo **enlaza** en modo hawkBit (ambos packs comparten un único módulo) y lo **copia** en modo native. La lista de módulos reutilizables lo indica por candidato en su campo `shared`, de modo que un cliente puede decirle al operador cuál de los dos casos tiene. Consulta [Conceptos](/docs/platform/updates/concepts).

En modo native un lanzamiento despacha un job por dispositivo con una única URI de descarga, así que un módulo no tiene entregable propio: el pack compila un único `.swu` a partir de las entradas de todos sus módulos. Por eso `software_module_deliverables` y `software_module_replace` no están admitidas allí.

## Qué debe hacer un cliente

- Llama a `capabilities` una vez al arrancar y antes de mostrar una función que la tabla marque como dependiente del backend.
- Trata un `501` en una ruta como definitivo: oculta la acción en lugar de reintentar.
- No deduzcas el backend por la URL. Ambos sirven las mismas rutas `/updates/v1`; consulta la [Referencia de la API](/docs/platform/updates/reference/api) para saber qué rutas responden `501` en cada backend.
- Vuelve a leer las capacidades tras cambiar los tipos de módulo de hawkBit o la configuración de compilación.
