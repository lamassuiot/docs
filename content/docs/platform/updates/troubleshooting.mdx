---
title: Troubleshooting
description: Symptoms, likely causes and fixes for start-up errors, API calls, builds, downloads and updates that do not reach devices.
---

Diagnose one operation at a time. Note the backend (`GET /updates/v1/capabilities` shows it), the endpoint, the HTTP status and the `err` text of the response body: errors are returned as `{"err": "..."}`. If your problem is not here, check [Limitations](/docs/platform/updates/limitations) first.

## HTTP status codes

| Status | Meaning |
|---|---|
| `400` | The request or the current state of the resource does not allow the operation. The message says what to change. |
| `403` | A policy refuses the operation. |
| `404` | The resource does not exist. Another group's launch also answers `404`. |
| `409` | A conflicting operation is in progress, or the version is already built. |
| `413` | A file is larger than `max_artifact_size_mb`. |
| `500` | An unexpected failure. Some validation errors still answer `500` (see below). |
| `501` | The active backend does not support the operation. Read the [capabilities](/docs/platform/updates/reference/capabilities). |

## Starting the service

| Symptom or message | Likely cause | Fix |
|---|---|---|
| `docker compose up` fails with a network error | The `ota-net` network does not exist | `docker network create ota-net` |
| Docker build cannot find `lamassuiot/core` | The build context is not the parent of the checkout | Build with the context that contains `ota/`, `lamassuiot/core` and `lamassuiot/sdk`. `docker compose build updates` uses it. |
| The service ignores `OTA_CONFIG_FILE` and logs a warning | The file could not be loaded, so it fell back to `/etc/lamassuiot/config.yml` | Check the path and the YAML. In the image the fallback is the repository's developer configuration. |
| `workflow_file "..." must contain "direct"` | `workflow_file` does not name the `direct` workflow | Point it at `wfx.workflow.dau.direct.yml` or a path containing `direct`. |
| `failed to list existing WFX workflows` | `wfx_endpoint` is wrong or WFX is down | Use the **management** port (`8081` inside the Compose network, `9081` on the host) and check that `custom-wfx` runs. |
| Postgres reports that database `updates` does not exist | The database is not created by the service | Create it (Docker Compose does it through `init.sql`). |
| `mode is "hawkbit" but hawkbit.base_url is not configured` | Missing key | Set `hawkbit.base_url`. |
| `mode is "hawkbit" but storage (Postgres) is not configured` | `storage.hostname` is empty | Set the `storage` block. |
| `S3 bucket "x" is not accessible at ...` | Wrong bucket, endpoint or credentials, or the bucket does not exist | Fix the `s3_*` keys of the block named in the error. The bucket must already exist. |
| `local encryption key must be exactly 32 bytes` | `encryption.local_key` is not 32 bytes of hex | Use 64 hex characters (`openssl rand -hex 32`). |
| `could not configure leader election: the service account may not ... Leases` | The pod cannot use Leases and `leaderElection.mode` is `kubernetes` | Grant the Role the chart provides (`serviceAccount.create: true`), or set `leaderElection.mode: database`. |
| `not running inside a Kubernetes cluster` | `leader_election.mode: kubernetes` outside a cluster | Use empty (auto) or `database`. |
| `builds.presign: ...` or `hawkbit.artifact_store.presign: ...` | The presigned-download settings of that block are invalid | See [Downloads and presigned URLs](#downloads-and-presigned-urls). |
| The hawkBit container exits | S3 storage is selected for hawkBit and the bucket is unreachable | Fix the S3 settings, or use `HAWKBIT_ARTIFACT_STORAGE=fs`. hawkBit never falls back to local disk silently. |
| `/health` answers but WFX calls fail | `/health` does not check dependencies | Check `wfx_endpoint` and that WFX is running. |
| Debug output shows secrets | `app.logs.level: debug` prints the configuration | Use `info`. See [Security](/docs/platform/updates/security). |

## API calls

| Symptom or message | Likely cause | Fix |
|---|---|---|
| `501 Not Implemented` | The active backend does not support the operation | Read `GET /updates/v1/capabilities`. In `hawkbit` mode, `POST .../swu` and `.../package` always answer `501`: build the modules in the catalog. |
| `409` `update pack version X is already built; create a new version ...` | You changed a built version | Native mode: `POST .../new` with `{"version":"x.y.z"}` greater than the current one, then upload the sw-description again (it is not carried over) and give any re-uploaded artifact a higher `version`. `hawkbit` mode: see the next row. |
| `hawkbit mode: cannot ... here — a software module linked to a distribution set is frozen` (`400`) | Pack-scoped edits are refused in `hawkbit` mode | Unlink the module, change and build it in the catalog, link it again. Or release a new version of the module and create a pack from it under another name: pack names are unique per group, and an `os` module cannot be swapped on an existing pack. See [hawkBit mode](/docs/platform/updates/hawkbit-mode#create-and-build-a-pack). |
| `409` `... is being built or changed by another request; retry when it finishes` | Two builds, or a build and a change, on the same pack or module | Wait and retry. The lock is released when the operation ends or fails. |
| `409` on create | A pack with that name exists in the group | Pick another name. |
| `413` `file "x" is N MiB; the maximum upload size is M MiB` | The file exceeds `max_artifact_size_mb` | Raise it, and the limits of every proxy in front. See [Operations](/docs/platform/updates/operations#upload-size-and-proxies). A proxy answering `413` with its own body (for example nginx's default 1 MiB) is the proxy, not the service. |
| Upload `400` mentioning content that contradicts the filename | A file named `.swu` is not a SWU | Upload a real `.swu`, or rename the file. |
| Artifact upload fails with `500` and `version X must be greater than the current latest version` | Artifact names are global, and a name can only be reused with a higher `version` | Give the new file a higher `version`, or a new artifact name. |
| `Cannot create launch: update pack 'x' has not been built yet` (`400`) | The pack is still a draft | Build it first. |
| `Cannot create launch: update pack "x" is per-device encrypted and only N of M devices have a package` (`400`) | Some devices have no key | Assign the missing keys and build again. There is no override. |
| `approval_threshold and error_threshold must be between 0 and 100` | Thresholds are percentages | Use `0`-`100`. |
| `launch X is paused; resume it first` (`400`) | The launch was paused | Call `resume`. |
| `test device X cannot act as this group's canary: device X does not exist` (`hawkbit` mode) | The canary check runs before the group's devices exist in hawkBit | Run a dry run without `test_device_id` first (`POST .../launch?dry_run=true`), which registers the devices as targets. |
| The device registry or KMS answers `401` | The service always sends `X-Principal-ID: admin-mode`, and the gateway in between rejects it | Point `dms_endpoint` and `kms_endpoint` at the internal service addresses, or allow that header. |

## Builds

| Symptom or message | Likely cause | Fix |
|---|---|---|
| `no sw-descriptor uploaded for update pack "x" vN` | The version has no sw-description (each version needs its own) | Upload it. |
| `failed to read binaries directory` or `binaries directory is empty` | `native` mode: nothing was staged, because the build body has no `selected_artifact_ids` | Pass the artifact IDs. See the [publish guide](/docs/platform/updates/guides/publish-and-roll-out). |
| `swugenerator failed: exit status N` | The tool rejected its input. Its own message is in the service log | Check the sw-description, the file names it references, the algorithm spelling (`aes-256-gcm`, hyphens required) and the key length. |
| `signing requested but sign_script_path/kms endpoint are not configured` | A `.swu` was asked to be signed without both settings | Set `sign_script_path` and `kms_endpoint`. |
| `signing requires key id, algorithm and certificate together` | A partial signature request | Send all three `signature_*` fields. |
| `failed to sign version manifest: the KMS did not return a PKCS7/CMS signature` | The KMS answered with a bare signature | Use a KMS version that returns CMS. See [Signing and encryption](/docs/platform/updates/signing-and-encryption#signing). |
| `symKMS SDK client is not configured` | `symkms_endpoint` is empty | Set it. In `hawkbit` mode also set the `symkms` block so the routes exist. |
| `failed to fetch key "k" via symKMS` | Wrong key ID or `user`, or the endpoint points at another instance | The key belongs to its `user_id`; `symkms_endpoint` must be this instance's own address and port. |
| Per-device build fails mentioning `encrypted = true` | No artifact in the sw-description is marked `encrypted = true;` | Mark the artifacts to encrypt. |
| `no devices found for DMS X` or `none of the N devices ... have a key assigned for firmware-encryption` | The group has no devices in the registry, or none has a key | Check the group in Lamassu IoT and `dms_endpoint`; assign `firmware-encryption` keys. |
| `hawkbit mode: this deployment has no SWU builder configured` (`501`) | `swugenerator_path` is empty | Set it, or upload a prebuilt `.swu` module. |
| `hawkbit mode: this deployment has no SymKMS configured` or `... no KMS endpoint configured` (`501`) | Encryption or signing asked without `symkms_endpoint` or `kms_endpoint` | Set them. |
| `software module "x" ... is N MB and encrypting it needs about M MB in memory` | `build_memory_limit_mb` refuses the build | Sign without encrypting, split the file, or raise the limit together with the pod's memory. |
| `... is already built; ... release a new version of it to build again` | A build replaces the module's input files | Create a new version of the module. |

## Downloads and presigned URLs

| Symptom or message | Likely cause | Fix |
|---|---|---|
| `404` `SWU not available for device D on pack "x" vN` | The pack is per-device encrypted and has no package for that device (its key was missing at build time, or the pack inherited per-device mode from an earlier version), or the build file is gone from the store | Assign the device's key and build a new version. To avoid inheriting, use a separate pack for each encryption variant (see [Limitations](/docs/platform/updates/limitations#packs-and-versions)). |
| Startup: `presign needs its own credential` | `presign` is enabled without a signing credential | Set `presign.access_key_id[_file]` and `secret_access_key[_file]`, a read-only pair. |
| Startup: `the presign credential can WRITE` | The signing credential has write access | Give it a read-only policy on the objects it serves. |
| Startup: `presign signs with the storage's own credential` | Same key as the storage | Create a separate read-only key. |
| Startup: `the store does not accept the presign credential` | The store does not know the key, or the signature does not match | Create the user in the store; check region and endpoint. |
| Startup: `presign cannot be combined with client-side encryption` | `encryption.type` is not `none` on that block | Use store-side encryption, or disable `presign`. |
| Startup: `presign.public_endpoint must be an http(s) origin` | The value has no scheme, or has a path | Use an origin such as `https://updates.example.com`. |
| The device gets `403` from the store after the `302` | The URL expired before the device started the GET, the signed `Host` is not what the device used (`public_endpoint` wrong), the signing key cannot read that prefix, or clocks differ | Retry (a fresh URL is issued per request); check `ttl`, `public_endpoint` and the key's policy. |
| Downloads stream through the service despite `presign` | A `HEAD` request, an artifact download by ID in `native` mode, a store without `presign` for that block, or the signing failed (logged) | Only builds in `native` mode and the S3 plugin objects in `hawkbit` mode are redirected. |

## Updates not reaching devices

| Symptom | Likely cause | Fix |
|---|---|---|
| Devices cannot download the `.swu` (`native` mode) | `update_domain` is not reachable from the device, or is not the full `.../updates/v1/` base with a trailing slash | Use an address the device can resolve. The Helm chart default lacks `/updates`. |
| `hawkbit` mode: a device gets `401` from DDI | hawkBit refuses devices that do not authenticate | Enable and use a hawkBit device authenticator. See [hawkBit mode](/docs/platform/updates/hawkbit-mode#device-authentication-in-production). |
| `hawkbit` mode: a device gets `429` | hawkBit's own DoS filter, which limits how often a device may call it | Slow the polling and feedback of the device. |
| `hawkbit` mode: the launch stays `running` with no progress | The devices never contacted hawkBit, or they poll a different hawkBit | Check which hawkBit the devices poll, and that the targets exist. A rollout group cannot advance until its devices poll. |
| `hawkbit` mode: devices are not found in the group | `dms_endpoint` is not set, so groups are the `group:<id>` target tags | Set `dms_endpoint`, or tag the targets. |
| A `phased` launch stays at `CREATED` (`native` mode) | In the `phased` workflow some steps are made by WFX or an operator | Confirm them through WFX, or use `direct`. |
| A `non-swu` launch shows SWU states (`native` mode) | It was created with `workflow_type: direct` | Use `download-install`. |
| The device installs and shows the old version | The payload version was not changed | Bump the version before building. |
| The device ignores new deployments | SWUpdate keeps the update state of an earlier install as pending test (`ustate=1`) and refuses a new one | Confirm or reset the device's update state. This is a device setting, not a service one. |
| The device rejects the `.swu` and the error mentions decryption or an invalid image | The `.swu` is unsigned while the device requires a signature, or the signature is not CMS | Sign it with a KMS that returns CMS. A signature failure can be reported as an encryption error. |
| The device fails to decrypt | The key used to build differs from the device's key, or the algorithm spelling differs | Use the same key and algorithm. Check the assignment in SymKMS. |

## Scaling and background work

| Symptom | Likely cause | Fix |
|---|---|---|
| Pods cannot start on different nodes | The `ReadWriteOnce` volume (both modes while `persistence.enabled` is true) | Set `persistence.enabled: false` and move `artifacts`, `builds` and `symkms` to S3. See [Operations](/docs/platform/updates/operations#scale-out). |
| Campaign batches never advance (`native` mode) | Leader election is failing, or WFX events are not arriving | Check the Leases and the RBAC, or set `leaderElection.mode: database`. The log line `leadership acquired` appears on the leader. |
| Scheduled launches never start (`native` mode) | The same background work, which runs on the leader | As above. |
| Per-device builds are slow | The CPU limit | Raise it. See [Resource sizing](/docs/platform/updates/operations#resource-sizing). |
| The pod is killed during an upload or an encrypted build | Memory limit, or the temporary disk is full | Size memory for the largest file you encrypt, and give `TMPDIR` room. |

## Getting more information

- Raise `app.logs.level` to `debug`, but remember that it prints secrets.
- `GET /updates/v1/capabilities` shows the active backend and what it supports.
- Each replica logs which one leads (`leadership acquired`, `is the leader, standing by`).
- In `hawkbit` mode, inspect what the service created through hawkBit's Management API (port `8090` in Compose, with the Basic Auth credentials of the configuration). Each hawkBit instance has its own data: query the one named in `hawkbit.base_url`.
