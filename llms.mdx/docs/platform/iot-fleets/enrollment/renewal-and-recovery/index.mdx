# EST in Lamassu (/docs/platform/iot-fleets/est/configuration)



The DMS applies the configured authentication mode to enrollment requests before enforcing registration and issuance rules. Initial enrollment and re-enrollment have independent authentication settings. Lamassu supports a client certificate, a webhook, both, or no DMS authentication. [Authentication and trust](/docs/platform/iot-fleets/est/bootstrap-identity) explains credentials, initial trust and validation.

The DMS also controls the CA, profile, renewal window, server-generated keys and distributed certificates. See the [DMS guide](/docs/platform/iot-fleets/enrollment/dms) for administration.

Endpoint reference [#endpoint-reference]

Public route in the examples: `/.well-known/est/{APS}/{operation}`. `APS` is the DMS ID. The router admits routes without that segment, but the controller requires it; do not use them as a default service. Gateway configuration determines the public host and route.

| Operation                            | Method | Authentication and condition                                                                   |
| ------------------------------------ | ------ | ---------------------------------------------------------------------------------------------- |
| [`/cacerts`](#cacerts)               | GET    | DMS reading does not require an EST credential; HTTPS and infrastructure controls still apply. |
| [`/simpleenroll`](#simpleenroll)     | POST   | Initial authentication and DMS registration/replacement policy.                                |
| [`/simplereenroll`](#simplereenroll) | POST   | Renewal authentication, existing identity, subject, revocation and window.                     |
| [`/serverkeygen`](#serverkeygen)     | POST   | Initial authentication and server-side key generation enabled.                                 |

These routes do not implement `/csrattrs` or `/fullcmc`. There is no native JWT EST authentication mode; a webhook can interpret a request credential according to its own contract.

Authentication per operation [#authentication-per-operation]

The blocks are independent:

* `settings.enrollment_settings.est_rfc7030_settings` for `/simpleenroll` and `/serverkeygen`.
* `settings.reenrollment_settings.est_rfc7030_settings` for `/simplereenroll`.

| `auth_mode`                               | Control applied in the configured operation          |
| ----------------------------------------- | ---------------------------------------------------- |
| `CLIENT_CERTIFICATE`                      | Presented certificate validation.                    |
| `EXTERNAL_WEBHOOK`                        | Configured webhook authorization.                    |
| `CLIENT_CERTIFICATE_AND_EXTERNAL_WEBHOOK` | Certificate validation followed by webhook approval. |
| `NO_AUTH`                                 | No DMS requester authentication.                     |

Webhook and combined modes also execute during re-enrollment when configured in its block. They do not implicitly degrade to NO\_AUTH. An absent or unrecognized mode fails.

For initial mTLS, `client_certificate_settings` contains `validation_cas`, `allow_expired`, `chain_level_validation` and `allow_unverifiable_revocation`. The validator receives one certificate credential; the flow does not guarantee forwarding every handshake intermediate to it. For a direct case, configure the bootstrap’s direct issuer as validation CA and test the actual Gateway path.

The authentication editor offers an **Allow certificates without revocation information** switch (`allow_unverifiable_revocation`, off by default). When it is on, certificates (and intermediate CAs of the chain) that Lamassu does not manage and that list no OCSP or CRL endpoint are accepted; unreachable, stale or inconclusive revocation answers are always rejected. While the switch is on, the console shows an amber warning: **Revocation will not be verified**. A revoked certificate with no OCSP or CRL endpoint, and not managed by Lamassu, will be accepted, and this also applies to the intermediate CAs of the chain.

The same switch is offered in both the enrollment and re-enrollment authentication editors and is stored per block inside `est_rfc7030_settings.client_certificate_settings`; a DMS stored before this field existed loads with the switch off. The console also shows an amber warning alert whenever an authentication option is in its insecure state (**Allow expired certificates** on, **Allow expired renewal** on or **Verify CSR signature** off) and the No authentication note is presented as a warning alert too.

Revocation is checked for every presented certificate. In initial enrollment the client certificate **and** every intermediate CA between it and the validation CA are checked, each against its issuer; extra certificates the device sends in the handshake are ignored. A validation CA that is revoked in Lamassu rejects the operation: the first validation CA that validates the certificate is used, and a revoked one is not replaced by the remaining validation CAs. Certificates issued and managed by Lamassu are checked against their stored status. External certificates are checked through their OCSP and CRL endpoints, and the operation fails closed when revocation cannot be verified: only `allow_unverifiable_revocation` (`false` by default in both blocks) relaxes the case of an external certificate that lists no endpoint at all. Endpoints that exist but are unreachable, return stale or invalid evidence, or report an inconclusive status are always rejected, whatever the option says. The details and the evidence the endpoints must present are in [Revocation and checks](/docs/platform/iot-fleets/est/bootstrap-identity#revocation-and-checks).

For certificate re-enrollment, the validator tries the enrollment CA first and then the CAs listed in `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`; those are the re-enrollment validation CAs. That list is optional because the enrollment CA is always trusted for re-enrollment, and each settings block consults only its own `validation_cas`. CAs listed only in the initial block's `validation_cas` do not extend re-enrollment acceptance; during a CA rotation, add the old issuance CA to the re-enrollment block's list. The re-enrollment validator compares the presented TLS leaf against those CAs; the re-enrollment block's `chain_level_validation` and `allow_expired` values are stored but not consulted, and expiry is governed by `enable_expired_renewal`. Re-enrollment checks revocation of the client certificate only; that check is governed by the re-enrollment block's own `allow_unverifiable_revocation`.

For a webhook, configure destination, Lamassu-to-service authentication, method and timeout. The [authentication contract](/docs/platform/iot-fleets/est/bootstrap-identity) explains the device credential and request body. `NO_AUTH` does not establish ownership of the requested ID.

External webhook settings [#external-webhook-settings]

The webhook authentication modes read `external_webhook_settings` in the same `est_rfc7030_settings` block:

| `external_webhook_settings` field | Decision                                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `url`                             | Absolute `http` or `https` URL of the receiver. It must be the final URL; redirects are not followed.                                            |
| `method`                          | `POST` or `PUT`; `POST` by default.                                                                                                              |
| `name`                            | Label used in service logs.                                                                                                                      |
| `config.auth_mode`                | `noauth`, `apikey`, `jwt` or `mtls`. An absent or unknown value behaves as `noauth`.                                                             |
| `config.log_level`                | Log level of the webhook call: `debug`, `info`, `warn` or `error`; `info` by default.                                                            |
| `config.apikey_options`           | Required for `apikey`: `header` and `key`. Reserved header names are rejected.                                                                   |
| `config.jwt_options`              | Required for `jwt`: `oidc_client_id`, `oidc_client_secret` and an absolute `http` or `https` `oidc_well_known`.                                  |
| `config.mtls_options`             | Required for `mtls`: `cert_content` and `key_content` as Base64-encoded PEM, like certificates elsewhere in the API; plain PEM is also accepted. |
| `config.insecure_skip_verify`     | Skips verification of the receiver certificate when `true`. Verification is on by default. Unlike alert channels, this flag is honored here.     |
| `config.call_timeout`             | Maximum duration of the authorization call (for example `10s`); 10 seconds by default.                                                           |

Rules for that configuration:

* Creating or updating a DMS whose enrollment or reenrollment `auth_mode` uses the webhook validates the block and returns HTTP 400 (the body starts with `struct validation error:` and continues with `invalid enrollment external webhook config` or `invalid reenrollment external webhook config`) when the URL, method or options are invalid. That includes an `mtls_options.cert_content`/`key_content` pair that does not decode to a matching certificate and private key. File references (`ca_cert_file`, `mtls_options.cert_file`, `mtls_options.key_file`) are always invalid: the service does not read files, so enter the certificate and key as Base64-encoded PEM in `mtls_options.cert_content` and `key_content`, or as plain PEM.
* A custom `apikey_options.header` may not use names that the platform or the receiving service trusts (for example `X-Principal-Id`, `X-Request-Id`, `Host`, `Content-Type` or `Forwarded`) and no name may start with `X-Forwarded-`, `X-Envoy-` or `X-Lms-` (case-insensitive). The [DMS API reference](/docs/api-reference/dms-manager) documents the `WebhookCall` and `WebhookCallHttpClient` schemas and that reserved API-key headers are rejected.
* The nested `http_client` key exists only in alert channel configurations; in a DMS body it is ignored. The DMS key is `external_webhook_settings.config`.
* A body with `config.auth_mode` set to `apikey`, `jwt` or `mtls` must carry its corresponding option block (`apikey_options`, `jwt_options` or `mtls_options`) and nothing else. Bodies with those auth modes carrying only `apikey`, `oidc` or `mtls` fail validation with 400, and `validate_server_cert` is always ignored: use `insecure_skip_verify`. Only bodies without option blocks are accepted as `noauth`, and their credentials are dropped.
* The authorization response must be JSON of at most 1 MiB; a larger body fails the call.

<Callout type="warn" title="Credentials over http://">
  With credentials configured, they are sent regardless of the URL scheme: an `http://` webhook receives the API key or bearer token in cleartext, and mTLS has no effect because no TLS handshake takes place, so the client certificate is never presented. Prefer `https://` for `url`, `oidc_well_known` and the token endpoint it advertises.
</Callout>

Initial authentication and renewal settings are stored independently. Re-enrollment reads its own block and an absent or unknown mode fails. Read both blocks before editing. The console exposes independent editors for the enrollment and re-enrollment authentication, with the same Log Level, Call Timeout, HTTP Authentication and credential fields as the webhook channels, plus a **Skip TLS Verification** switch (off by default, so verification stays on; the console warns when you enable it).

Webhook credentials must be stored as PEM content. File references (`ca_cert_file`, `mtls_options.cert_file`, `mtls_options.key_file`) are never valid in a stored webhook config: delivery rejects any webhook config that references files, whatever its auth mode, so every enroll and reenroll that calls that webhook fails until the certificate and key are entered as Base64-encoded or plain PEM in `mtls_options.cert_content` and `key_content`, or the file fields are removed if the webhook does not use mTLS. If a stored config holds file paths in `mtls_options.cert_content` or `key_content`, every full settings update (`POST /v1/dms`, `PUT /v1/dms/:id`) fails validation (settings are replaced wholesale, so the stored config must be resent) until the values are replaced by PEM content or the webhook stops being used. Meanwhile, delivery of that webhook fails on every call; a metadata-only update through `PUT` or `PATCH` on `/v1/dms/:id/metadata` still succeeds. To fix it in the console, open the DMS, replace any file-path value with PEM content (the editor rejects file paths with an inline field error) and save. Saving rewrites `external_webhook_settings.config` with the current keys, and the console reads both plain and Base64-encoded PEM from migrated configurations and stores the material Base64-encoded. If your stored config previously relied on `validate_server_cert: false`, it now carries `insecure_skip_verify: true`: receiver-certificate verification stays skipped until you set that flag to `false`. See [3.8.0 to 4.0.0](/docs/upgrades/3-8-0-to-4-0-0) for the upgrade notes and the operator checklist.

The re-enrollment trust set lives in `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`. The flat field `reenrollment_settings.additional_validation_cas` is not part of the API: bodies that carry it are accepted but the value is silently ignored (unknown JSON fields are dropped) and GET responses do not include it. Read the DMS before sending API edits: an update body built with that flat field silently empties `validation_cas`.

Compatibility notes [#compatibility-notes]

Do not interpret every 500 as a transient failure. Invalid input typically produces 400; service denials and errors typically produce 500 with a JSON `err` body. Gateway errors and some controller paths can have another format. Retain headers and body before decoding and see [troubleshooting](/docs/platform/iot-fleets/est/troubleshooting).

The examples use [openssl-pkcs7](https://docs.openssl.org/3.6/man1/openssl-pkcs7/) to extract certificates and [openssl-x509](https://docs.openssl.org/3.6/man1/openssl-x509/) to prepare renewal. Check your version's capabilities and responses before integrating a generic EST client.

Before you begin [#before-you-begin]

For an end-to-end first enrollment, follow [Enroll and connect your first device](/docs/platform/iot-fleets/quickstarts/enroll-device).

You need the public HTTPS DMS URL, server trust obtained through an approved channel, the operation's authentication mode and an admitted identifier. The examples use Bash, OpenSSL 3.x and curl with `--fail-with-body`; use a private working directory and compatible versions of these tools.

Prepare `est-trust.pem` to verify the EST server, `bootstrap.crt` and `bootstrap.key` for initial certificate authentication, and `device-root.pem` as the approved root of the device issuer. The two trust files can contain different roots. For another authentication mode, adapt the credentials according to [Bootstrap identity](/docs/platform/iot-fleets/est/bootstrap-identity).

Replace the host and `REPLACE_DMS_ID` with those of your installation. The URL's APS is the DMS identifier, not its display name.

```bash
set -euo pipefail
umask 077
EST_BASE='https://lamassu.example.com/.well-known/est/REPLACE_DMS_ID'
```

/cacerts [#cacerts]

`GET /cacerts` retrieves the certificates published by the DMS. The client can inspect the bundle and use approved certificates to build trust chains.

Configuration [#trust-distribution]

The options are stored in `settings.ca_distribution_settings` and determine the contents of `/cacerts`.

<span id="lamassu-tls-certificate" />

**Lamassu TLS certificate**

`include_system_ca` (**Include Lamassu System CA**). Available downstream TLS certificate; it can be a leaf, not an issuing CA.

<span id="enrollment-ca" />

**Enrollment CA**

`include_enrollment_ca` (**Include Enrollment CA**). Selected issuing CA certificate.

<span id="managed-cas" />

**Managed CAs**

`managed_cas` (**Managed CAs**). Explicitly selected CA certificates.

All ancestors are not added automatically.

Request and Response [#cacerts-request-and-response]

Send an HTTPS GET with an empty body. The DMS lets clients retrieve certificates without an EST credential. Gateway controls still apply.

* **Default response.** `Content-Type: application/pkcs7-mime; smime-type=certs-only` and `Content-Transfer-Encoding: base64`. The body is Base64-encoded DER PKCS#7 with lines of up to 76 characters.
* **PEM response.** Lamassu selects this format when `Accept` is exactly `application/x-pem-file` and returns the same value in `Content-Type`. The body contains the certificates in PEM.

<span id="what-cacerts-returns" />

**What cacerts returns**

The DMS may include the available downstream TLS certificate, selected Managed CAs and enrollment CA. Selecting the issuer does not include every ancestor. The set may contain leaves, roots and intermediates, including multiple hierarchies during migration.

Position does not define the chain. Identify certificates by subject, issuer, AKI/SKI, signature and constraints. Download and inspect using [EST client](/docs/platform/iot-fleets/est/configuration#download-and-inspect-cacerts).

<span id="download-and-inspect-cacerts" />

**Download and inspect cacerts**

This example downloads and converts the default response. Follow the [shared client setup](#before-you-begin) to set `EST_BASE` and prepare the credentials.

```bash
curl --fail-with-body --show-error --silent --max-time 30 \
  --cacert est-trust.pem \
  --dump-header cacerts.headers --output cacerts.b64 \
  "$EST_BASE/cacerts"
openssl base64 -d -in cacerts.b64 -out cacerts.p7b
openssl pkcs7 -inform DER -in cacerts.p7b -print_certs -quiet -out cacerts.pem
openssl crl2pkcs7 -nocrl -certfile cacerts.pem | openssl pkcs7 -print_certs -noout
```

Check fingerprints, issuers and dates against the [trust distribution](/docs/platform/iot-fleets/est/configuration#trust-distribution) policy. The response can contain a selection of CAs and Lamassu's TLS certificate. Do not turn the entire bundle into trusted roots or use it to authenticate its own initial download. HTTP 200 here does not prove that authentication or issuance works.

/simpleenroll [#simpleenroll]

`POST /simpleenroll` issues a device’s initial certificate from a CSR. Lamassu takes the device identifier from the CN and binds the issued certificate to the device identity. The private key stays on the client.

Configuration [#enrollment-configuration]

The following options are stored in `settings.enrollment_settings`.

<span id="enrollment-device-registration" />

**Registration mode**

`settings.enrollment_settings.registration_mode` accepts `JITP` or `PRE_REGISTRATION`. JITP creates an unknown device with the CSR CN as ID and the DMS as owner.

PRE\_REGISTRATION requires an existing ID. An existing device encounters replacement checks first, even without an identity. Review [preregistration conditions](/docs/platform/iot-fleets/enrollment/provisioning-strategies#preregistration-and-replacement) before using this mode.

<span id="device-provisioning-profile" />

**Device provisioning profile**

`settings.enrollment_settings.device_provisioning_profile` supplies tags, metadata and an icon for JITP registration.

<span id="enrollment-settings" />

**Protocol**

`protocol`. `EST_RFC7030` for these operations.

<span id="issuing-ca" />

**Issuing CA**

`enrollment_ca`. ID of the signing CA.

<span id="csr-signature-verification" />

**CSR signature verification**

`verify_csr_signature`. Keep `true` to verify CSR key possession.

<span id="certificate-replacement" />

**Certificate replacement**

`enable_replaceable_enrollment`. Allows `/simpleenroll` for an existing ID in the same DMS. It can attempt previous certificate revocation even if a later phase fails; this is not atomic.

<span id="authentication-mode" />

**Authentication mode**

`est_rfc7030_settings.auth_mode`. Select an [authentication mode](#authentication-per-operation) for initial enrollment.

Initial enrollment rejects an ID owned by another DMS. Do not automatically enable replacement in response to an error; [Troubleshooting](/docs/platform/iot-fleets/est/troubleshooting) distinguishes repeated IDs, ownership and partial changes.

<span id="issuance-profile" />

**Issuance profile**

`settings.issuance_profile_id` takes precedence over `settings.issuance_profile`; without either, the CA default profile is used. The resolved profile (including the CA default used as fallback when the DMS defines none) must define an end-entity certificate: a `Sign as CA` profile is rejected at enrollment and re-enrollment time. Rules are documented once in [Profiles](/docs/platform/pki/certificate-profiles). DMS changes affect future requests; they do not modify signed certificates or install client trust.

Request and Response [#simpleenroll-request-and-response]

Send `Content-Type: application/pkcs10` with a Base64-encoded DER PKCS#10 CSR in the body. Lamassu decodes the body directly as Base64. Send the encoded CSR as the entire body.

* **Default response.** `Content-Type: application/pkcs7-mime; smime-type=certs-only` and `Content-Transfer-Encoding: base64`. The PKCS#7 contains the issued certificate. Retrieve the CA certificates you need to validate its chain separately.
* **PEM response.** Send exactly `Accept: application/x-pem-file` to receive the certificate in PEM with `Content-Type: application/x-pem-file`.

<span id="initial-enrollment-example" />

Follow the [shared client setup](#before-you-begin) to set `EST_BASE` and prepare the credentials.

<span id="prepare-the-csr" />

**Prepare the CSR**

The example generates a new EC P-256 key and uses `est-device-001`, which must be available if the DMS registers automatically. The `Common Name` becomes the device identifier. Check that the profile permits the selected key and subject.

```bash
test ! -e device.key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out device.key
openssl req -new -sha256 -key device.key -subj '/CN=est-device-001' -out device.csr
openssl req -in device.csr -verify -noout
openssl req -in device.csr -outform DER -out device.csr.der
openssl base64 -A -in device.csr.der -out device.csr.b64
```

An implementation using hardware or its own store must produce the CSR through its resident key. `simpleenroll` sends the request and retains the key in the client. Honor Extensions does not authorize every requested attribute: see [Profiles](/docs/platform/pki/certificate-profiles).

<span id="request-the-identity" />

**Request the identity**

With initial `CLIENT_CERTIFICATE` authentication, send the Base64-encoded DER CSR using `Content-Type: application/pkcs10`:

```bash
curl --fail-with-body --show-error --silent --max-time 30 \
  --cacert est-trust.pem --cert bootstrap.crt --key bootstrap.key \
  --header 'Content-Type: application/pkcs10' \
  --data-binary @device.csr.b64 \
  --dump-header enroll.headers --output enroll.b64 \
  "$EST_BASE/simpleenroll"
openssl base64 -d -in enroll.b64 -out enroll.p7b
openssl pkcs7 -inform DER -in enroll.p7b -print_certs -quiet -out device.crt
```

Stop if curl fails. Retain the HTTP code, headers and body for diagnosis; an error response is not decoded as a certificate. The Bash example stops before that conversion. A timeout leaves the operation's result to be checked in Lamassu: do not automatically repeat issuance.

<span id="check-and-install-the-result" />

For a root that issues directly:

```bash
openssl verify -CAfile device-root.pem -purpose sslclient device.crt
openssl x509 -in device.crt -noout -subject -issuer -serial -dates -text
openssl x509 -in device.crt -pubkey -noout > certificate-public.pem
openssl pkey -pubin -in certificate-public.pem -outform DER -out certificate-public.der
openssl pkey -in device.key -pubout -outform DER -out key-public.der
cmp certificate-public.der key-public.der
```

Also verify that the CN is correct, the certificate is a leaf, its uses permit your application and its dates satisfy the profile. `cmp` must exit with code 0. With intermediates, provide the chain through `-untrusted` as described in [PKI validation](/docs/platform/pki/certificate-validation).

Query the device: the owning DMS, current serial number and history must match the result. Protect the key/certificate pair and install both using the device's mechanism. Association in Lamassu does not install files in the client. Check a real connection before considering the process complete.

<span id="next-steps" />

/simplereenroll [#simplereenroll]

`POST /simplereenroll` issues a successor certificate for an active identity. The client keeps the device identifier and can request the certificate with a new key.

Configuration [#re-enrollment-configuration]

The following options are stored in `settings.reenrollment_settings`.

<span id="renewal-authentication" />

**Renewal authentication**

`est_rfc7030_settings.auth_mode` controls how the client authenticates for renewal. See [Authentication per operation](#authentication-per-operation).

<span id="renewal-window" />

**Renewal window**

`reenrollment_delta`. Opens the window at the active certificate’s `NotAfter` minus this delta.

<span id="preventive-threshold" />

**Preventive threshold**

`preventive_delta`. Preventive operational monitoring threshold.

<span id="critical-threshold" />

**Critical threshold**

`critical_delta`. Critical operational monitoring threshold.

<span id="renewal-with-an-expired-certificate" />

**Renewal with an expired certificate**

`enable_expired_renewal`. Accepts an expired presented certificate in the renewal mTLS validator. Does not authorize another mode or remove Gateway constraints by itself.

<span id="renewal-validation-cas" />

**Renewal validation CAs**

`est_rfc7030_settings.client_certificate_settings.validation_cas`. Re-enrollment validation CAs for the renewal mTLS credential, tried after the enrollment CA; optional, because the enrollment CA is always trusted. Typically populated during CA rotation while old-CA cohorts renew.

<span id="previous-certificate-revocation" />

**Previous certificate revocation**

`revoke_on_reenrollment`. If the previous certificate is ACTIVE, attempts Superseded revocation before binding its successor.

Monitoring does not renew: the client must schedule the request and installation. Webhook and NO\_AUTH modes do not use the same mTLS expired-credential validator; the webhook must explicitly authorize permitted recovery. Review [renewal and recovery](#recover-according-to-state) for operation order and partial failures.

Request and Response [#simplereenroll-request-and-response]

Use the same [CSR format and headers](#simpleenroll-request-and-response) as `simpleenroll`. The response contains the successor certificate in Base64-encoded DER PKCS#7, or in PEM if you send exactly `Accept: application/x-pem-file`.

With certificate authentication, Lamassu requires the credential’s CN to match the CSR’s CN and compares the requested subject with the current certificate. The DMS rejects a revoked current certificate or a request made before the renewal window. See [authentication per operation](#authentication-per-operation) for accepted CAs, expiry and revocation checks.

<span id="renewal-example" />

<span id="prepare-renewal" />

**Prepare renewal**

* Query the current certificate in Lamassu and compare it with the installed certificate. You need its subject, serial and dates, as well as the client key.
* Check the **re-enrollment** authentication mode: it is independent of initial authentication. With `CLIENT_CERTIFICATE`, use the current identity; do not assume the bootstrap credential is admitted.
* Calculate the window's start: the current certificate's `NotAfter` minus `reenrollment_delta`. Preventive and critical thresholds produce states/notifications; they do not extend that window.
* Review **Revoke on Re-enrollment** and recovery if installation fails. When enabled, Lamassu can revoke the previous identity before the client installs the new one.

<span id="request-the-successor-certificate" />

**Request the successor certificate**

The example continues the [EST tutorial](/docs/platform/iot-fleets/quickstarts/enroll-device), in the same Bash session with `set -euo pipefail`, `umask 077` and `EST_BASE`. Use a new key compatible with the profile. Conversion from the certificate preserves the subject and copies only SAN when present; check the subject and requested names before sending it. The backend checks the subject against the current identity: it attempts RawSubject equality and then compares CN, OU, O, L, ST and C. Rebuilding only the CN can lose required attributes.

```bash
test ! -e device.next.key
test ! -e device.next.crt
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out device.next.key
openssl x509 -x509toreq -in device.crt -key device.next.key -sha256 \
  -copy_extensions copy -ext subjectAltName -out device-renewal.csr
openssl req -in device-renewal.csr -verify -noout -subject
openssl req -in device-renewal.csr -outform DER -out device-renewal.csr.der
openssl base64 -A -in device-renewal.csr.der -out device-renewal.csr.b64
curl --fail-with-body --show-error --silent --max-time 30 \
  --cacert est-trust.pem --cert device.crt --key device.key \
  --header 'Content-Type: application/pkcs10' \
  --data-binary @device-renewal.csr.b64 \
  --dump-header renewal.headers --output renewal.b64 \
  "$EST_BASE/simplereenroll"
openssl base64 -d -in renewal.b64 -out renewal.p7b
openssl pkcs7 -inform DER -in renewal.p7b -print_certs -quiet -out device.next.crt
openssl verify -CAfile device-root.pem -purpose sslclient device.next.crt
openssl x509 -in device.next.crt -noout -subject -issuer -serial -dates
openssl x509 -in device.next.crt -pubkey -noout > next-certificate-public.pem
openssl pkey -pubin -in next-certificate-public.pem -outform DER -out next-certificate-public.der
openssl pkey -in device.next.key -pubout -outform DER -out next-key-public.der
cmp next-certificate-public.der next-key-public.der
```

The request authenticates with `device.crt` and `device.key`; the CSR contains the new public key. Also check extensions, dates and correspondence of the serial with the current slot in Lamassu. Do not resubmit a failed request without querying that state: issuance, previous revocation and successor binding can have partial results.

<span id="install-and-check-the-new-pair" />

Keep the result as `device.next.crt` and `device.next.key` until verified. Switch the pair through a coordinated operation in the device store or configuration; avoid temporarily exposing a certificate with another version's key.

Test mTLS with the consumer and verify that it uses the new serial. Confirm the history and current certificate in Lamassu. If **Revoke on Re-enrollment** was disabled, the previous identity can remain valid: retire it according to PKI policy after testing the successor, and check revocation publication and consumption.

If the previous identity is already revoked, retaining its files does not restore a valid connection. Recovery requires an admitted credential and authorized intervention according to the situation.

Recover according to state [#recover-according-to-state]

| Situation                                 | Procedure                                                                                                                                                                          |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Valid certificate, outside the window     | Schedule the request within the window. Do not use `simpleenroll` to bypass it.                                                                                                    |
| Expired certificate, key available        | With certificate authentication, review `enable_expired_renewal` and whether Gateway permits presenting that credential. Revocation, subject and the remaining checks still apply. |
| Renewal through webhook or `NO_AUTH`      | The mTLS expiry check does not run in these modes. Define expiry and authorization policy in the corresponding admission process; the flag is not a universal prohibition.         |
| Lost or inaccessible key                  | You cannot prove possession of the previous identity. Authorize new admission and, if appropriate, controlled replacement; revoke the compromised identity.                        |
| Current identity revoked                  | `simplereenroll` rejects the revoked current certificate. Investigate the reason and prepare an authorized readmission procedure; do not disable authentication to force it.       |
| Device without an identity                | Use initial enrollment. For an existing entry, check the replacement restriction in [provisioning](/docs/platform/iot-fleets/enrollment/provisioning-strategies).                  |
| Retired device                            | Review the operational decision before readmission. Decommissioned state and revocation of the entire history are not equivalent.                                                  |
| Timeout, HTTP 500 or installation failure | Inspect the device, issued certificates and history before retrying. A successor may have been issued or the previous identity revoked.                                            |

Continuous operation [#continuous-operation]

Schedule renewal with time for disconnections, trust distribution and consumer checks. Stagger requests across the population and bound retries within the window; authentication, subject and policy errors require correcting their cause. Maintain an admitted and tested recovery mechanism for lost keys and pairs that could not be installed.

Continue with [Trust distribution](/docs/platform/iot-fleets/est/configuration#trust-distribution), [Devices and identities](/docs/platform/iot-fleets/device-management) and [Troubleshooting](/docs/platform/iot-fleets/est/troubleshooting).

/serverkeygen [#serverkeygen]

`POST /serverkeygen` generates a software key in Lamassu, rebuilds the CSR with that key and performs initial enrollment. The client receives the private key and certificate.

Configuration [#serverkeygen-configuration]

`settings.server_keygen_settings` controls key generation. The operation applies the [initial enrollment policy](#enrollment-configuration). Before testing with a registered ID, check whether the policy allows certificate replacement.

<span id="enable-key-generation" />

**Enable key generation**

`enabled` turns on the operation. The console shows an **Enable server-side key generation** switch. When disabled, the console omits the `key` field.

<span id="key-type" />

**Key type**

`key.type` selects RSA or ECDSA in **Key type**. The issuance profile must allow the selected algorithm and size.

<span id="key-size" />

**Key size**

`key.bits` is the modulus size for RSA or the curve for ECDSA. The console offers 2048, 3072 or 4096 bits for RSA, defaulting to 4096, and P-256, P-384 or P-521 for ECDSA, defaulting to P-256.

For ECDSA, the service also recognizes 224, 256, 384 and 521 as P-224, P-256, P-384 and P-521. An unrecognized value selects P-256. Choose a compatible size and check the resulting key.

Request and Response [#serverkeygen-request-and-response]

Send a Base64-encoded DER PKCS#10 CSR with `Content-Type: application/pkcs10`. The response uses this operation’s multipart format even if `Accept` asks for PEM. Lamassu generates the key in software even when the CA signs with an HSM-backed key.

<span id="response-format" />

**Response format**

The body is **MIME multipart/mixed**, with the boundary specified in `Content-Type`. It contains two parts:

| Part                                            | Content after decoding its Base64             |
| ----------------------------------------------- | --------------------------------------------- |
| `application/pkcs8`                             | Unencrypted DER PKCS#8 private key.           |
| `application/pkcs7-mime; smime-type=certs-only` | DER PKCS#7 containing the issued certificate. |

The controller also adds `Content-Transfer-Encoding: base64` to the outer header, although the outer body is MIME text. **Do not Base64-decode the entire body.** Read the actual boundary and decode each part according to its headers.

<span id="request-and-extraction" />

**Example request**

In a Bash session with `set -euo pipefail` and `umask 077`, use `EST_BASE` and the trust/bootstrap files from [client setup](#before-you-begin). Select an available and admitted `est-serverkeygen-001`. The `server-request.key` only signs the input CSR; the received identity uses the server-generated key.

```bash
test ! -e server-request.key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server-request.key
openssl req -new -sha256 -key server-request.key \
  -subj '/CN=est-serverkeygen-001' -out serverkeygen.csr
openssl req -in serverkeygen.csr -outform DER -out serverkeygen.csr.der
openssl base64 -A -in serverkeygen.csr.der -out serverkeygen.csr.b64
curl --fail-with-body --show-error --silent --max-time 30 \
  --cacert est-trust.pem --cert bootstrap.crt --key bootstrap.key \
  --header 'Content-Type: application/pkcs10' \
  --data-binary @serverkeygen.csr.b64 \
  --dump-header serverkeygen.headers --output serverkeygen.mime \
  "$EST_BASE/serverkeygen"
```

<span id="extraction-and-verification" />

Process the MIME parts according to their headers and verify that the received key matches the certificate. Inspect the CN, serial, dates and uses, and check the association in Lamassu before installing. Protect files containing the key and remove temporary copies according to the device storage mechanism.
