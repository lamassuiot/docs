EST in Lamassu

Configure EST operations, authentication and trust distribution.

Each DMS exposes the EST operations its devices use to obtain and renew their identity. This page describes the routes, how each operation authenticates, the DMS settings that govern each endpoint and request examples with curl and OpenSSL. To create and manage the DMS, see the DMS guide; to prepare the device's credentials and initial trust, see Authentication and trust.

Endpoint reference

Each DMS publishes its operations at /.well-known/est/{APS}/{operation}, where APS is the DMS ID, not its display name. Gateway configuration determines the public host and route. The router also admits routes without the APS segment, but the controller requires it, so do not use them.

OperationMethodAuthentication and condition
/cacertsGETNo EST credential required; HTTPS and infrastructure controls still apply.
/simpleenrollPOSTInitial authentication and DMS registration and replacement policy.
/simplereenrollPOSTRenewal authentication, existing identity, subject, revocation and window.
/serverkeygenPOSTInitial authentication and server-side key generation enabled.

Lamassu does not implement /csrattrs or /fullcmc. There is no native JWT EST authentication mode either; a webhook can interpret a request credential according to its own contract.

Authentication per operation

The DMS authenticates the request before it applies registration and issuance rules. Each operation reads its authentication from its own est_rfc7030_settings block:

  • settings.enrollment_settings.est_rfc7030_settings for /simpleenroll and /serverkeygen.
  • settings.reenrollment_settings.est_rfc7030_settings for /simplereenroll.

The two blocks are stored independently and neither inherits from the other, so read both before editing. auth_mode accepts these values:

auth_modeControl applied in the configured operation
CLIENT_CERTIFICATEPresented certificate validation.
EXTERNAL_WEBHOOKConfigured webhook authorization.
CLIENT_CERTIFICATE_AND_EXTERNAL_WEBHOOKCertificate validation followed by webhook approval.
NO_AUTHNo DMS requester authentication.

Webhook modes also run during re-enrollment when configured in its block. An absent or unrecognized mode makes the operation fail: there is no implicit downgrade to NO_AUTH. NO_AUTH does not establish ownership of the requested ID.

Client certificate

The certificate modes read client_certificate_settings in the same block:

FieldDescription
validation_casIDs of the CAs the presented certificate is validated against. The first one that validates it is used.
allow_expiredAllow expired certificates: accepts expired certificates in initial enrollment.
chain_level_validationWhen greater than 0, only that many certificates of the presented chain are validated.
allow_unverifiable_revocationAllow certificates without revocation information: accepts certificates without revocation information; false by default.

The validator receives one certificate credential; the flow does not guarantee forwarding every handshake intermediate to it. For a direct case, configure the bootstrap’s direct issuer as validation CA and test the actual Gateway path.

Revocation. In initial enrollment the client certificate and every intermediate CA between it and the validation CA are checked, each against its issuer; extra certificates the device sends in the handshake are ignored. Certificates managed by Lamassu are checked against their stored status, and external ones through their OCSP and CRL endpoints. The operation fails closed when revocation cannot be verified: unreachable endpoints, stale or invalid evidence and inconclusive statuses always reject the certificate. A validation CA that is revoked in Lamassu also rejects the operation, without falling back to the remaining validation CAs. Revocation and checks details the evidence the endpoints must present.

allow_unverifiable_revocation relaxes a single case: a certificate, or an intermediate CA of the chain, that Lamassu does not manage and that lists no OCSP or CRL endpoint. With the option on, that certificate is accepted even if it is revoked, and the console shows the warning Revocation will not be verified. The option is set separately in the enrollment and re-enrollment blocks, and it is off in DMSs created before it existed.

Re-enrollment. The validator tries the enrollment CA first and then the re-enrollment block's validation_cas. That list is optional because the enrollment CA is always trusted, and CAs listed only in the initial block's validation_cas do not extend re-enrollment acceptance: during a CA rotation, add the old issuance CA to the re-enrollment block's list. The validator compares only the presented TLS leaf against those CAs and checks only its revocation. In this block chain_level_validation and allow_expired are stored but not consulted; expiry is governed by enable_expired_renewal.

External webhook settings

The webhook modes read external_webhook_settings in the same est_rfc7030_settings block. These settings define the destination, method, timeout and how Lamassu authenticates to the receiver; the webhook contract describes the device credential, the request body and the expected response.

external_webhook_settings fieldDecision
urlAbsolute http or https URL of the receiver. It must be the final URL; redirects are not followed.
methodPOST or PUT; POST by default.
nameLabel used in service logs.
config.auth_modenoauth, apikey, jwt or mtls. An absent or unknown value behaves as noauth.
config.log_levelLog level of the webhook call: debug, info, warn or error; info by default.
config.apikey_optionsRequired for apikey: header and key. Reserved header names are rejected.
config.jwt_optionsRequired for jwt: oidc_client_id, oidc_client_secret and an absolute http or https oidc_well_known.
config.mtls_optionsRequired for mtls: cert_content and key_content as Base64-encoded PEM, like certificates elsewhere in the API; plain PEM is also accepted.
config.insecure_skip_verifySkips verification of the receiver certificate when true. Verification is on by default. Unlike alert channels, this flag is honored here.
config.call_timeoutMaximum duration of the authorization call (for example 10s); 10 seconds by default.

Creating or updating a DMS that uses the webhook in any of its blocks validates this configuration. When it is invalid, the response is HTTP 400, with a body that starts with struct validation error: and continues with invalid enrollment external webhook config or invalid reenrollment external webhook config. These rules apply:

  • The URL, method and options must be valid, and mtls_options.cert_content and key_content must decode to a matching certificate and private key.
  • File references (ca_cert_file, mtls_options.cert_file, mtls_options.key_file) are never valid, because the service does not read files. Enter the certificate and key as PEM, Base64-encoded or plain, in cert_content and key_content.
  • A custom apikey_options.header may not use names that the platform or the receiving service trusts (for example X-Principal-Id, X-Request-Id, Host, Content-Type or Forwarded), and no name may start with X-Forwarded-, X-Envoy- or X-Lms- (case-insensitive). The DMS API reference documents the WebhookCall and WebhookCallHttpClient schemas.
  • With config.auth_mode set to apikey, jwt or mtls, the body must carry its option block (apikey_options, jwt_options or mtls_options) and no other. The legacy apikey, oidc and mtls names fail validation, and validate_server_cert is ignored: use insecure_skip_verify. Only bodies without option blocks are accepted as noauth, and their credentials are dropped.
  • The http_client key belongs to alert channels; in a DMS body it is ignored. The DMS configuration goes in external_webhook_settings.config.

Credentials over http://

With credentials configured, they are sent regardless of the URL scheme: an http:// webhook receives the API key or bearer token in cleartext, and mTLS has no effect because no TLS handshake takes place, so the client certificate is never presented. Prefer https:// for url, oidc_well_known and the token endpoint it advertises.

The console exposes independent editors for the enrollment and re-enrollment authentication, with the same Log Level, Call Timeout, HTTP Authentication and credential fields as the webhook channels, plus a Skip TLS Verification switch (insecure_skip_verify, off by default; the console warns when you enable it). The editor rejects file paths in the certificate and key fields, and saving rewrites external_webhook_settings.config with the current keys and the material Base64-encoded. Configurations migrated from 3.8.0 that referenced files or relied on validate_server_cert: false need fixing; see DMS webhooks.

Before you begin

For an end-to-end first enrollment, follow Enroll and connect your first device.

The examples on this page need the public HTTPS DMS URL, server trust obtained through an approved channel, the operation's authentication mode and an admitted identifier. They use Bash, curl with --fail-with-body and OpenSSL 3.x (openssl-pkcs7 to extract certificates and openssl-x509 to prepare renewal); work in a private directory. If you integrate a generic EST client, first check the Lamassu specifics described for each operation, such as the PEM response or the multipart format of /serverkeygen.

Prepare est-trust.pem to verify the EST server, bootstrap.crt and bootstrap.key for initial certificate authentication, and device-root.pem as the approved root of the device issuer. The two trust files can contain different roots. For another authentication mode, adapt the credentials according to Authentication and trust. When a request fails, retain the HTTP code, headers and body before decoding anything. A 500 does not mean a transient failure: service denials return it too. Troubleshooting explains how to interpret them.

/cacerts

GET /cacerts retrieves the certificates published by the DMS. The client can inspect the bundle and use approved certificates to build trust chains.

Configuration

settings.ca_distribution_settings determines which certificates /cacerts returns:

FieldContent it adds
include_system_ca (Include Lamassu System CA)The available downstream TLS certificate. It can be a leaf, not an issuing CA.
include_enrollment_ca (Include Enrollment CA)The selected enrollment CA certificate.
managed_cas (Managed CAs)The explicitly selected CA certificates.

The DMS does not add the ancestors of those CAs: selecting the enrollment CA does not publish its root or intermediates, which must be selected in Managed CAs. The set may contain leaves, roots and intermediates, including more than one hierarchy during a migration. A certificate's position does not define the chain: identify certificates by subject, issuer, AKI/SKI, signature and constraints.

Request and response

Send an HTTPS GET with an empty body and no EST credential. Gateway controls still apply.

  • Default response. Content-Type: application/pkcs7-mime; smime-type=certs-only and Content-Transfer-Encoding: base64. The body is Base64-encoded DER PKCS#7 with lines of up to 76 characters.
  • PEM response. Lamassu selects this format when Accept is exactly application/x-pem-file and returns the same value in Content-Type. The body contains the certificates in PEM.

Example

This example downloads the default response and converts it to PEM. It uses EST_BASE and est-trust.pem from Before you begin.

Check fingerprints, issuers and dates against the distribution configuration. Do not turn the entire bundle into trusted roots or use it to authenticate its own initial download. HTTP 200 here does not prove that authentication or issuance works.

/simpleenroll

POST /simpleenroll issues a device’s initial certificate from a CSR. Lamassu takes the device identifier from the CN and binds the issued certificate to the device identity. The private key stays on the client.

Configuration

The initial enrollment options are stored in settings.enrollment_settings:

FieldDescription
protocolEST_RFC7030 for these operations.
enrollment_caID of the CA that signs the certificates.
registration_modeJITP creates an unknown device with the CSR CN as ID and the DMS as owner. PRE_REGISTRATION requires the ID to exist beforehand.
device_provisioning_profileTags, metadata and icon a device registered through JITP receives.
enable_replaceable_enrollmentAllows /simpleenroll for an existing ID in the same DMS.
verify_csr_signature (Verify CSR signature)Verifies possession of the CSR key. Keep it true.
est_rfc7030_settingsInitial enrollment authentication; see Authentication per operation.

Registration and replacement. With PRE_REGISTRATION, an existing device goes through the replacement check first, even without an identity; review the preregistration conditions before using this mode. Initial enrollment rejects an ID owned by another DMS. Replacement can attempt to revoke the previous certificate even if a later phase fails: it is not atomic. Do not enable it as an automatic response to an error; Troubleshooting distinguishes repeated IDs, ownership and partial changes.

Issuance profile. The profile is defined in settings, not in enrollment_settings, and applies to all three operations that issue certificates. settings.issuance_profile_id takes precedence over settings.issuance_profile; without either, the CA default profile is used. The resolved profile must define an end-entity certificate: a Sign as CA profile is rejected at enrollment and re-enrollment time. The rules are documented in Profiles. DMS changes affect future requests; they do not modify signed certificates or install client trust.

Request and response

Send Content-Type: application/pkcs10 with a Base64-encoded DER PKCS#10 CSR in the body. Lamassu decodes the body directly as Base64, with no PEM or JSON wrapper.

  • Default response. Content-Type: application/pkcs7-mime; smime-type=certs-only and Content-Transfer-Encoding: base64. The PKCS#7 contains the issued certificate. Retrieve the CA certificates you need to validate its chain separately.
  • PEM response. Send exactly Accept: application/x-pem-file to receive the certificate in PEM with Content-Type: application/x-pem-file.

Example

The example uses initial CLIENT_CERTIFICATE authentication and the files from Before you begin.

  1. Prepare the CSR. The example generates a new EC P-256 key and uses est-device-001, which must be available if the DMS registers automatically. The Common Name becomes the device identifier. Check that the profile permits the selected key and subject.

An implementation using hardware or its own store must produce the CSR through its resident key. Honor Extensions does not authorize every requested attribute: see Profiles.

If curl fails, the example stops before decoding: an error response is not a certificate. A timeout leaves the operation's result to be checked in Lamassu, so do not automatically repeat issuance.

  1. Check and install the result. For a root that issues directly:

/simplereenroll

POST /simplereenroll issues a successor certificate for an active identity. The client keeps the device identifier and can request the certificate with a new key.

Configuration

The renewal options are stored in settings.reenrollment_settings:

FieldDescription
est_rfc7030_settingsRe-enrollment authentication, independent of the initial one; see Authentication per operation.
est_rfc7030_settings.client_certificate_settings.validation_casRe-enrollment validation CAs, tried after the enrollment CA. Optional; typically populated during a CA rotation while devices with old-CA certificates renew.
reenrollment_deltaThe renewal window opens at the active certificate’s NotAfter minus this delta.
preventive_deltaPreventive monitoring threshold. Produces states and notifications; it does not extend the window.
critical_deltaCritical monitoring threshold. Produces states and notifications; it does not extend the window.
enable_expired_renewal (Allow expired renewal)Accepts an expired presented certificate in the renewal mTLS validator. Does not authorize another mode or remove Gateway constraints by itself.
revoke_on_reenrollment (Revoke on Re-enrollment)If the previous certificate is ACTIVE, attempts to revoke it with reason Superseded before binding its successor.

The legacy flat field reenrollment_settings.additional_validation_cas is not part of the API: it is ignored without error, so an update body built with it empties validation_cas. Read the DMS before editing it through the API.

Monitoring does not renew: the client must schedule the request and installation with time for disconnections, trust distribution and consumer checks. Stagger requests across the population and bound retries within the window; authentication, subject and policy errors require correcting their cause. Maintain an admitted and tested recovery mechanism for lost keys and pairs that could not be installed; see Recover according to state.

Request and response

Use the same CSR format and headers as simpleenroll. The response contains the successor certificate in Base64-encoded DER PKCS#7, or in PEM if you send exactly Accept: application/x-pem-file.

With certificate authentication, Lamassu requires the credential’s CN to match the CSR’s CN and compares the requested subject with the current certificate. The DMS rejects a revoked current certificate or a request made before the renewal window. Client certificate details accepted CAs, expiry and revocation checks.

Example

The example continues the initial enrollment in the same Bash session, with device.crt and device.key as the current identity.

  1. Prepare renewal. Before requesting the successor:
    • Query the current certificate in Lamassu and compare it with the installed certificate. You need its subject, serial and dates, as well as the client key.
    • Check the re-enrollment authentication mode: it is independent of initial authentication. With CLIENT_CERTIFICATE, use the current identity; do not assume the bootstrap credential is admitted.
    • Calculate the window's start: the current certificate's NotAfter minus reenrollment_delta.
    • Review Revoke on Re-enrollment. When enabled, Lamassu can revoke the previous identity before the client installs the new one.
  1. Request the successor certificate. The request authenticates with device.crt and device.key, and the CSR contains a new key compatible with the profile. Conversion from the certificate preserves the subject and copies only SAN when present; check the subject and requested names before sending it. The backend checks the subject against the current identity: it attempts RawSubject equality and then compares CN, OU, O, L, ST and C, so rebuilding only the CN can lose required attributes.

Also check extensions, dates and that the serial matches the current slot in Lamassu. Do not resubmit a failed request without querying that state: issuance, previous revocation and successor binding can have partial results.

  1. Install and check the new pair. Keep the result as device.next.crt and device.next.key until verified. Switch the pair through a coordinated operation in the device store or configuration; avoid temporarily exposing a certificate with another version's key.

Test mTLS with the consumer and verify that it uses the new serial. Confirm the history and current certificate in Lamassu. If Revoke on Re-enrollment was disabled, the previous identity can remain valid: retire it according to PKI policy after testing the successor, and check revocation publication and consumption.

Recover according to state

SituationProcedure
Valid certificate, outside the windowSchedule the request within the window. Do not use simpleenroll to bypass it.
Expired certificate, key availableWith certificate authentication, review enable_expired_renewal and whether Gateway permits presenting that credential. Revocation, subject and the remaining checks still apply.
Renewal through webhook or NO_AUTHThe mTLS expiry check does not run in these modes. Define expiry and authorization policy in the corresponding admission process; the webhook must explicitly authorize the recovery it permits.
Lost or inaccessible keyYou cannot prove possession of the previous identity. Authorize new admission and, if appropriate, controlled replacement; revoke the compromised identity.
Current identity revokedsimplereenroll rejects the revoked current certificate, and retaining its files does not restore a valid connection. Investigate the reason and prepare an authorized readmission procedure; do not disable authentication to force it.
Device without an identityUse initial enrollment. For an existing entry, check the replacement restriction in provisioning.
Retired deviceReview the operational decision before readmission. Decommissioned state and revocation of the entire history are not equivalent.
Timeout, HTTP 500 or installation failureInspect the device, issued certificates and history before retrying. A successor may have been issued or the previous identity revoked.

/serverkeygen

POST /serverkeygen generates a software key in Lamassu, rebuilds the CSR with that key and performs initial enrollment. The client receives the private key and certificate.

Configuration

settings.server_keygen_settings controls key generation. The rest of the operation applies the initial enrollment configuration; before testing with a registered ID, check whether that configuration allows certificate replacement.

FieldDescription
enabled (Enable server-side key generation)Turns on the operation. With the operation disabled, the console omits the key field.
key.type (Key type)RSA or ECDSA. The issuance profile must allow the selected algorithm and size.
key.bitsModulus size for RSA or curve for ECDSA. The console offers 2048, 3072 or 4096 bits for RSA (default 4096) and P-256, P-384 or P-521 for ECDSA (default P-256).

For ECDSA, the service also recognizes 224, 256, 384 and 521 as P-224, P-256, P-384 and P-521, and an unrecognized value selects P-256. Choose a compatible size and check the resulting key.

Request and response

Send a Base64-encoded DER PKCS#10 CSR with Content-Type: application/pkcs10. The response uses this operation’s multipart format even if Accept asks for PEM. Lamassu generates the key in software even when the CA signs with an HSM-backed key.

The body is MIME multipart/mixed, with the boundary specified in Content-Type, and contains two parts:

PartContent after decoding its Base64
application/pkcs8Unencrypted DER PKCS#8 private key.
application/pkcs7-mime; smime-type=certs-onlyDER PKCS#7 containing the issued certificate.

The controller also adds Content-Transfer-Encoding: base64 to the outer header, although the outer body is MIME text. Do not Base64-decode the entire body. Read the actual boundary and decode each part according to its headers.

Example

The example uses EST_BASE and the trust and bootstrap files from Before you begin. Choose an available and admitted ID, such as est-serverkeygen-001. The server-request.key only signs the input CSR; the received identity uses the server-generated key.

Process the MIME parts according to their headers and verify that the received key matches the certificate. Inspect the CN, serial, dates and uses, and check the association in Lamassu before installing. Protect files containing the key and remove temporary copies according to the device storage mechanism.
