# Fastlane (/docs/pr-preview/pr-26/deployment/self-hosted/fastlane)



Fastlane - Despliegue automatizado en Kubernetes [#fastlane---despliegue-automatizado-en-kubernetes]

Esta sección documenta el script `scripts/lamassu-fast-lane.sh`, cuyo objetivo es desplegar de forma automatizada una pila completa de Lamassu PKI sobre un clúster Kubernetes ya existente, con intervención manual mínima.

La instalación incluye:

* PostgreSQL
* Keycloak
* RabbitMQ
* Chart Helm de Lamassu

<div className="lm-diff-ins lm-diff-block">
  De forma opcional, también puede desplegar un backend HSM con soporte PKCS#11 (`--with-hsm`) y una pila de observabilidad con OpenTelemetry (`--otel`). El orden de ejecución es: PostgreSQL → Keycloak → RabbitMQ → observabilidad (opcional) → SoftHSM/NetHSM (opcional) → Lamassu → datos de ejemplo (opcional).
</div>

Detección de distribución Kubernetes [#detección-de-distribución-kubernetes]

La función `detect_distribution` identifica la distribución con el siguiente orden de prioridad:

1. `microk8s`
2. `k3s`
3. `kind`
4. Kubernetes estándar

Comportamientos específicos:

* En `microk8s`, los comandos se ejecutan con prefijos `microk8s kubectl` y `microk8s helm`.
* En `kind`, el script muestra una advertencia de uso exclusivo para pruebas.

</div>

  Con `--otel`, antes de Lamassu se despliega una pila de trazas y logs en el mismo namespace:
</div>

  * **VictoriaLogs** (`vm/victoria-logs-single`, release `victoria-logs`) y **VictoriaTraces** (`vm/victoria-traces-single`, release `victoria-traces`), sin volumen persistente.

</div>

<div className="lm-diff-ins lm-diff-block">
  SoftHSM y NetHSM (--with-hsm) [#softhsm-y-nethsm---with-hsm]
</div>

<div className="lm-diff-ins lm-diff-block">
  La opción `--with-hsm` configura el KMS de Lamassu para usar PKCS#11. El flujo tiene tres pasos:
</div>

<div className="lm-diff-ins lm-diff-block">
  1. **Preparación de credenciales SSH**: el script genera un par de claves SSH ed25519 con `ssh-keygen` y lo usa para el reenvío del socket PKCS#11.
  2. **Instalación del chart de SoftHSM**: se despliega el release `hsm` desde la ruta indicada en `--softhsm-chart-path` (por defecto `./charts/softhsm`), con los PIN, slot y token preconfigurados y la clave pública SSH autorizada.
  3. **Configuración de Lamassu**: se crea el secret `kms-pkcs11-sidecar-ssh-key` con la clave privada y se fusionan en el `values` de Lamassu tres bloques: `kms.pkcs11Sidecar` (sidecar `p11-kit-ssh-sidecar` que expone el socket PKCS#11 en un volumen compartido), `kms.pkcs11Modules` (init containers que preparan los módulos PKCS#11 en volúmenes compartidos: `p11-kit-client` siempre y `nethsm` solo cuando se despliega NetHSM) y `kms.cryptoEngines` (motor `pkcs11-softhsm` como motor por defecto, `pkcs11-nethsm` si NetHSM está habilitado y `filesystem-1`).
</div>

<div className="lm-diff-ins lm-diff-block">
  NetHSM solo se despliega si todos los nodos del clúster admiten la arquitectura `amd64` (su imagen no existe para ARM). Antes de instalar, `detect_nethsm_support` consulta la arquitectura de cada nodo con `kubectl get nodes`:
</div>

<div className="lm-diff-ins lm-diff-block">
  * Clúster solo ARM (o sin ningún nodo `amd64`): se omite NetHSM y se despliega solo SoftHSM/PKCS#11.
  * Clúster mixto amd64 + ARM: NetHSM se restringe a los nodos amd64.
  * Arquitectura desconocida o no soportada: el script aborta sin desplegar NetHSM.
</div>

<div className="lm-diff-ins lm-diff-block">
  Para detalles del sidecar PKCS#11 y sus requisitos de Kubernetes, ver [SoftHSM como complemento opcional](/docs/deployment/self-hosted/overview#softhsm-como-complemento-opcional).
</div>

Lamassu (install_lamassu) [#lamassu-install_lamassu]

Se genera un archivo `lamassu.yaml` que se pasa a `helm install`.

Configuraciones principales:

* PostgreSQL: host `postgresql`, puerto `5432`<ins className="lm-diff-ins">; las mismas credenciales se reutilizan en `services.authz.credentials` para las bases de datos `pki` y `authz`</ins>
* AMQP: host `rabbitmq`, puerto `5672`, TLS deshabilitado
* CA: motor criptográfico `fs-1` de tipo `filesystem` (`/crypto/fs`); `--with-hsm` no lo modifica, reconfigura el KMS (`services.kms.cryptoEngines`), que pasa a usar PKCS#11 con `pkcs11-softhsm` como motor por defecto (y `pkcs11-nethsm` si se despliega NetHSM), conservando `filesystem-1`
* Autorización: principales bootstrap `oidc:lamassu` con la política `SUPER ADMIN` (claim `preferred_username=lamassu`); con `--sample-data` se añade `oidc:service-account-sample-data`
* OIDC JWKS:
  <del className="lm-diff-del">`http://auth-keycloak.<NAMESPACE>/auth/realms/lamassu/protocol/openid-connect/certs`</del><ins className="lm-diff-ins">`http://auth-keycloak.<NAMESPACE>.svc.cluster.local/auth/realms/lamassu/protocol/openid-connect/certs`</ins>
* Ruta adicional de gateway: <del className="lm-diff-del">`/auth -> auth-keycloak:8080`</del><ins className="lm-diff-ins">`/auth -> auth-keycloak:80`</ins>
* Direcciones de gateway: <del className="lm-diff-del">IP(s) obtenidas</del><ins className="lm-diff-ins">la IP indicada con `-ip/--gateway-ip` o, en su defecto, las IP(s) detectadas</ins> con `hostname -I`
* Puertos de gateway: desde `--https-port` y `--http-port`
* Dominios CA: valor de `--domain`
* Observabilidad: con `--otel`, `observability.enabled: true`

<del className="lm-diff-del">Cuando se ejecuta en modo online y</del><ins className="lm-diff-ins">Si</ins> no se usa <del className="lm-diff-del">`--local-chart-path`</del><ins className="lm-diff-ins">`-l/--local-chart-path`</ins>, el script añade el repositorio Helm:

```bash
helm repo add lamassuiot http://www.lamassu.io/lamassu-helm/
```

Después instala el release `lamassu` usando la versión indicada por `--version` si se ha proporcionado.

Si `--https-port` es distinto de `443`, el puerto se añade al dominio antes de escribirlo en `values`.

Salida tras la instalación [#salida-tras-la-instalación]

* URL de Lamassu UI: `https://<DOMAIN>`
* Credenciales iniciales: `lamassu / lamassu`
* Consola Keycloak: `https://<DOMAIN>/auth/admin`

```yaml

```

Este bootstrap está pensado para laboratorio, demos y CI. En producción, sustituye el principal por un rol o grupo administrado en tu proveedor OIDC y sigue [Control de acceso](/docs/platform/pki/access-control).

Uso en CI [#uso-en-ci]

El script está pensado también para validaciones rápidas y smoke tests locales. Tras la instalación puede ejecutarse:

```bash
helm test lamassu -n <namespace>
```

El chart incluye una prueba <del className="lm-diff-del">que valida conectividad contra </del><ins className="lm-diff-ins">de conectividad con el hook `helm test` (`<release>-connectivity-test`), que verifica los endpoints `/health` de </ins>`ca`, `dms-manager`, `device-manager`<del className="lm-diff-del">, </del><ins className="lm-diff-ins"> y </ins>`va`<ins className="lm-diff-ins">,</ins> y <del className="lm-diff-del">`ui`</del><ins className="lm-diff-ins">comprueba que la UI responde con el título `LamassuIoT Certificate Manager`</ins>.

Ejemplo:


* `-ns`: namespace específico
* `-d`: dominio de CI

Resumen [#resumen]

`lamassu-fast-lane.sh` proporciona un mecanismo totalmente automatizado para desplegar un entorno Lamassu funcional en Kubernetes en pocos minutos, integrando base de datos, autenticación, mensajería, gateway y TLS.

Está optimizado para rapidez, reproducibilidad y uso en entornos no productivos<del className="lm-diff-del">, con soporte para escenarios offline y pipelines de CI</del><ins className="lm-diff-ins"> y pipelines de CI; para despliegues productivos con requisitos propios (TLS corporativo, HSM, OIDC gestionado), usa un despliegue manual del chart con un `values.yaml` específico</ins>.
