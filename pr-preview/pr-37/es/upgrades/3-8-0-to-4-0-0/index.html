3.8.0 a 4.0.0

Qué cambia en 4.0.0 y qué comprobar después de actualizar desde 3.8.0.

Página nueva

Esta página recoge qué cambia entre 3.8.0 y 4.0.0 y qué comprobar después de aplicar la actualización. El comportamiento actual se documenta en las páginas correspondientes de cada funcionalidad.

DMS: autenticación de reenrolamiento independiente

Los ajustes de autenticación de reenrolamiento se almacenan independientes de la autenticación inicial. Después de actualizar, lee ambos bloques antes de editar un DMS. Si la versión de tu consola no expone los ajustes independientes, usa la API DMS.

DMS: formato de la configuración de webhook

Las configuraciones de webhook almacenadas se reescriben al formato actual: validate_server_cert pasa a ser el negado de insecure_skip_verify, oidc pasa a jwt_options, apikey pasa a apikey_options y mtls pasa a mtls_options. Cuando el certificado y la clave heredados son ambos PEM, se trasladan a mtls_options.cert_content y key_content y no requieren ninguna acción.

Revisa insecure_skip_verify en cada configuración migrada: una configuración con validate_server_cert: false pasa a insecure_skip_verify: true, así que la verificación del certificado del receptor sigue sin realizarse hasta que pongas ese flag a false. El canal de autorización del webhook lleva la API key o el bearer token, así que saltarse la verificación expone esas credenciales a un atacante con posición de red.

Una configuración mixta (certificado PEM, clave como ruta de archivo) pasa a mtls_options.cert_file y key_file, que la entrega rechaza. La entrega de cualquier configuración de webhook que haga referencia a archivos falla en cada llamada, sea cual sea su modo de autenticación, por lo que todos los enroll y reenroll que llaman a ese webhook fallan hasta que el certificado y la clave se vuelvan a introducir como PEM, en Base64 o plano, o se eliminen los campos de archivo sobrantes si el webhook no usa mTLS. Mientras tanto, una actualización solo de metadatos mediante PUT o PATCH en /v1/dms/:id/metadata sigue funcionando. Si una configuración almacenada guarda rutas de archivos en mtls_options.cert_content o key_content, toda actualización completa de ajustes (POST /v1/dms, PUT /v1/dms/:id) falla la validación — los ajustes se sustituyen al completo, así que la configuración almacenada debe reenviarse.

DMS: conjunto de confianza del reenrolamiento

reenrollment_settings.additional_validation_cas se traslada a reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas. Ese valor anidado nunca se consultó al validar reenrolamientos, así que el conjunto de confianza efectivo no cambia; una lista plana ausente o nula pasa a ser una lista vacía. Los cuerpos que aún contengan additional_validation_cas se aceptan, pero su valor se ignora en silencio — los campos JSON desconocidos se descartan — y las respuestas GET ya no lo incluyen. Lee el DMS antes de enviar ediciones por API: un cuerpo de actualización construido con el formato antiguo vacía en silencio validation_cas.

Lista de verificación

Después de aplicar la actualización, revisa cada área tocada por las notas anteriores:

  1. Webhooks del DMS — lista los DMS con webhook en enrolamiento o reenrolamiento y confirma que cada bloque config lleva insecure_skip_verify y el bloque de opciones esperado (apikey_options, jwt_options o mtls_options con contenido PEM, sin campos de archivo).
  2. Verificación del receptor — confirma que insecure_skip_verify está a false salvo que el certificado del receptor sea intencionadamente no verificado.
  3. Conjunto de confianza del reenrolamiento — lee est_rfc7030_settings.client_certificate_settings.validation_cas y confirma que sigue conteniendo las CAs esperadas para las cohortes de la CA antigua durante los solapamientos de rotación.
  4. Clientes de la API — verifica que cualquier script o consola construida con el formato antiguo del DMS (campo plano additional_validation_cas, campos heredados mtls/apikey/oidc) está actualizado; los cuerpos que los contienen descartan sus valores en silencio.
  5. Entrega — lanza u observa un enroll o reenroll a través de cada webhook migrado y confirma que la llamada de autorización se completa.
