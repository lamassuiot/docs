# Configura y opera el DMS (/docs/pr-preview/pr-38/es/platform/iot-fleets/enrollment/dms)



Un **Device Management Service (DMS)** configura la admisión y el ciclo de identidad de sus dispositivos. Actúa como autoridad de registro; la CA indicada en `Enrollment CA` firma los certificados. Esta guía se dirige a quien administra esa política.

Antes de empezar [#antes-de-empezar]

Necesitas permisos para gestionar DMS, una CA activa con clave utilizable y un [perfil de emisión](/docs/platform/pki/certificate-profiles) probado. Acuerda con el integrador ID del dispositivo, credencial inicial, consumidor y ventana de renovación. Revisa la [estrategia de aprovisionamiento](/docs/platform/iot-fleets/enrollment/provisioning-strategies) antes de elegir registro y sustitución.

Prepara confianza del servidor EST y acceso desde el dispositivo con [Despliegue](/docs/deployment/self-hosted/networking). La autenticación administrativa de tu operador no sustituye la autenticación EST del dispositivo.

Configura un DMS [#configura-un-dms]

<Steps>
  <Step>
    Identifica la flota [#identifica-la-flota]

    Crea el DMS con un nombre reconocible y conserva su ID. Las URLs EST utilizan ese identificador, no el nombre visible. Cada dispositivo conserva un DMS propietario.
  </Step>

  <Step>
    Selecciona la CA de enrolamiento [#selecciona-la-ca-de-enrolamiento]

    Elige **Enrollment CA** y un perfil explícito apropiado para la identidad final. Mantén CN compatible con `Device ID`. El certificado de prueba debe permitir el uso previsto y terminar dentro de la vigencia del emisor.
  </Step>

  <Step>
    Configura EST [#configura-est]

    Selecciona registro y autenticación del primer enrolamiento. Configura por separado la autenticación de reenrolamiento, sus umbrales y la retirada del certificado anterior. Deja ServerKeyGen deshabilitado si el cliente genera su clave.
  </Step>

  <Step>
    Distribuye la confianza [#distribuye-la-confianza]

    Selecciona los certificados que devolverá `/cacerts`. Incluye explícitamente las intermedias y raíces necesarias, sin confundir distribución con instalación automática de confianza.
  </Step>

  <Step>
    Verifica los endpoints [#verifica-los-endpoints]

    Guarda y vuelve a leer la configuración. Consulta `/cacerts`, realiza un enrolamiento permitido y otro rechazado, y comprueba dispositivo, serie e historial. Crear el DMS o descargar cacerts no demuestra que autenticación y emisión funcionen.
  </Step>
</Steps>

Configuración de enrollment [#configuración-de-enrollment]

Enrollment Device Registration [#enrollment-device-registration]

`settings.enrollment_settings.registration_mode` permite `JITP` o `PRE_REGISTRATION`. En JITP se crea el dispositivo desconocido con el CN de la CSR como ID y el DMS como propietario. El `device_provisioning_profile` aporta etiquetas, metadatos e icono a ese alta.

En PRE\_REGISTRATION, el ID debe existir previamente. En el código examinado, un dispositivo existente pasa antes por el control de sustitución, incluso si no tiene identidad. Consulta las [condiciones de prerregistro](/docs/platform/iot-fleets/enrollment/provisioning-strategies#prerregistro-y-sustitución) antes de utilizar este modo.

Enrollment Settings [#enrollment-settings]

| Campo de `settings.enrollment_settings` | Decisión                                                                                                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `protocol`                              | `EST_RFC7030` para estas operaciones.                                                                                                                        |
| `enrollment_ca`                         | ID de la CA que firmará.                                                                                                                                     |
| `verify_csr_signature`                  | Mantén `true` para comprobar posesión de la clave de la CSR.                                                                                                 |
| `enable_replaceable_enrollment`         | Permite `/simpleenroll` para un ID existente del mismo DMS. Puede intentar revocar el anterior incluso si falla una fase posterior; no es un cambio atómico. |
| `est_rfc7030_settings.auth_mode`        | Uno de los cuatro modos de autenticación.                                                                                                                    |

Si el ID pertenece a otro DMS, el enrolamiento inicial se rechaza. No actives sustitución como respuesta automática a un error; el [diagnóstico](/docs/platform/iot-fleets/enrollment/troubleshooting) distingue ID repetido, propiedad y cambios parciales.

Autenticación por operación [#autenticación-por-operación]

Los bloques son independientes:

* `settings.enrollment_settings.est_rfc7030_settings` para `/simpleenroll` y `/serverkeygen`.
* `settings.reenrollment_settings.est_rfc7030_settings` para `/simplereenroll`.

| `auth_mode`                               | Control aplicado en la operación configurada                   |
| ----------------------------------------- | -------------------------------------------------------------- |
| `CLIENT_CERTIFICATE`                      | Validación del certificado presentado.                         |
| `EXTERNAL_WEBHOOK`                        | Autorización del webhook configurado.                          |
| `CLIENT_CERTIFICATE_AND_EXTERNAL_WEBHOOK` | Validación del certificado y, después, aprobación del webhook. |
| `NO_AUTH`                                 | Sin autenticación del solicitante por el DMS.                  |

Webhook y modo combinado también se ejecutan en reenrolamiento si se configuran en su bloque. No hay una degradación implícita a NO\_AUTH en esos casos. Un modo ausente o no reconocido falla.

Para mTLS inicial, `client_certificate_settings` contiene `validation_cas`, `allow_expired` y `chain_level_validation`. El flujo examinado recibe una credencial de certificado, no garantiza transportar todas las intermedias del handshake al validador. Para el caso directo, configura como CA de validación el emisor directo del bootstrap y prueba la ruta real del Gateway.

En <ins className="lm-diff-ins">el </ins>reenrolamiento con certificado, el validador <del className="lm-diff-del">utiliza </del><ins className="lm-diff-ins">prueba primero </ins>la CA de enrolamiento<del className="lm-diff-del">, </del><ins className="lm-diff-ins"> y </ins>después <del className="lm-diff-del">`additional_validation_cas`, y la opción `enable_expired_renewal`. No presupongas que copiar `validation_cas` del bloque inicial cambia esos emisores</del><ins className="lm-diff-ins">las CAs listadas en `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`; esas son las CAs de validación de reenrolamiento, y cada bloque de ajustes consulta solo su propia `validation_cas` — copiar la lista del bloque inicial no amplía la aceptación en reenrolamiento. El validador de reenrolamiento compara la hoja TLS presentada con esas CAs; los valores `chain_level_validation` y `allow_expired` del bloque de reenrolamiento se almacenan pero no se consultan, y el vencimiento lo rige `enable_expired_renewal`</ins>.

Para el webhook, configura destino, autenticación de Lamassu hacia ese servicio, método y timeout. El [contrato de autenticación](/docs/platform/iot-fleets/enrollment/bootstrap-identity) explica la credencial del dispositivo y el cuerpo de la llamada. `NO_AUTH` no acredita propiedad del ID solicitado.

Ajustes del webhook externo [#ajustes-del-webhook-externo]

Los modos de autenticación por webhook leen `external_webhook_settings` en el mismo bloque `est_rfc7030_settings`:

| Campo de `external_webhook_settings` | Decisión                                                                                                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url`                                | URL absoluta `http` o `https` del receptor. Debe ser la URL final; no se siguen redirecciones.                                                                |
| `method`                             | `POST` o `PUT`; `POST` por defecto.                                                                                                                           |
| `name`                               | Etiqueta usada en los logs del servicio.                                                                                                                      |
| `config.auth_mode`                   | `noauth`, `apikey`, `jwt` o `mtls`. Un valor ausente o desconocido se comporta como `noauth`.                                                                 |
| `config.apikey_options`              | Obligatorios para `apikey`: `header` y `key`. Los nombres de cabecera reservados se rechazan.                                                                 |
| `config.jwt_options`                 | Obligatorios para `jwt`: `oidc_client_id`, `oidc_client_secret` y un `oidc_well_known` absoluto `http` o `https`.                                             |
| `config.mtls_options`                | Obligatorios para `mtls`: `cert_content` y `key_content` como PEM en línea.                                                                                   |
| `config.insecure_skip_verify`        | Con `true`, omite la verificación del certificado del receptor. Por defecto se verifica. A diferencia de los canales de alertas, este ajuste se respeta aquí. |
| `config.call_timeout`                | Duración máxima de la llamada de autorización (por ejemplo `10s`); 10 segundos por defecto.                                                                   |

Reglas de esa configuración:

* Crear o actualizar un DMS cuyo `auth_mode` de enrolamiento o reenrolamiento use el webhook valida el bloque y devuelve HTTP 400 — el cuerpo empieza por `struct validation error:` y continúa con `invalid enrollment external webhook config` o `invalid reenrollment external webhook config` — cuando la URL, el método o las opciones no son válidos. Las referencias a archivos (`ca_cert_file`, `mtls_options.cert_file`, `mtls_options.key_file`) siempre son inválidas: el servicio no lee archivos, así que entrega el PEM como `mtls_options.cert_content` y `key_content`.
* Un `apikey_options.header` propio no puede usar nombres en los que la plataforma o el servicio receptor confían — por ejemplo `X-Principal-Id`, `X-Request-Id`, `Host`, `Content-Type` o `Forwarded` — y ningún nombre puede empezar por `X-Forwarded-`, `X-Envoy-` o `X-Lms-` (sin distinguir mayúsculas). La [referencia de la API DMS](/docs/api-reference/dms-manager) documenta los esquemas `WebhookCall` y `WebhookCallHttpClient` y que las cabeceras API-key reservadas se rechazan.
* La clave anidada `http_client` existe solo en las configuraciones de canales de alertas; en un cuerpo de DMS se ignora. La clave de DMS es `external_webhook_settings.config`.
* La API ignora los campos heredados `validate_server_cert`, `apikey`, `oidc` y `mtls`. Un cuerpo con `config.auth_mode` establecido a `apikey`, `jwt` o `mtls` que aún solo contenga los campos de opción heredados (`apikey`, `oidc`, `mtls`) falla la validación con 400; solo se aceptan cuerpos heredados `noauth`, y sus credenciales se descartan.
* La respuesta de autorización debe ser JSON de como máximo 1 MiB; un cuerpo mayor hace fallar la llamada.

<Callout type="warn" title="Credenciales sobre http://">
  Si hay credenciales configuradas, se envían sea cual sea el esquema de la URL: un webhook `http://` recibe la API key o el bearer token en claro, y mTLS no tiene efecto porque no hay handshake TLS, así que el certificado de cliente nunca se presenta. Usa preferentemente `https://` en `url`, en `oidc_well_known` y en el endpoint de token que este anuncia.
</Callout>

La migración `20260604110000` copia la autenticación inicial al bloque de renovación si este falta y existe la estructura necesaria. No sustituye una configuración ya presente. Después de actualizar, lee ambos bloques; si la consola de tu versión no expone la configuración independiente, utiliza la [API DMS](/docs/api-reference/dms-manager).

La migración `20261021120000` reescribe todas las configuraciones de webhook almacenadas con este formato: `validate_server_cert` pasa a ser `insecure_skip_verify` negado (una configuración con `validate_server_cert` a false sigue sin verificar el certificado), `oidc` pasa a ser `jwt_options`, `apikey` pasa a ser `apikey_options` y `mtls` pasa a ser `mtls_options`. Cuando el certificado y la clave heredados son ambos PEM, se trasladan a `mtls_options.cert_content` y `key_content` y no requieren ninguna acción. En cualquier otro caso, incluida una configuración mixta (certificado PEM y clave como ruta de fichero), ambos valores pasan a `mtls_options.cert_file` y `key_file`. La entrega rechaza cualquier configuración de webhook que haga referencia a ficheros, sea cual sea su modo de autenticación, por lo que todos los enroll y reenroll que llaman a ese webhook fallan hasta que el certificado y la clave se vuelvan a introducir como contenido PEM, o se eliminen los campos de fichero sobrantes si el webhook no usa mTLS. Si la consola de tu versión no muestra esos campos, edita el DMS mediante la [API de DMS](/docs/api-reference/dms-manager).

<div className="lm-diff-ins lm-diff-block">
  La migración `20261022120000` traslada `reenrollment_settings.additional_validation_cas` a `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`, sustituyendo lo que hubiera en la clave anidada. Ese valor anidado nunca se consultó al validar reenrolamientos, así que el conjunto de confianza efectivo no cambia; una lista plana ausente o nula pasa a ser una lista vacía. Los DMS sin `reenrollment_settings` quedan intactos. Los cuerpos que aún contengan `additional_validation_cas` se aceptan, pero su valor se ignora en silencio — los campos JSON desconocidos se descartan — y las respuestas GET ya no lo incluyen. Lee el DMS antes de enviar ediciones por API: un cuerpo de actualización construido con el formato antiguo vacía en silencio la lista migrada.
</div>

Perfil de emisión [#perfil-de-emisión]

`settings.issuance_profile_id` tiene precedencia sobre `settings.issuance_profile`; si ninguno existe, se utiliza el perfil predeterminado de la CA. Las reglas se documentan una sola vez en [Perfiles](/docs/platform/pki/certificate-profiles). Cambiar un DMS afecta a solicitudes futuras; no modifica certificados ya firmados ni instala confianza en clientes.

Configuración de re-enrollment [#configuración-de-re-enrollment]

| Campo de `settings.reenrollment_settings`                         | Función                                                                                                                                                                                                                 |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reenrollment_delta`                                              | La ventana abre en `NotAfter` del certificado activo menos este delta.                                                                                                                                                  |
| `preventive_delta`                                                | Umbral operativo preventivo de monitorización.                                                                                                                                                                          |
| `critical_delta`                                                  | Umbral operativo crítico de monitorización.                                                                                                                                                                             |
| `enable_expired_renewal`                                          | Aceptación de un certificado presentado vencido en el validador mTLS de renovación. No autoriza por sí solo otro modo ni elimina restricciones del Gateway.                                                             |
| `additional_validation_cas`                                       | Emisores adicionales para la credencial mTLS durante una migración.                                                                                                                                                     |
| `est_rfc7030_settings.client_certificate_settings.validation_cas` | CAs de validación adicionales para la credencial mTLS de renovación, probadas después de la CA de enrolamiento; suelen poblarse durante la rotación de CAs mientras las cohortes con certificados antiguos se renuevan. |
| `revoke_on_reenrollment`                                          | Si el certificado anterior está ACTIVE, intenta revocarlo con Superseded antes de vincular el sucesor.                                                                                                                  |

Monitorizar no renueva: el cliente debe programar la solicitud y la instalación. En modos webhook o NO\_AUTH, la política de credencial vencida no pasa por el mismo validador mTLS; el webhook debe autorizar explícitamente la recuperación que admita. Revisa [Renovación y recuperación](/docs/platform/iot-fleets/enrollment/renewal-and-recovery) para orden de operaciones y fallos parciales.

ServerKeyGen [#serverkeygen]

`settings.server_keygen_settings.enabled` habilita generación software en el servidor. Algoritmo y tamaño proceden de su campo `key`; el perfil de emisión debe permitirlos. La respuesta contiene una clave PKCS#8 sin cifrar dentro de TLS, además del certificado. Consulta formato y extracción en [Referencia EST](/docs/platform/iot-fleets/enrollment/est-reference#serverkeygen).

Distribución de confianza [#distribución-de-confianza]

| Opción                        | Qué publica                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------- |
| **Include Lamassu System CA** | Certificado TLS downstream disponible; puede ser una hoja, no una CA de emisión. |
| **Include Enrollment CA**     | Certificado de la CA emisora seleccionada.                                       |
| **Managed CAs**               | Certificados de las CAs elegidas explícitamente.                                 |

No se añaden todos los ascendientes automáticamente. La [distribución de confianza](/docs/platform/iot-fleets/enrollment/trust-distribution) distingue raíces confiables, intermedias y confianza inicial del servidor.

Opera el inventario de DMS [#opera-el-inventario-de-dms]

**Edit** cambia nombre, ajustes y metadatos. La actualización del backend sustituye esos bloques completos; al usar la API, lee el DMS antes de enviar una edición para no perder campos.

**Go to DMS owned devices** limita el inventario al propietario. **Show/Edit Metadata** contiene datos operativos y de integraciones; consulta su guía antes de alterarlos. **EST (RFC-7030)** ayuda a localizar las URLs.

**Delete** elimina el registro y la configuración del DMS; no realiza por sí solo una cascada de revocación sobre todos sus dispositivos y certificados. Migra dependencias y conserva las referencias de auditoría antes de retirarlo.
