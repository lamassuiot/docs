Integrate the EST client

Prepare trust, send a CSR and check the identity you receive.

Sin cambios en esta página

This guide is for those implementing the device client. The administrator must have prepared the DMS policy. For a complete first run, follow Enroll and connect your first device.

Before you begin

You need the public HTTPS DMS URL, server trust obtained through an approved channel, the operation's authentication mode and an admitted identifier. The examples use Bash, OpenSSL 3.x and curl with --fail-with-body; use a private working directory and compatible versions of these tools.

Prepare est-trust.pem to verify the EST server, bootstrap.crt and bootstrap.key for initial certificate authentication, and device-root.pem as the approved root of the device issuer. The two trust files can contain different roots. For another authentication mode, adapt the credentials according to Bootstrap identity.

Replace the host and REPLACE_DMS_ID with those of your installation. The URL's APS is the DMS identifier, not its display name.

Download and inspect cacerts

The default content is Base64-encoded DER PKCS#7. It is not a direct PEM file.

Check fingerprints, issuers and dates against the trust distribution policy. The response can contain a selection of CAs and Lamassu's TLS certificate. Do not turn the entire bundle into trusted roots or use it to authenticate its own initial download. HTTP 200 here does not prove that authentication or issuance works.

Prepare the CSR

The example generates a new EC P-256 key and uses est-device-001, which must be available if the DMS registers automatically. The Common Name becomes the device identifier. Check that the profile permits the selected key and subject.

An implementation using hardware or its own store must produce the CSR through its resident key. simpleenroll sends the request and retains the key in the client. Honor Extensions does not authorize every requested attribute: see Profiles.

Request the identity

With initial CLIENT_CERTIFICATE authentication, send the Base64-encoded DER CSR using Content-Type: application/pkcs10:

Stop if curl fails. Retain the HTTP code, headers and body for diagnosis; an error response is not decoded as a certificate. The Bash example stops before that conversion. A timeout leaves the operation's result to be checked in Lamassu: do not automatically repeat issuance.

Check and install the result

For a root that issues directly:

Also verify that the CN is correct, the certificate is a leaf, its uses permit your application and its dates satisfy the profile. cmp must exit with code 0. With intermediates, provide the chain through -untrusted as described in PKI validation.

Query the device: the owning DMS, current serial number and history must match the result. Protect the key/certificate pair and install both using the device's mechanism. Association in Lamassu does not install files in the client. Check a real connection before considering the process complete.
