Deployment troubleshooting

Diagnose access, service health and infrastructure dependencies.

6 cambios en esta página

Start by locating the failing layer. A Gateway response and an unready pod require different evidence. For rejected issuance or validation results, see PKI troubleshooting; for enrollment, see EST diagnostics.

Diagnostic sequence

Reproduce a single operation

Note the time in UTC, user or principal, resource, endpoint and result. Avoid repeating a destructive action such as revocation or deletion.

Separate client, Gateway and service

Check the HTTP status. A 401 points to authentication; a 403, to authorization; a 404, to route or resource; a 5xx, to the service or a dependency.

Review Kubernetes status

Locate unready pods, restarts, recent events and the state of the release.

Query the affected service

Review its /health endpoint and its logs in the same time window. Then follow the indicated dependency: PostgreSQL, RabbitMQ, the OIDC provider or the cryptographic engine.

Validate the result from outside

For PKI, check the certificate, the chain, OCSP or CRL with the same type of client production uses.

Also run the chart's connectivity test:

The test checks the health of CA, DMS Manager, Device Manager and VA, and verifies that the UI returns HTML. A passing test confirms basic connectivity, not a full issuance flow.

Probes use /health

The chart's services expose startup, readiness and liveness probes over /health. A pod can be running but receive no traffic if the readiness probe fails.

I cannot sign in

If you receive a 401:

  • check that the UI's OIDC authority is reachable from the browser;
  • verify issuer, audience and expiration of the token;
  • confirm the Gateway can fetch the keys from the JWKS URI;
  • check that the provider's public and internal routes point to the same realm.

If login succeeds but the APIs return 403:

  • inspect the token's real claims;
  • confirm they match an active principal;
  • review the policies granted to that principal;
  • verify that authz reaches PostgreSQL and its JWKS.

On a fresh installation, confirm the migration Job finished. That Job creates schemas, migrates authz, preloads policies and provisions the principals defined in services.authz.bootstrap.

Everything returns 403 or 5xx

External authorization fails closed by default. If authz is unavailable, protected routes are blocked.

  1. Locate the authz pod and Service.
  2. Check /health, logs and its database connection.
  3. Verify the DNS and port configured in externalAuthorization.
  4. Check the check route is /v1/ext_authz/check.
  5. Do not switch to failOpen: true as a permanent workaround: it would allow traffic without authorization during the outage.

API 500 errors

A 500 indicates an internal failure, such as an unavailable database. The {"err": ...} body currently includes the text of the internal error, which can contain schema, table and constraint names and, on connection failures, the database host and user (not the password). Find the cause in the service log using the request time, and do not forward the body to third parties or show it to end users. This is a known information-disclosure defect: generic messages are planned for 500 responses, keeping the detail only in the service log (tracked in lamassuiot#814). The authorization connector also returns the internal error, in the details.error field. Some request errors, such as a key size the engine does not support, are also returned as 500.

A pod is not Ready

Review kubectl describe pod first. Common causes are:

  • wrong credentials or DNS for PostgreSQL or RabbitMQ;
  • a missing AMQP CA or client certificate Secret referenced by amqp.ca.secretName or amqp.client.secretName;
  • unbound persistent volume;
  • inaccessible image or incorrect pull policy;
  • invalid cryptographic engine configuration;
  • CPU or memory limits set too low;
  • an incomplete prior migration.

Generic values request 100 mCPU and 128 MiB and limit to 500 mCPU and 512 MiB. Tune per service when you see OOMKills, throttling or slow startups.

Filesystem-based KMS engines and VA local storage use exclusive-access volumes. Keep a single replica or migrate to shared backends before enabling autoscaling.

Internal calls now fail fast instead of hanging for the clients covered by Egress proxy: connection attempts time out after 30 seconds and TLS handshakes after 10 seconds. The authorization-engine connector keeps its own transport without these dial and handshake timeouts; only its overall 30-second request timeout bounds each call. If an egress proxy handles the cluster's outbound traffic, check the pod's HTTP_PROXY, HTTPS_PROXY and NO_PROXY environment variables and list in-cluster service names in NO_PROXY.

Events are not arriving

Domain and audit events depend on the bus publisher:

  • verify it is enabled in the emitting service;
  • check AMQP connectivity and credentials;
  • review exchange, routing key, queues and consumers;
  • inspect dead-letter queues;
  • alert on orphan durable queues and backlog growth.

If amqp.tls is enabled, verify the TLS side as well:

  • confirm the broker listener speaks AMQPS on the configured port — the default port stays 5672 and does not follow TLS automatically;
  • if you set amqp.ca.secretName, confirm the Secret exists in the release namespace and its data key matches amqp.ca.certificateKey (default ca.crt); without it, the clients trust the system CAs;
  • remember that a missing referenced Secret prevents the consuming pods from starting;
  • after updating the CA or client certificate Secret, restart the consuming pods: the AMQP client loads certificates at startup.

See AMQP TLS (AMQPS) for the full configuration.

A consumer outage does not always prevent the main operation from completing. That is why you must monitor RabbitMQ and independently verify the persistence of audit logs.

Observability

The chart can enable OpenTelemetry instrumentation. Traces are exported over OTLP HTTP and logs can be directed to a compatible endpoint, such as VictoriaLogs. Use a correlation identifier and the same time window to join Gateway, authz, service and dependency.

Before closing an incident, record:

  • the confirmed cause;
  • the time scope and affected resources;
  • the commands or queries used;
  • the applied change and how to revert it;
  • validation from a consumer;
  • the preventive action and its owner.
