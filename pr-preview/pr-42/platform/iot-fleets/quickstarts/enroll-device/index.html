Enroll and connect your first device

Obtain an identity through EST, verify its association and use it in an mTLS connection.

Sin cambios en esta página

Prepare an evaluation DMS, enroll est-device-001 from the client and use its identity with a local consumer that requires a certificate. The path connects administrator policy to the material the device actually installs.

Before you begin

  • A Lamassu instance accessible through HTTPS and permissions for CAs, profiles, DMSs and reading devices/certificates.
  • Bash, OpenSSL 3.x, curl with --fail-with-body and two terminals on your computer. Work in a new directory with restricted access.
  • An active root CA that issues directly, with an available key and sufficient validity. Follow Create your first CA. Save its verified public certificate as device-root.pem.
  • Available global identifier est-device-001. This path uses automatic registration: do not create the device in the console first.
  • The approved root for Lamassu HTTPS in est-trust.pem, obtained through an independent channel. It can differ from the device CA; prepare networking/TLS in Deployment.

Prepare the bootstrap credential

Issue a bootstrap leaf certificate with CN=est-device-001, its own key and Client Authentication use. Follow Issue and verify a certificate, changing its CN and saving the result as bootstrap.crt and bootstrap.key. Choose validity that covers this test and check the pair and chain.

The same root CA can issue it for this isolated evaluation. The operational identity will have a different key and certificate. The matching CN makes the example easier to read; initial certificate authentication does not itself bind the bootstrap CN to the requested ID. Review admission before applying the policy to a population.

Configure the evaluation DMS

Create an explicit leaf profile compatible with EC P-256, with Honor Subject, CN from the CSR, Digital Signature, Client Authentication and 1 hour validity within the root's validity. Do not enable CA signing. Rules and precedence are explained in Profiles.

Save, reread both authentication blocks and retain the DMS ID. If your console does not expose the independent block, configure and check the resource through the DMS API and DMS guide.

Verify the obtained identity

Expect device.crt: OK and exit code 0 from cmp. Check the CN, serial, dates, Digital Signature and Client Authentication. The certificate must be a leaf: it must not declare CA:TRUE or Certificate Sign use. Check that its validity matches the one-hour profile.

In Lamassu, open est-device-001. It must be created with the intended owning DMS, a current identity and the received certificate in its history. Compare the local serial with the slot; thresholds can show a renewal state rather than simply Active.

With the same server still running, test that a request without a client certificate is rejected:

Rejection must correspond to a missing certificate at the server, not a stopped server. Stop the consumer with Ctrl+C after the test. This exercise demonstrates TLS authentication and key possession; your application must also define authorization and revocation consumption. Server options are described in openssl-s_server.

Continue with Renewal and recovery to request a successor pair within the window, install it and repeat the mTLS check. The consumer must use the new files in that test. After checking the successor, retire the previous certificate according to PKI policy; the example does not revoke it automatically.

Devices and identities explains retirement and the limits of historical revocation. For a real destination, prepare consumer trust, validation and permissions; AWS IoT Core is an available integration.
