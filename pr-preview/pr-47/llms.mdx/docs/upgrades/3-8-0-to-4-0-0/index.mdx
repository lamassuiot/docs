# 3.8.0 to 4.0.0 (/docs/pr-preview/pr-47/upgrades/3-8-0-to-4-0-0)



Upgrading from 3.8.0 to 4.0.0 automatically migrates stored DMS configuration. Most of it converts without intervention, but three changes can leave enrollments failing or configs holding unexpected values if they are not reviewed. This page states what changes, what symptoms to expect and what to do in each case. Current behavior of each feature is documented in the [DMS](/docs/platform/iot-fleets/enrollment/dms) pages.

<div className="lm-diff-ins lm-diff-block">
  The upgrade also carries backend changes that are not DMS-specific: storage consolidates into the PostgreSQL `pki` database, legacy CA keys can be registered in the KMS, device events move to a dedicated store, `authz` replaces the gateway's token validation, and SQLite storage disappears. These steps are covered from [PostgreSQL consolidation](#postgresql-consolidation) onward and should be completed before the DMS checks.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="warn" title="Backend migration steps are provisional">
    The 4.0.0 release is upcoming and the backend migration steps on this page are provisional. Verify each procedure against the final release artifacts before upgrading production.
  </Callout>
</div>

Summary [#summary]

| Change                                                                                | Who is affected                                                   | Severity                                                            | Action                                                         |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| [Webhooks with file references](#webhooks-with-file-references)                       | DMSs with a webhook whose mTLS certificate or key were file paths | High: enrollments and re-enrollments calling the webhook fail       | Re-enter certificate and key as PEM, or remove the file fields |
| [Receiver certificate verification](#receiver-certificate-verification)               | DMSs with a webhook that had `validate_server_cert: false`        | Medium: webhook credentials are sent to an unverified receiver      | Set `insecure_skip_verify` to `false`                          |
| [Re-enrollment trust set](#re-enrollment-trust-set)                                   | Scripts and consoles that edit DMSs through the API               | Medium: an edit in the old layout silently empties `validation_cas` | Read the DMS before editing and use the new field              |
| [Independent re-enrollment authentication](#independent-re-enrollment-authentication) | Any DMS                                                           | Low: informational                                                  | Read both blocks before editing                                |
| [DMS update API](#dms-update-api)                                                     | Clients that send the DMS ID in the update body                   | Low: the update targets the ID in the URL                           | Send update requests with the ID in the URL                    |
| [PostgreSQL consolidation](#postgresql-consolidation)                                 | 3.8.0 deployments with per-service databases                      | High: services find no data after the upgrade                       | Move data and migration history into the `pki` schemas         |
| [Legacy CA keys in the KMS](#legacy-ca-keys-in-the-kms)                               | Installations whose CA keys predate the KMS                       | Medium: CA keys stay unmanaged                                      | Run `ca-to-kms-migration`, with `--dry-run` first              |
| [Device events](#device-events)                                                       | Consumers that read the device `events` field                     | Medium: the field disappears from the device representation         | Use the new event endpoints                                    |
| [SQLite storage removed](#sqlite-storage-removed)                                     | Deployments with SQLite storage                                   | High: the backend no longer supports it                             | Move to PostgreSQL before upgrading                            |
| [Authorization cutover](#authorization-cutover)                                       | All deployments                                                   | High: without bootstrap there is no administrator                   | Configure `authz` following the access-control guide           |
| [AMQP over TLS](#amqp)                                                                | Deployments with TLS on the message broker                        | Medium: plaintext clients are rejected                              | Point clients at the TLS port and trust the broker certificate |
| [Local storage and container images](#local-storage-and-container-images)             | Filesystem KMS engines and locally stored CRLs                    | Medium: data can be left behind                                     | Preserve volumes, transfer data and check permissions          |

A [verification checklist](#verification-checklist) at the end confirms the result.

DMS webhooks [#dms-webhooks]

Stored webhook configs are rewritten to the current layout. Fields are renamed as follows:

| Field in 3.8.0         | Field in 4.0.0                         |
| ---------------------- | -------------------------------------- |
| `validate_server_cert` | `insecure_skip_verify` (value negated) |
| `oidc`                 | `jwt_options`                          |
| `apikey`               | `apikey_options`                       |
| `mtls`                 | `mtls_options`                         |

When the legacy mTLS certificate and key are both PEM, they move into `mtls_options.cert_content` and `mtls_options.key_content` and need no action. The two cases below do need it.

Webhooks with file references [#webhooks-with-file-references]

A mixed config, with a PEM certificate and a file-path key, is migrated to `mtls_options.cert_file` and `mtls_options.key_file`. Webhook delivery rejects those fields, and does so on every call, whatever the configured authentication mode. As a result, every enroll and re-enroll that calls that webhook fails until the config is fixed.

There are two ways to fix it, depending on the webhook:

* If the webhook uses mTLS, re-enter the certificate and key as Base64-encoded or plain PEM.
* If the webhook does not use mTLS, remove the leftover file fields.

Metadata-only updates keep working in the meantime (`PUT` or `PATCH` on `/v1/dms/:id/metadata`).

A variant of the same problem exists: if the stored config holds file paths inside `mtls_options.cert_content` or `mtls_options.key_content`, every full settings update (`POST /v1/dms` or `PUT /v1/dms/:id`) fails validation. Settings are replaced wholesale, so the stored config must be resent with the certificate and key as PEM.

Receiver certificate verification [#receiver-certificate-verification]

A config with `validate_server_cert: false` becomes `insecure_skip_verify: true`. Receiver certificate verification therefore stays skipped until that field is set to `false`.

It should be corrected on every migrated config. The webhook authorization channel carries the API key or bearer token, so skipping verification exposes those credentials to a network-positioned attacker. Keeping `insecure_skip_verify: true` is only justified when the receiver certificate is deliberately unverifiable.

Re-enrollment trust set [#re-enrollment-trust-set]

The flat field `reenrollment_settings.additional_validation_cas` moves into the nested field `reenrollment_settings.est_rfc7030_settings.client_certificate_settings.validation_cas`.

```json
{
  "reenrollment_settings": {
    "est_rfc7030_settings": {
      "client_certificate_settings": {
        "validation_cas": ["<CA_ID>"]
      }
    }
  }
}
```

The effective trust set does not change, because the nested value was never consulted when validating re-enrollments. If the flat list was missing or null, it becomes an empty list.

What does change is how API requests are handled. Bodies that still carry `additional_validation_cas` are accepted, but the value is silently ignored because unknown JSON fields are dropped, and GET responses no longer include it. Consequently, an update body built from the old layout empties `validation_cas` without returning any error. To avoid it, always read the DMS before sending an edit and reuse the layout the API returns.

Independent re-enrollment authentication [#independent-re-enrollment-authentication]

Re-enrollment authentication settings are now stored independently from initial authentication. Nothing needs migrating, but both blocks should be read before editing a DMS so that one is not modified while believing the other is being edited.

If the console version does not expose independent settings, they can be edited through the [DMS API](/docs/api-reference/dms-manager).

<div className="lm-diff-ins lm-diff-block">
  DMS update API [#dms-update-api]
</div>

<div className="lm-diff-ins lm-diff-block">
  `PUT /v1/dms/:id` now takes the DMS ID from the URL and validates the request body. An ID in the body is ignored. Update clients that relied on the body ID.
</div>

<div className="lm-diff-ins lm-diff-block">
  PostgreSQL consolidation [#postgresql-consolidation]
</div>

<div className="lm-diff-ins lm-diff-block">
  The 4.0.0 backend connects to one PostgreSQL database named `pki` and isolates each service in a schema: `kms`, `ca`, `va`, `devicemanager`, `dmsmanager` and `alerts`. Standalone `authz` can use a separate `authz` database; the development monolith stores its data in the `authz` schema of `pki`. WFX keeps its own `wfx` database.
</div>

<div className="lm-diff-ins lm-diff-block">
  Installations on 3.8.0 with separate per-service databases must move their data and migration history into the corresponding `pki` schemas, preserving structure, indexes, constraints and data.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="warn" title="There is no automatic data transfer">
    The migration tooling applies migrations to an existing schema; no command moves data between databases. The transfer procedure on this page is provisional — validate it against the final release artifacts before upgrading production.
  </Callout>
</div>

<div className="lm-diff-ins lm-diff-block">
  Plan the transfer like any data migration: take a verifiable backup of PostgreSQL first, schedule downtime and prevent writes while data is copied.
</div>

<div className="lm-diff-ins lm-diff-block">
  Migrations against the pki database [#migrations-against-the-pki-database]
</div>

<div className="lm-diff-ins lm-diff-block">
  For manual migration, `goose-lamassu` requires `search_path=<schema>` in the connection string and must run against the `pki` database. The binary does not validate the database name, so verify `dbname=pki` before running:
</div>

<div className="lm-diff-ins lm-diff-block">
  ```bash
  ./goose-lamassu "host=$DB_HOST port=5432 user=$DB_USER dbname=pki search_path=kms" up
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  Use the connection and TLS options appropriate for your environment, and repeat per schema: `kms`, `ca`, `va`, `devicemanager`, `dmsmanager` and `alerts`.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="warn" title="The tool's own README is outdated">
    The `goose-lamassu` documentation still shows per-database examples (`dbname=ca`, `dbname=kms`) and claims the tool validates the database name. It does not — only `search_path` is validated. Follow the `dbname=pki` form above.
  </Callout>
</div>

<div className="lm-diff-ins lm-diff-block">
  Legacy CA keys in the KMS [#legacy-ca-keys-in-the-kms]
</div>

<div className="lm-diff-ins lm-diff-block">
  CA certificates of type `MANAGED` or `IMPORTED_WITH_KEY` whose private keys predate the KMS service have the key stored only in the crypto engine, under the certificate's `subject_key_id`, with no record in the KMS. The `ca-to-kms-migration` tool registers them:
</div>

<div className="lm-diff-ins lm-diff-block">
  * `key_id` is the certificate's `subject_key_id` (SHA-256 of the public key).
  * The tool is idempotent: keys already present in the KMS are skipped, so it can be run several times safely.
  * Certificates that cannot be read, or that lack an engine or a subject key ID, are skipped with a warning. Review the logs and resolve affected records.
</div>

<div className="lm-diff-ins lm-diff-block">
  Run it with `--dry-run` first to scan and report without writing to KMS storage, then run the real migration:
</div>

<div className="lm-diff-ins lm-diff-block">
  ```bash
  LAMASSU_CONFIG_FILE=migrate.yaml ./ca-to-kms-migration --dry-run
  LAMASSU_CONFIG_FILE=migrate.yaml ./ca-to-kms-migration
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  Point the tool's `storage` configuration at the `pki` database: in 4.0.0 the CA and KMS data live in the `ca` and `kms` schemas of the same database. The tool's README still describes the pre-4.0.0 two-database layout, so do not copy its examples. In Kubernetes, the recommended approach is to run the migration as a Helm `pre-upgrade` hook Job; see the tool's README (`backend/cmd/ca-to-kms-migration/README.md` in the repository).
</div>

<div className="lm-diff-ins lm-diff-block">
  Device events [#device-events]
</div>

<div className="lm-diff-ins lm-diff-block">
  Historical device events move from the `devices.events` column to a dedicated `device_events` store. The upgrade transforms the existing data.
</div>

<div className="lm-diff-ins lm-diff-block">
  The `events` field no longer appears in the device representation. Adapt consumers that read it and use the new endpoints instead:
</div>

<div className="lm-diff-ins lm-diff-block">
  * `GET /v1/devices/:id/events` returns a device's events.
  * `POST /v1/devices/:id/events` creates an event.
</div>

<div className="lm-diff-ins lm-diff-block">
  When the request `Accept` header includes `text/event-stream`, the events endpoint streams events over Server-Sent Events, with a keepalive every 15 seconds. SSE returns `501` when it is disabled in the deployment.
</div>

<div className="lm-diff-ins lm-diff-block">
  SSE needs to fan out across service instances, so each instance binds its own durable AMQP queue (named `device-manager-sse-<uuid>`). Queues from crashed or replaced instances linger until cleaned up out-of-band — configure an expiration or cleanup policy on the broker to avoid accumulating queues.
</div>

<div className="lm-diff-ins lm-diff-block">
  SQLite storage removed [#sqlite-storage-removed]
</div>

<div className="lm-diff-ins lm-diff-block">
  The SQLite storage engine is removed. Supported providers are `postgres`, `couch_db` and `dynamo_db`. Deployments that used SQLite must move to PostgreSQL first and consolidate their data into the `pki` schemas as described in [PostgreSQL consolidation](#postgresql-consolidation).
</div>

<div className="lm-diff-ins lm-diff-block">
  Authorization cutover [#authorization-cutover]
</div>

<div className="lm-diff-ins lm-diff-block">
  4.0.0 introduces the `authz` service, which validates tokens against the OIDC provider's JWKS endpoint and applies fine-grained authorization to service requests. Validation no longer uses the gateway's former JWT policy.
</div>

<div className="lm-diff-ins lm-diff-block">
  Configure the JWKS endpoint, the credentials for accessing PKI and authz data, the policies, and an initial bootstrap principal. Without a matching principal there is no implicit initial administrator, so nobody can administer the PKI.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="info" title="Full guide available">
    The [access control](/docs/platform/administration/access-control) page documents principals, policies and the first administrator. The [Helm installation](/docs/deployment/self-hosted/helm) page documents `services.authz.bootstrap` and how the pre-install job applies it.
  </Callout>
</div>

<div className="lm-diff-ins lm-diff-block">
  AMQP [#amqp]
</div>

<div className="lm-diff-ins lm-diff-block">
  If TLS is enabled for AMQP, clients connect to the broker's TLS port — `amqps`, commonly `5671` — and must trust the broker's certificate. Verify the effective configuration before upgrading, especially if plaintext AMQP was previously used. The port is operator-configured, so check the one your deployment uses.
</div>

<div className="lm-diff-ins lm-diff-block">
  Local storage and container images [#local-storage-and-container-images]
</div>

<div className="lm-diff-ins lm-diff-block">
  If the KMS uses a filesystem engine or the VA stores CRLs locally, preserve that data during the upgrade and, where necessary, transfer it. Make sure the identity running the services can access keys, CRLs and cryptographic devices, and verify their operation before retiring the original data.
</div>

<div className="lm-diff-ins lm-diff-block">
  Service images run on a distroless, non-root base with numeric UID `65532`; the `authz` image is Ubuntu with a non-root user (the same numeric UID). If you mount volumes holding keys or CRLs, ensure ownership and permissions allow that identity to read them and, where applicable, write them.
</div>

Verification checklist [#verification-checklist]

After applying the upgrade, check in this order:

1. **Databases.** Confirm each service reads the `pki` database with its own schema (`kms`, `ca`, `va`, `devicemanager`, `dmsmanager`, `alerts`), that `authz` and `wfx` data are reachable, and that the migration status is registered per schema. If the deployment used SQLite, confirm the new PostgreSQL storage works end to end.
2. **Legacy CA keys.** Run `ca-to-kms-migration` with `--dry-run`, review the report and any warnings, then run it without the flag and confirm the expected keys appear in the KMS.
3. **Device events.** Query `GET /v1/devices/:id/events` for devices with historical events, confirm the data was migrated, and point consumers at the new endpoints.
4. **Authorization.** Authenticate as the bootstrap principal and confirm administration works; check that a denied identity receives `403`; review client and integration permissions.
5. **AMQP.** Confirm the backend connects to the broker with the expected TLS settings and that the cleanup policy for SSE queues is in place.
6. **Local storage.** Confirm the services can read the KMS keys and CRLs on their volumes, and that CRL issuance and retrieval work.
7. **Webhooks without file fields.** List the DMSs that use a webhook for enrollment or re-enrollment and confirm each `config` block carries `insecure_skip_verify` and the expected option block (`apikey_options`, `jwt_options` or `mtls_options`), with the certificate and key as PEM and no `cert_file` or `key_file`.
8. **Receiver verification.** Confirm `insecure_skip_verify` is `false`, unless the receiver certificate is intentionally unverified.
9. **Delivery.** Trigger, or wait for, one enroll or re-enroll through each migrated webhook and confirm the authorization call completes.
10. **Trust set.** Read `est_rfc7030_settings.client_certificate_settings.validation_cas` and confirm it holds the expected CAs, in particular those of the old CA during rotation overlaps.
11. **API clients.** Update any script or console that uses the old DMS layout (flat `additional_validation_cas`, or the legacy `mtls`, `apikey` and `oidc` fields), since they silently drop those values<ins className="lm-diff-ins">, and confirm DMS updates send the ID in the URL</ins>.
