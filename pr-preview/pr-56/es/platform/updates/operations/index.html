Operaciones

Despliega Lamassu Updates con Docker Compose o Helm, escálalo, dimensiónalo, obsérvalo, haz copias de seguridad y actualízalo.

Página nueva

Esta página es para quien opera el servicio: cómo desplegarlo, qué poner a su alrededor, cómo se comporta con varias réplicas, qué respaldar y cómo actualizarlo. Las claves de configuración están en la referencia de configuración; el modelo de amenazas, en Seguridad.

Despliegue

La imagen de contenedor

Las imágenes de release se publican en ghcr.io/lamassuiot/ota. La imagen ejecuta un único proceso, el monolito (la API de Updates y SymKMS), en el puerto 10090. Contiene la herramienta swugenerator, los scripts firmantes (/app/sign_kms.sh) y los ficheros de workflow de WFX (/app/wfx/workflow/dau/). No define un usuario sin privilegios.

La imagen incluye el config.yml de desarrollo del repositorio en /etc/lamassuiot/config.yml: monta siempre tu propio fichero encima, o apunta OTA_CONFIG_FILE al tuyo (consulta cómo se carga la configuración). Para construir tú mismo la imagen, el Dockerfile espera que su contexto sea el directorio padre del checkout de ota, que además debe contener lamassuiot/core y lamassuiot/sdk.

Docker Compose

docker-compose.yml es para uso local y de demostración. Necesita la red externa ota-net (docker network create ota-net) y un fichero .env (copia .env.example; HOST_IP permite a los contenedores alcanzar Lamassu en el host). Define estos volúmenes con nombre:

VolumenContiene
pgdataDatos de Postgres: las bases de datos updates y hawkbit, y la base wfx que guarda los trabajos de los dispositivos en modo native
update_filesEspacio temporal de construcción y ficheros de actualización locales del servicio updates
sym_keysMaterial de claves de SymKMS
hawkbit_artifactsFicheros de artefactos de hawkBit, con HAWKBIT_ARTIFACT_STORAGE=fs
rustfs_dataEl almacén S3 local, con --profile s3

docker compose --profile s3 up -d arranca además RustFS (API S3 en el puerto 9000) y un trabajo s3-init que crea un único bucket, ota-updates, con el cifrado del lado del servidor activado por defecto. Por convención cada backend usa un prefijo: hawkbit/ para los artefactos de hawkBit y ota/artifacts/ y ota/builds/ para el modo native. Para guardar artefactos y compilaciones en S3, añade los bloques artifacts y builds que muestra config.yml, y define HAWKBIT_ARTIFACT_STORAGE=s3 para hawkBit.

Fijado por las plantillas: la estrategia de despliegue es Recreate (un despliegue tiene una breve interrupción), el periodo de gracia de terminación del pod es de 120 s con una pausa preStop de 5 s, las sondas llaman a GET /health, y un cambio en config reinicia los pods (una anotación con una suma de verificación).

Apunta config.* a las dependencias. En particular, crea antes la base de datos updates en tu Postgres. El servicio crea sus tablas, no la base de datos. El valor por defecto del chart para config.update_domain es http://updates:10090/v1/, que carece del prefijo /updates: defínelo con la base completa de la API, terminada en /updates/v1/, tal como la alcanzan los dispositivos, o las URLs de descarga guardadas en los paquetes no resolverán.

Secretos con Helm

El chart vuelca todo el valor config, incluidos storage.password, encryption.local_key, las claves de S3 y hawkbit.password, en un ConfigMap. No tiene opción existingSecret, ni un valor para añadir variables de entorno o volúmenes, así que las sobrescrituras por variables de entorno del servicio y sus credenciales *_file no se pueden alimentar desde un Secret de Kubernetes sin parchear o envolver el chart. Mientras tanto:

  • Guarda los valores reales en un fichero de valores que no se versione (-f secrets.values.yaml), o genéralo desde tu gestor de secretos en el momento del despliegue.
  • Restringe quién puede leer ConfigMaps y secretos de release de Helm en el espacio de nombres.
  • Prefiere credenciales que eviten claves estáticas: omite las claves de acceso de S3 para usar la cadena de credenciales por defecto de AWS (IRSA o un perfil de instancia).
  • Sustituye la contraseña de base de datos de ejemplo que incluye el chart en config.storage.

helm/updates.yaml es una sobrescritura de valores para el chart paraguas de Lamassu, que se usa como helm upgrade lamassu lamassu/lamassu -f lamassu.yaml -f updates.yaml. Allí define la imagen, las réplicas, los recursos, la persistencia y el config del servicio updates. Su límite de recursos de ejemplo (500m de CPU) es menor que el del chart: consulta Dimensionado de recursos.

Escalar horizontalmente

Servir HTTP funciona con cualquier número de réplicas en ambos modos. Lo que cambia es el estado que necesita cada réplica.

nativehawkbit
Trabajo en segundo planoCon líder elegido: el consumidor de eventos de WFX y el disparador de lanzamientos programados se ejecutan en una réplicaNinguno
EstadoPostgres, WFX, los almacenes artifacts, builds y symkmsPostgres y hawkBit
Ficheros localesSolo espacio temporal de construcción (cada réplica lo recrea)Ninguno
Requisito adicionalAlmacenes S3 y elección de lídersymkms.storage compartido o en S3 si usas cifrado con clave compartida

Para ejecutar más de una réplica native:

  1. Almacenamiento compartido. El valor por defecto es un volumen ReadWriteOnce, que no pueden montar pods de nodos distintos, así que limita el despliegue a una réplica sea cual sea replicaCount. Apunta config.artifacts, config.builds y config.symkms.storage a S3 y define persistence.enabled: false. Las claves de SymKMS también usan por defecto almacenamiento local, y no se compartirían entre réplicas. El servicio registra una advertencia al arrancar cuando las salidas de compilación están en almacenamiento local. Las sw-descriptions se guardan en Postgres, así que ninguna réplica necesita nada local de otra.
  2. Elección de líder. Deja leaderElection.enabled: true. El consumidor de eventos de WFX avanza los lotes de una campaña con cada trabajo completado, y el disparador inicia los lanzamientos programados que vencen y repara los lotes interrumpidos. Con varias réplicas y sin elección, cada una cuenta las mismas finalizaciones y libera el siguiente lote antes de que el actual haya tenido éxito.

leaderElection.mode (leader_election.mode en el fichero) es:

ValorComportamiento
vacío (automático)Leases de Kubernetes dentro de un clúster; en caso contrario, un bloqueo consultivo de Postgres. Es el valor por defecto del binario.
kubernetesLeases, obligatorio. El arranque falla si la cuenta de servicio no puede usarlos. Es el valor por defecto del chart.
databaseUn bloqueo consultivo de Postgres, para cuando conceder RBAC no es una opción.

Con Leases, se crea un Lease por rol en el espacio de nombres del pod (lamassu-updates-wfx-event-consumer y lamassu-updates-scheduled-launch-trigger), y kubectl get lease muestra el pod que lidera (POD_NAME es el titular). El lease dura 15 s y se renueva en 10 s, así que una conmutación por fallo tarda aproximadamente eso. Con el bloqueo de base de datos, una réplica en espera reintenta cada 15 s y el líder verifica cada 5 s que su conexión sigue viva.

Otras garantías con varias réplicas: las construcciones y cambios de versión del mismo paquete toman un bloqueo de Postgres (una petición concurrente responde 409), las migraciones de esquema también, y un lote de campaña se reclama de forma atómica para que no se libere dos veces. Cada réplica mantiene hasta 25 conexiones de base de datos: calcula 25 x réplicas frente al max_connections de Postgres.

En modo hawkbit no hay nada que elegir ni ficheros locales que compartir. El chart sigue montando el volumen ReadWriteOnce mientras persistence.enabled es true, así que defínelo en false para ejecutar réplicas en nodos distintos.

Como el chart usa la estrategia Recreate, un despliegue detiene todas las réplicas antes de arrancar las nuevas, incluso con replicaCount superior a 1.

Dimensionado de recursos

  • La CPU es la palanca del tiempo de construcción por dispositivo. Una construcción ejecuta un swugenerator por dispositivo, y el paralelismo se deriva del límite de CPU del contenedor, no de los núcleos del nodo: un límite de 500m lo reduce a medio núcleo. El valor por defecto del chart, 2000m, es un punto de partida para grupos de cientos.
  • Memoria. Las subidas, las descargas y las construcciones sin cifrado se transmiten en streaming, así que la memoria no crece con el fichero (los mantenedores midieron un pico de unos 150 MiB residentes para una subida de 10 GiB y para una descarga de 10 GiB). Cifrar necesita el fichero en memoria: swugenerator lee un artefacto en memoria para cifrarlo, el AES-GCM de los paquetes non-swu y de los módulos raw trabaja sobre un único búfer, y un almacén con cifrado en reposo descifra objetos enteros en memoria. Dimensiona la memoria para el mayor fichero que cifres multiplicado por las construcciones concurrentes. En modo hawkbit, build_memory_limit_mb rechaza una construcción así antes de que el pod muera.
  • Disco. Cada subida en curso se escribe en un fichero temporal bajo TMPDIR antes de almacenarse, así que las subidas simultáneas necesitan ese espacio libre. El espacio temporal de construcción usa además update_files_base_dir (/data en el chart). Da al volumen margen para varias subidas simultáneas (el ejemplo del chart paraguas usa 50Gi). El chart no expone valores de entorno, así que fijar TMPDIR en el volumen exige un chart parcheado o envuelto.

Tamaño de subida y proxies

max_artifact_size_mb (por defecto 10 GiB) limita un fichero subido. Todo lo que haya delante del servicio debe permitir el mismo tamaño y mantener la conexión abierta tanto como dure la transferencia: el propio servicio usa tiempos de lectura y escritura de 6 horas y cierra las conexiones inactivas a los 5 minutos. Para ingress-nginx:

El límite de cuerpo por defecto de nginx es de 1 MiB, que es lo que rechaza subidas de «unos pocos MB» antes de que lleguen al servicio. Un fichero por encima del límite propio del servicio recibe 413 con el límite indicado.

Salud, registro y apagado

QuéCómo
Liveness y readinessGET /health devuelve {"status":"ok"} sin comprobar Postgres, WFX ni hawkBit, así que solo demuestra que el proceso responde. El chart lo usa para ambas sondas, y la imagen Docker lo ejecuta cada 30 segundos.
CapacidadesGET /updates/v1/capabilities muestra el backend activo y lo que soporta. No requiere autenticación y no tiene efectos secundarios, pero en modo hawkbit consulta a hawkBit, así que no lo uses como sonda.
RegistrosSe escriben en la salida estándar: el registro de la aplicación (nivel app.logs.level) y un registro de acceso de cada petición. Con debug, el registro de arranque incluye toda la configuración, secretos también.
ApagadoCon SIGTERM o SIGINT el servicio deja de aceptar peticiones, drena las que están en curso hasta app.server.shutdown_timeout (60 s), cede el liderazgo y, en modo native, espera hasta 30 s más a que termine un envío de lote en marcha. El periodo de gracia del chart (120 s) lo cubre.

Observabilidad

El servicio no exporta trazas, métricas ni registros. Sus clientes HTTP salientes (el cliente de SymKMS) y su capa de base de datos están instrumentados con OpenTelemetry, pero no se configura ningún proveedor de trazas ni exportador, y no hay endpoint de métricas. El directorio otel/ del repositorio contiene una pila local de desarrollo (Grafana Alloy con receptores OTLP en 4317 y 4318, Loki, Tempo, Prometheus, Grafana; Jaeger en otel/jaeger/) a la que hoy no envía nada. Mientras no haya exportadores, monitoriza el registro del proceso y /health, y vigila los eventos y los Leases de Kubernetes.

Restaura la base de datos y los almacenes de blobs desde el mismo instante: una base de datos que referencia un artefacto ausente del almacenamiento devuelve errores al descargar y al reconstruir. En modo hawkbit, mantén además coherentes las bases de datos updates y hawkbit: las filas de la base updates están acotadas a la instancia de hawkBit que las escribió, y se ignoran si hawkBit vuelve con un conjunto de datos distinto.

Actualizaciones

Haz una copia de seguridad

Haz las copias de arriba, sobre todo de la base de datos updates.

Despliega la imagen nueva

No hay ficheros de migración. Al arrancar, el servicio renombra, crea y migra sus propias tablas bajo un bloqueo consultivo de Postgres, así que las réplicas que arrancan a la vez no compiten. Entre otras cosas, renombra las tablas y columnas del antiguo vocabulario de «update pack» al de «distribution set», integra la tabla de módulos independientes en las tablas de módulos, rellena las asignaciones de dispositivos y convierte los umbrales de aprobación. Consulta Modelo de datos.

Verifica

Comprueba GET /health y GET /updates/v1/capabilities, y lee el registro de arranque en busca de errores de migración.

No hay reversión automática, y las migraciones son de un solo sentido: una imagen anterior no entiende las tablas renombradas. Para volver atrás, restaura la base de datos y los almacenes de blobs desde la copia de seguridad y ejecuta la imagen anterior.

Operaciones de hawkBit

En modo hawkbit, hawkBit es un servicio aparte que operas tú. Su heap de JVM se fija con X_MS y X_MX (el valor por defecto de la imagen es 768m cada una; JAVA_OPTS no lo fija), sus límites de artefactos con las variables SPRING_SERVLET_MULTIPART_* y HAWKBIT_SERVER_SECURITY_DOS_*, y su almacén de artefactos con HAWKBIT_ARTIFACT_STORAGE. Consulta Modo hawkBit.

Lista de comprobación de seguridad

Consulta Seguridad. En resumen: pon delante del servicio un gateway con TLS y autenticación, mantén enable_test_endpoints: false, restringe las rutas de claves de SymKMS, mantén Postgres, la gestión de WFX, el KMS y hawkBit en redes privadas, y no dejes secretos en el repositorio ni en los registros.
