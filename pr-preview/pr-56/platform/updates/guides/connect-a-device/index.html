Connect a device

What a device must do to receive updates from Lamassu Updates, in native mode and in hawkBit mode.

Página nueva

This guide describes the contract between a device and Lamassu Updates, for each backend. The device software is SWUpdate: this page covers what the device must send and receive, not SWUpdate's own installation and configuration, which its documentation describes. Use it when a launch is running and no device moves.

Before you begin

  • A device with SWUpdate installed, and a way to run an update client: a small agent, or SWUpdate's suricatta module.
  • A device identity: one ID that is the same everywhere. It is the WFX client ID in native mode and the hawkBit controller ID in hawkBit mode, and it must equal the device's ID in the Lamassu device registry (see Device management).
  • The device must be a member of a Lamassu IoT device group, because a pack belongs to a group and a launch targets the group's devices. In hawkBit mode group membership is also read from the registry when dms_endpoint is set.
  • Native mode only: update_domain must be an address the device can reach. See Configuration. In hawkBit mode devices download from hawkBit.

Native mode: the device polls WFX

In native mode a launch creates one WFX job per device. The device polls WFX for jobs addressed to its ID, downloads the deliverable from the Updates API, installs it and reports each state back to WFX. Lamassu Updates reads those states from WFX to drive the launch.

The sample device in docker-compose.yml (swupdate-device1) shows the minimum configuration. It takes three variables: DEVICE_NAME (its ID), WFX_URI (the WFX client API, http://custom-wfx:8080/api/wfx/v1 inside the Compose network, localhost:9080 from the host) and PORT. The WFX management API on 9081 is for the service, not for devices.

The job the device receives

The job is addressed to the device (the WFX clientId is the device ID), names a workflow and is tagged with the launch (lms://secure-updates/<launch id>) and the group (lms://dms/<group id>). Its definition looks like this:

FieldMeaning
typeThe pack type: rawfile, firmware, or both (["rawfile","firmware"])
artifacts[0].uriWhere to download the deliverable. The service appends the device ID, so each device fetches its own file. A .swu for SWU packs, a .tar.gz for non-swu packs
algorithm, ivPresent only for an encrypted pack: the algorithm and, for shared-key packs, the hex IV or nonce. A per-device pack carries the algorithm but no iv
signature_key_id, signature_algorithm, signature_certificatePresent only for a signed pack

The device needs the key to decrypt, and holds it itself. For a per-device pack it is the key that SymKMS assigned to that device, and each device downloads a different file.

Downloading

The download answers with the bytes, or with 302 to a short-lived signed URL when presigned downloads are enabled for the build store. Make sure the device's HTTP client follows redirects. The route also answers HEAD and byte-range requests (206), so an interrupted download can resume. The URL is fixed when the pack is built, so a device never sees a new update_domain until you rebuild.

The states the device reports

The device moves its job through the workflow's states, and the workflow decides who may make each move. For the direct workflow:

The device reports INSTALLING, INSTALLED, ACTIVATING and ACTIVATED. WFX itself makes the INSTALLED → ACTIVATE step. From INSTALL, INSTALLING, ACTIVATE and ACTIVATING the device can move to TERMINATED to report a failure; INSTALLED has no failure transition.

WorkflowUsed forTerminal states
wfx.workflow.dau.directSWU packs, no confirmationACTIVATED (success), TERMINATED (failure)
wfx.workflow.dau.phasedSWU packs with confirmation steps (CREATED → DOWNLOAD → ... → ACTIVATED)ACTIVATED, TERMINATED
wfx.workflow.dau.download-installnon-swu packs: DOWNLOAD → ... → INSTALLED, every move made by the deviceINSTALLED, TERMINATED
wfx.workflow.dau.simpleMinimal DOWNLOAD → INSTALL → INSTALLEDINSTALLED, TERMINATED

A phased job has moves that WFX or an operator makes, and nothing in Lamassu Updates advances them: it stays at CREATED until someone confirms it through WFX (the dashboard's Next button does that). The launch endpoints force-version and sync-to-latest use phased for SWU packs unless you pass a workflow. The workflow files are in wfx/workflow/dau/ of the repository. The WFX HTTP API (listing jobs, updating status) is documented by WFX.

hawkBit mode: the device polls hawkBit

In hawkBit mode devices do not poll Lamassu Updates. They poll hawkBit's DDI API, and Lamassu Updates reads the resulting action state from hawkBit.

Make the device a hawkBit target

The device needs a controller ID, and a target tagged group:<id> for its group. With dms_endpoint set, the service does this itself: when it reads a group's devices from the registry it creates the missing targets and tags them. Without dms_endpoint you create the targets and tags yourself. Either way the device must poll hawkBit with valid credentials.

Configure SWUpdate

Point the device's SWUpdate (suricatta) at hawkBit's URL (hawkbit.ddi_url, which defaults to hawkbit.base_url), with the tenant, the controller ID and an authentication method that your hawkBit tenant accepts. hawkBit refuses unauthenticated devices by default. With target security tokens, enable them for the tenant (PUT /rest/v1/system/configs/authentication.targettoken.enabled with {"value":true}) and give each device its target's securityToken, which it sends as Authorization: TargetToken <token>. The hawkBit curl guide shows every request.

Point it at the right hawkBit

The device must poll the same hawkBit that the service is configured for. A service pointed at a hawkBit with no targets builds and launches without error, and nothing downloads it. See Troubleshooting.

hawkBit then hands the device every artifact of its distribution set. A pack with several modules runs several independent installs.

When your gateway routes hawkBit's device artifact URLs (the path of hawkbit.ddi_url, .../<tenant>/controller/v1/<controller>/softwaremodules/<id>/artifacts/<file>) to Lamassu Updates, the service serves them only for modules assigned to or installed on that controller, and answers 404 otherwise. With presigned downloads on, it redirects to a signed URL of hawkBit's S3 bucket instead of streaming the file.

Signed and encrypted images

If the device verifies signatures, set its public key (public-key-file in SWUpdate's configuration) and sign the package with the matching key. If it decrypts, it needs the same key and algorithm the pack was built with. A mismatch is the usual reason an install fails silently after a successful download. Signing and encryption explains which key, algorithm and IV each mode uses, and what the device receives.

Troubleshooting

SymptomLikely cause
The device never sees a job (native)It polls the wrong WFX endpoint or uses a different ID than the group member. The WFX clientId must equal the device ID
The job stays at CREATEDThe launch uses phased. Confirm it through WFX or the dashboard, or relaunch with direct
The download fails with 404The pack is per-device encrypted and the device has no key, or the URL names another device. Check the pack's coverage and that the URL ends with this device's ID
The download succeeds and the install failsThe signature or the key does not match what the device holds. See Signing and encryption
A non-swu launch looks stuck although the device finishedIt was launched with direct or phased, which wait for ACTIVATED. Launch non-swu packs with download-install
The launch never advances (hawkBit)The device is not polling this hawkBit, is not tagged into the group, or cannot authenticate
