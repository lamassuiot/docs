Operations

Deploy Lamassu Updates with Docker Compose or Helm, scale it out, size it, observe it, back it up and upgrade it.

Página nueva

This page is for whoever runs the service: how to deploy it, what to put around it, how it behaves with several replicas, what to back up and how to upgrade. Configuration keys are documented in the configuration reference; the threat model is in Security.

Deploy

The container image

Release images are published to ghcr.io/lamassuiot/ota. The image runs one process, the monolith (the Updates API and SymKMS), on port 10090. It contains the swugenerator tool, the signer scripts (/app/sign_kms.sh) and the WFX workflow files (/app/wfx/workflow/dau/). It does not set a non-root user.

The image includes the repository's developer config.yml at /etc/lamassuiot/config.yml: always mount your own file over it, or point OTA_CONFIG_FILE at yours (see how the configuration is loaded). To build the image yourself, the Dockerfile expects its context to be the parent directory of the ota checkout, which must also contain lamassuiot/core and lamassuiot/sdk.

Docker Compose

docker-compose.yml is for local and demonstration use. It needs the external network ota-net (docker network create ota-net) and a .env file (copy .env.example; HOST_IP lets containers reach Lamassu on the host). It defines these named volumes:

VolumeHolds
pgdataPostgres data: the updates and hawkbit databases, and the wfx database that holds device jobs in native mode
update_filesBuild scratch and local update files of the updates service
sym_keysSymKMS key material
hawkbit_artifactshawkBit's artifact files, with HAWKBIT_ARTIFACT_STORAGE=fs
rustfs_dataThe local S3 store, with --profile s3

docker compose --profile s3 up -d also starts RustFS (S3 API on port 9000) and an s3-init job that creates one bucket, ota-updates, with default server-side encryption turned on. By convention each backend uses a prefix: hawkbit/ for hawkBit's artifacts and ota/artifacts/ and ota/builds/ for native mode. To keep artifacts and builds in S3, add the artifacts and builds blocks shown in config.yml, and set HAWKBIT_ARTIFACT_STORAGE=s3 for hawkBit.

Helm

The chart is helm/updates-monolithic in the repository. It deploys the updates service only: Postgres, WFX, Lamassu and, in hawkbit mode, hawkBit are external.

ValueDefaultMeaning

service.type, service.portClusterIP, 10090The chart has no ingress template: ingress.* in values.yaml has no effect. Expose the service with your own ingress or gateway.

Fixed by the templates: the deployment strategy is Recreate (a deploy has a short outage), the pod's termination grace period is 120 s with a 5 s preStop sleep, probes call GET /health, and a change in config rolls the pods (a checksum annotation).

Point config.* at the dependencies. In particular, create the updates database in your Postgres first. The service creates its tables, not the database. The chart default config.update_domain is http://updates:10090/v1/, which lacks the /updates prefix: set it to the full API base ending in /updates/v1/ as devices reach it, or the download URLs stored on packs will not resolve.

Secrets with Helm

The chart renders the whole config value, including storage.password, encryption.local_key, S3 keys and hawkbit.password, into a ConfigMap. It has no existingSecret option, and no value to add environment variables or volumes, so the service's environment-variable overrides and its *_file credentials cannot be fed from a Kubernetes Secret without patching or wrapping the chart. Until then:

  • Keep the real values in a values file that is not committed (-f secrets.values.yaml), or generate it from your secret manager at deploy time.
  • Restrict who can read ConfigMaps and Helm release secrets in the namespace.
  • Prefer credentials that avoid static keys: leave the S3 access keys out to use the AWS default credential chain (IRSA or an instance profile).
  • Override the placeholder database password the chart ships in config.storage.

helm/updates.yaml is a values override for the umbrella Lamassu chart, used as helm upgrade lamassu lamassu/lamassu -f lamassu.yaml -f updates.yaml. It sets the image, replicas, resources, persistence and config of the updates service there. Its example resource limit (500m CPU) is lower than the chart's: see Resource sizing.

Scale out

Serving HTTP works on any number of replicas in both modes. What differs is the state each replica needs.

nativehawkbit
Background workElected: the WFX event consumer and the scheduled-launch trigger run on one replicaNone
StatePostgres, WFX, the artifacts, builds and symkms storesPostgres and hawkBit
Local filesBuild scratch only (rebuilt by each replica)None
Extra requirementS3 stores and leader electionShared or S3 symkms.storage if you use shared-key encryption

To run more than one native replica:

  1. Shared storage. The default is a ReadWriteOnce volume, which cannot be mounted by pods on different nodes, so it limits the deployment to one replica regardless of replicaCount. Point config.artifacts, config.builds and config.symkms.storage at S3 and set persistence.enabled: false. SymKMS keys also default to local storage, and would not be shared between replicas. The service logs a warning at start-up when build outputs are on local storage. sw-descriptions are stored in Postgres, so nothing local is needed by another replica.
  2. Leader election. Leave leaderElection.enabled: true. The WFX event consumer advances a campaign's batches on every job completion, and the trigger starts due scheduled launches and repairs interrupted batches. With several replicas and no election, each one counts the same completions and releases the next batch before the current one succeeded.

leaderElection.mode (leader_election.mode in the file) is:

ValueBehaviour
empty (auto)Kubernetes Leases inside a cluster; otherwise a Postgres advisory lock. This is the default of the binary.
kubernetesLeases, required. Startup fails if the service account cannot use them. This is the chart default.
databaseA Postgres advisory lock, for when granting RBAC is not an option.

With Leases, one Lease per role is created in the pod's namespace (lamassu-updates-wfx-event-consumer and lamassu-updates-scheduled-launch-trigger), and kubectl get lease shows the pod that leads (POD_NAME is the holder). The lease lasts 15 s and is renewed within 10 s, so a failover takes about that long. With the database lock, a standby retries every 15 s and the leader verifies every 5 s that its connection is still alive.

Other multi-replica guarantees: builds and version changes of the same pack take a Postgres lock (a concurrent request answers 409), schema migrations take one too, and a campaign batch is claimed atomically so it is not released twice. Each replica keeps up to 25 database connections: budget 25 x replicas against Postgres max_connections.

In hawkbit mode there is nothing to elect and no local files to share. The chart still mounts the ReadWriteOnce volume while persistence.enabled is true, so set it to false to run replicas on different nodes.

Because the chart uses the Recreate strategy, a deploy stops every replica before starting the new ones, even with replicaCount above 1.

Resource sizing

  • CPU is the lever on per-device build time. A build runs one swugenerator per device, and the parallelism is derived from the container's CPU limit, not the node's cores: a 500m limit collapses it to half a core. The chart's default of 2000m is a starting point for groups in the hundreds.
  • Memory. Uploads, downloads and non-encrypting builds are streamed, so memory does not grow with the file (the maintainers measured a peak of about 150 MiB resident for a 10 GiB upload and for a 10 GiB download). Encrypting needs the file in memory: swugenerator reads an artifact into memory to encrypt it, AES-GCM of non-swu packages and raw modules works on one buffer, and a store with at-rest encryption enabled decrypts whole objects in memory. Size memory for the largest file you encrypt times the concurrent builds. In hawkbit mode, build_memory_limit_mb refuses such a build before the pod is killed.
  • Disk. Each in-flight upload is written to a temporary file under TMPDIR before it is stored, so overlapping uploads need that much free disk. Build scratch also uses update_files_base_dir (/data in the chart). Give the volume room for several simultaneous uploads (the umbrella example uses 50Gi). The chart exposes no environment values, so setting TMPDIR to the volume needs a patched or wrapped chart.

Upload size and proxies

max_artifact_size_mb (default 10 GiB) caps one uploaded file. Anything in front of the service must allow the same size and keep the connection open as long as the transfer takes: the service itself uses 6-hour read and write timeouts and closes idle connections after 5 minutes. For ingress-nginx:

nginx's default body limit is 1 MiB, which is what rejects "a few MB" uploads before they reach the service. A file above the service's own limit gets 413 naming the limit.

Health, logging and shutdown

WhatHow
Liveness and readinessGET /health returns {"status":"ok"} without checking Postgres, WFX or hawkBit, so it shows only that the process answers. The chart uses it for both probes, and the Docker image runs it every 30 seconds.
CapabilitiesGET /updates/v1/capabilities shows the active backend and what it supports. It is unauthenticated and has no side effects, but in hawkbit mode it asks hawkBit, so do not use it as a probe.
LogsWritten to standard output: the application log (level app.logs.level) and an access log of every request. At debug the start-up log includes the whole configuration, secrets too.
ShutdownOn SIGTERM or SIGINT the service stops accepting requests, drains in-flight ones for up to app.server.shutdown_timeout (60 s), hands over leadership and, in native mode, waits up to 30 s more for a batch dispatch under way. The chart's grace period (120 s) covers this.

Observability

The service does not export traces, metrics or logs. Its outgoing HTTP clients (the SymKMS client) and its database layer are instrumented with OpenTelemetry, but no tracer provider or exporter is configured, and there is no metrics endpoint. The otel/ directory of the repository holds a local development stack (Grafana Alloy with OTLP receivers on 4317 and 4318, Loki, Tempo, Prometheus, Grafana; Jaeger in otel/jaeger/) that nothing feeds today. Until exporters are added, monitor the process log and /health, and watch Kubernetes events and Leases.

Backup and restore

Back upWhy
Postgres: the updates database, plus wfx in native mode (the device jobs) and hawkbit in hawkbit modePacks, launches, device history and, in hawkbit mode, sw-descriptions, signed manifests and staged state
The artifacts and builds S3 buckets (or the update_files volume)Artifact binaries and build outputs. Builds can be rebuilt from artifacts and the sw-description (stored in Postgres); the artifacts themselves cannot be recreated.
The symkms store (S3 bucket or the sym_keys volume)Device and shared encryption keys. If they are lost, packages already delivered cannot be rebuilt identically, and devices cannot decrypt new ones.
encryption.local_key (or the AWS KMS key)Every blob stored with at-rest encryption is unreadable without it. Store it separately from the data.
hawkBit's artifact store (volume or bucket), hawkbit modeThe artifact files

Restore the database and the blob stores from the same point in time: a database that references an artifact missing from storage returns errors on download and rebuild. In hawkbit mode, also keep the updates and hawkbit databases consistent: rows of the updates database are scoped to the hawkBit instance that wrote them, and are ignored if hawkBit comes back from a different data set.

Upgrades

Back up

Take the backups above, mainly the updates database.

Deploy the new image

There are no migration files. At start-up the service renames, creates and migrates its own tables under a Postgres advisory lock, so replicas starting together do not race. Among others it renames the tables and columns of the former "update pack" vocabulary to the "distribution set" ones, folds the standalone-module table into the module tables, backfills device assignments and converts approval thresholds. See Data model.

Verify

Check GET /health and GET /updates/v1/capabilities, and read the start-up log for migration errors.

There is no automated rollback, and migrations are one-way: an older image does not understand renamed tables. To go back, restore the database and the blob stores from the backup, and run the previous image.

hawkBit operations

For hawkbit mode, hawkBit is a separate service you operate. Its JVM heap is set with X_MS and X_MX (the image default is 768m each; JAVA_OPTS does not set it), its artifact limits with the SPRING_SERVLET_MULTIPART_* and HAWKBIT_SERVER_SECURITY_DOS_* variables, and its artifact store with HAWKBIT_ARTIFACT_STORAGE. See hawkBit mode.

Security checklist

See Security. In short: put a gateway with TLS and authentication in front of the service, keep enable_test_endpoints: false, restrict the SymKMS key routes, keep Postgres, WFX management, the KMS and hawkBit on private networks, and keep secrets out of the repository and the logs.
