# Toolchain de Go PQC (/docs/pr-preview/pr-58/es/platform/pqc/go-toolchain)



<div className="lm-diff-ins lm-diff-block">
  Go 1.27 incluye ML-DSA en `crypto/mldsa` y en X.509 y TLS, pero no tiene certificados composite ni SLH-DSA, ni certificados relacionados, ni esquemas de firma TLS composite. Por ello Lamassu compila su backend y su proxy TLS con un fork de Go, mantenido en la rama `release-branch.go1.27`. Esta página describe lo que añade el fork, para quienes compilan Lamassu o escriben un cliente que debe comunicarse con él.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="warn" title="No es Go estándar">
    El fork expone APIs que no existen en la distribución oficial de Go. El código que las usa solo compila con este toolchain, y no debe suponerse que un binario construido con él cumple la promesa de compatibilidad de Go para esas APIs.
  </Callout>
</div>

<div className="lm-diff-ins lm-diff-block">
  Qué añade el fork [#qué-añade-el-fork]
</div>

<div className="lm-diff-ins lm-diff-block">
  **ML-DSA composite en X.509.** El paquete `x509` incorpora `CompositePublicKey` y `CompositePrivateKey`, que implementan `crypto.Signer`, y 15 valores `CompositeAlgorithm` (por ejemplo `x509.MLDSA65_ECDSA_P384_SHA512`) que permiten generar claves, firmar y verificar. Los certificados, las solicitudes de certificado y las listas de revocación firmados con estas claves se interpretan, se serializan y se verifican como cualquier otro. Se admite la codificación PKCS#8 de claves privadas composite. La [página de algoritmos](/docs/platform/pqc/algorithms) enumera los identificadores.
</div>

<div className="lm-diff-ins lm-diff-block">
  **SLH-DSA en X.509.** El algoritmo de clave pública `x509.SLHDSA` y doce algoritmos de firma `PureSLHDSA...` están disponibles para interpretar y verificar certificados y claves. La implementación es la biblioteca `circl` de Cloudflare incorporada al fork. Es la parte menos probada: no tiene pruebas propias en x509 ni soporte TLS.
</div>

<div className="lm-diff-ins lm-diff-block">
  **Certificados relacionados (RFC 9763).** El fork ofrece `x509.CreateBoundCertificate`, que añade a un certificado la extensión `id-pe-relatedCert` (`1.3.6.1.5.5.7.1.36`), `x509.VerifyRelatedCertificate` y las funciones para construir y comprobar el atributo `relatedCertRequest` de una solicitud de certificado (`1.2.840.113549.1.9.16.2.60`). `x509.CertificateRequest` incorpora el campo `ExtraAttributes` para transportarlo. [Certificados relacionados](/docs/platform/pqc/related-certificates) explica cómo los usa Lamassu.
</div>

<div className="lm-diff-ins lm-diff-block">
  **Esquemas de firma composite en TLS.** El paquete `tls` añade 15 constantes `SignatureScheme`, una por algoritmo composite, que se anuncian por defecto después de los esquemas ML-DSA nativos. Solo funcionan con TLS 1.3 y están probadas con autenticación mutua. Sus puntos de código se describen a continuación.
</div>

<div className="lm-diff-ins lm-diff-block">
  Puntos de código TLS [#puntos-de-código-tls]
</div>

<div className="lm-diff-ins lm-diff-block">
  IANA no ha asignado puntos de código a los esquemas de firma TLS composite, por lo que el fork usa el rango de uso privado `0xFE00` a `0xFE0E`, en el orden de la tabla composite: `0xFE00` es `MLDSA44-RSA2048-PSS-SHA256` y `0xFE0E` es `MLDSA65-Ed25519-SHA512`. Un cliente o un servidor construido con una biblioteca TLS estándar no los reconoce y recurrirá a otro esquema o fallará en el handshake. La interoperabilidad queda así limitada a pares construidos con este fork, o a los esquemas ML-DSA nativos (`0x0904` a `0x0906`) que implementa Go 1.27 estándar.
</div>

<div className="lm-diff-ins lm-diff-block">
  Las tres variantes que usan RSA PKCS#1 v1.5 (`MLDSA44-RSA2048-PKCS15-SHA256`, `MLDSA65-RSA3072-PKCS15-SHA512` y `MLDSA65-RSA4096-PKCS15-SHA512`) se anuncian únicamente en la extensión `signature_algorithms_cert`, por lo que pueden aparecer en una cadena de certificados, pero un certificado hoja con una clave de ese tipo no puede firmar el handshake.
</div>

<div className="lm-diff-ins lm-diff-block">
  El intercambio de claves no cambia respecto a Go original. Los grupos híbridos como `X25519MLKEM768`, `SecP256r1MLKEM768`, `SecP384r1MLKEM1024` y el `MLKEM1024` puro son los de la biblioteca estándar de Go 1.27.
</div>

<div className="lm-diff-ins lm-diff-block">
  Un ejemplo mínimo [#un-ejemplo-mínimo]
</div>

<div className="lm-diff-ins lm-diff-block">
  El siguiente programa crea un certificado composite autofirmado y lo usa como certificado de servidor en una configuración TLS 1.3. Se omite la gestión de errores.
</div>

<div className="lm-diff-ins lm-diff-block">
  ```go
  alg := x509.MLDSA65_ECDSA_P384_SHA512
  pub, priv, _ := alg.GenerateCompositeKey(rand.Reader)

  tmpl := &x509.Certificate{
      SerialNumber:          big.NewInt(1),
      Subject:               pkix.Name{CommonName: "example.com"},
      NotBefore:             time.Now().Add(-time.Hour),
      NotAfter:              time.Now().Add(24 * time.Hour),
      KeyUsage:              x509.KeyUsageDigitalSignature,
      BasicConstraintsValid: true,
      DNSNames:              []string{"example.com"},
  }
  der, _ := x509.CreateCertificate(rand.Reader, tmpl, tmpl, pub, priv)
  keyDER, _ := x509.MarshalPKCS8PrivateKey(priv)

  cert, _ := tls.X509KeyPair(
      pem.EncodeToMemory(&pem.Block{Type: "CERTIFICATE", Bytes: der}),
      pem.EncodeToMemory(&pem.Block{Type: "PRIVATE KEY", Bytes: keyDER}),
  )
  cfg := &tls.Config{
      Certificates: []tls.Certificate{cert},
      MinVersion:   tls.VersionTLS13,
  }
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  Una clave composite también puede firmar directamente un mensaje, con un contexto opcional de como máximo 255 bytes:
</div>

<div className="lm-diff-ins lm-diff-block">
  ```go
  sig, _ := priv.Sign(rand.Reader, msg, x509.CompositeSignerOpts{Context: ctx})
  ok := alg.CompositeVerify(pub, msg, ctx, sig)
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  Qué se eliminó [#qué-se-eliminó]
</div>

<div className="lm-diff-ins lm-diff-block">
  Las primeras iteraciones del fork exploraron certificados Chameleon (`draft-bonnell-lamps-chameleon-certs`) y una construcción de certificados delta. Se eliminaron porque ya no se persiguen. El mecanismo de certificados relacionados se recuperó después por separado, siguiendo el RFC 9763.
</div>

<div className="lm-diff-ins lm-diff-block">
  Compilación del toolchain y de las imágenes [#compilación-del-toolchain-y-de-las-imágenes]
</div>

<div className="lm-diff-ins lm-diff-block">
  El fork se compila en CI mediante un workflow que ejecuta la batería de pruebas de Go y después publica una imagen multiarquitectura, `ghcr.io/lamassuiot/golang-pqc`, con la etiqueta `go1.27` y, para la rama `release-branch.go1.27`, `latest`. La imagen contiene el toolchain en `/usr/local/go-pqc`, con `GOROOT` apuntando a esa ruta.
</div>

<div className="lm-diff-ins lm-diff-block">
  Lamassu consume el toolchain de dos maneras. Las imágenes del backend (CA, KMS, VA, alertas, device manager, DMS manager y la compilación monolítica) usan `ghcr.io/lamassuiot/golang-pqc:latest` como imagen de compilación. El workflow de CI del backend instala el mismo toolchain mediante una acción de configuración propia, en lugar de `actions/setup-go`, y el backend exige `go 1.27.3` en su fichero de módulo. Traefik no se compila desde la imagen: su script `build.sh` espera una copia ya compilada del fork en un directorio vecino y genera el binario fuera de un contenedor. Véase [Proxy TLS con Traefik](/docs/platform/pqc/tls-front-proxy).
</div>
