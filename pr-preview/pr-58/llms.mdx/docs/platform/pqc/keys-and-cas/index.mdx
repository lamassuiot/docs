# Keys and certificate authorities (/docs/pr-preview/pr-58/platform/pqc/keys-and-cas)



<div className="lm-diff-ins lm-diff-block">
  The Lamassu backend treats post-quantum keys as one more key type of the Key Management Service (KMS). A certificate authority created with such a key signs certificates and revocation lists through the same paths as an RSA or ECDSA CA, because the fork of Go performs the signing. This page explains what to send to the API, which crypto engines can hold the keys and where the behaviour differs from classical keys. The backend must be built with the [Go PQC toolchain](/docs/platform/pqc/go-toolchain).
</div>

<div className="lm-diff-ins lm-diff-block">
  Choose a crypto engine that supports the algorithm [#choose-a-crypto-engine-that-supports-the-algorithm]
</div>

<div className="lm-diff-ins lm-diff-block">
  Not every crypto engine can create or hold post-quantum keys. Only the engines that run the cryptography in the Lamassu process can.
</div>

<div className="lm-diff-ins lm-diff-block">
  | Engine                            | ML-DSA, SLH-DSA, Composite, Ed25519 |
  | --------------------------------- | ----------------------------------- |
  | Filesystem                        | Supported                           |
  | Software (golang)                 | Supported                           |
  | HashiCorp Vault KV2               | Not supported                       |
  | AWS Secrets Manager               | Not supported                       |
  | AWS KMS                           | Not supported                       |
  | Azure Key Vault and Azure Secrets | Not supported                       |
  | PKCS#11 (HSM)                     | Not supported                       |
</div>

<div className="lm-diff-ins lm-diff-block">
  In practice, post-quantum keys currently require the filesystem engine, which has security level 1. Keys with a higher assurance level, in a hardware security module or a cloud KMS, are not available for these algorithms.
</div>

<div className="lm-diff-ins lm-diff-block">
  <Callout type="warn" title="Engines that advertise more than they support">
    The Vault KV2 and AWS Secrets Manager engines list the post-quantum key types among the types they support, so a request passes the compatibility check. The creation then fails with an `unsupported key type` error from the engine. Select a filesystem or software engine explicitly with `engine_id`.
  </Callout>
</div>

<div className="lm-diff-ins lm-diff-block">
  Create a key [#create-a-key]
</div>

<div className="lm-diff-ins lm-diff-block">
  A KMS key is created with the algorithm and size described in [Algorithms](/docs/platform/pqc/algorithms):
</div>

<div className="lm-diff-ins lm-diff-block">
  ```bash
  curl -X POST https://<LAMASSU_HOST>/api/kms/v1/keys \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer <TOKEN>" \
    -d '{ "name": "mldsa-87-key", "algorithm": "ML-DSA", "size": 87, "engine_id": "<ENGINE_ID>" }'
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  Invalid parameters are rejected with an explicit message: an ML-DSA size other than 44, 65 or 87, an SLH-DSA identifier outside 1 to 12, a composite variant outside 1 to 15, or a composite variant that does not belong to the requested family. Importing a private key in PKCS#8 form detects the algorithm and the parameter set automatically; the import accepts ML-DSA, SLH-DSA, composite and Ed25519 keys.
</div>

<div className="lm-diff-ins lm-diff-block">
  Create a certificate authority [#create-a-certificate-authority]
</div>

<div className="lm-diff-ins lm-diff-block">
  A CA with a post-quantum key uses the same request as any other CA, sent to `POST /api/ca/v1/cas`. Only `key_metadata` changes, where `bits` carries the parameter set. A root CA with ML-DSA-65:
</div>

<div className="lm-diff-ins lm-diff-block">
  ```json
  {
    "id": "mldsa-root",
    "subject": { "common_name": "ML-DSA Root CA", "organization": "Lamassu", "country": "ES" },
    "key_metadata": { "type": "ML-DSA", "bits": 65 },
    "ca_expiration": { "type": "Duration", "duration": "8760h" },
    "profile_id": "<ISSUANCE_PROFILE_ID>",
    "engine_id": "<ENGINE_ID>"
  }
  ```
</div>

<div className="lm-diff-ins lm-diff-block">
  A root CA with a composite key of ML-DSA-44 and ECDSA P-256 uses `"key_metadata": { "type": "Composite-ML-DSA-ECDSA", "bits": 9 }`. Ed25519 uses `"type": "Ed25519", "bits": 256` and SLH-DSA uses `"type": "SLH-DSA", "bits": 1` to select SLH-DSA-SHA2-128s. Subordinate CAs are created the same way: the subordinate signs its own certificate request with the KMS key and the parent CA issues the certificate.
</div>

<div className="lm-diff-ins lm-diff-block">
  Existing CAs can be imported with a post-quantum private key for ML-DSA and Ed25519. Importing a CA with an SLH-DSA or composite key is not supported.
</div>

<div className="lm-diff-ins lm-diff-block">
  Mixing algorithms in a hierarchy [#mixing-algorithms-in-a-hierarchy]
</div>

<div className="lm-diff-ins lm-diff-block">
  The backend places no restriction on which algorithm issues which. A CA with an ML-DSA key can issue certificates to RSA, ECDSA, Ed25519 and ML-DSA subjects, and an RSA or ECDSA CA can issue certificates to post-quantum subjects. The test suite covers the full ML-DSA and Ed25519 matrix through the API, and covers SLH-DSA and composite CAs and leaves at the certificate engine level. This makes it possible to introduce a post-quantum CA beneath a classical root, or the reverse, but a relying party must be able to verify every algorithm in the chain. In TLS, the signatures in the certificate chain are checked against the client's `signature_algorithms_cert` extension, so a chain signed with ML-DSA or a composite algorithm needs a client that announces it there.
</div>

<div className="lm-diff-ins lm-diff-block">
  Signing and verifying with a key [#signing-and-verifying-with-a-key]
</div>

<div className="lm-diff-ins lm-diff-block">
  The KMS signing endpoint accepts new `signature_algorithm` values. The `message_type` field is ignored for all of them. The ML-DSA, SLH-DSA and Ed25519 values are "pure": the message is signed directly, without pre-hashing (not HashML-DSA, HashSLH-DSA or Ed25519ph). The composite values hash the message with the hash of the variant and sign a message representative that includes a fixed label and the optional context.
</div>

<div className="lm-diff-ins lm-diff-block">
  | Key                 | `signature_algorithm`                                                                    |
  | ------------------- | ---------------------------------------------------------------------------------------- |
  | ML-DSA-44, -65, -87 | `MLDSA_44_PURE`, `MLDSA_65_PURE`, `MLDSA_87_PURE`                                        |
  | SLH-DSA             | `SLHDSA_PURE`                                                                            |
  | Composite           | `COMPOSITE_MLDSA_RSA_PURE`, `COMPOSITE_MLDSA_ECDSA_PURE`, `COMPOSITE_MLDSA_ED25519_PURE` |
  | Ed25519             | `Ed25519_PURE`                                                                           |
</div>

<div className="lm-diff-ins lm-diff-block">
  The backend does not check that the algorithm matches the key; choose the value that corresponds to the key type. When a CA signs a certificate or a revocation list, the algorithm is selected automatically.
</div>

<div className="lm-diff-ins lm-diff-block">
  Constraints to keep in mind [#constraints-to-keep-in-mind]
</div>

<div className="lm-diff-ins lm-diff-block">
  Several parts of the platform do not yet handle post-quantum keys. They are collected in [Known limitations](/docs/platform/pqc/limitations); the ones that affect daily operation are these.
</div>

<div className="lm-diff-ins lm-diff-block">
  Issuance profiles enforce key restrictions only for RSA and ECDSA, through `allow_rsa_keys` and `allow_ecdsa_keys`. A profile with enforcement enabled does not block post-quantum keys, and has no switch to allow or deny them.
</div>

<div className="lm-diff-ins lm-diff-block">
  The key strength recorded for a certificate whose key is post-quantum or Ed25519 is computed only for RSA and ECDSA, so those certificates are stored with an unknown key type and size and a low strength.
</div>

<div className="lm-diff-ins lm-diff-block">
  OCSP responses are signed with the `golang.org/x/crypto/ocsp` library, which supports only RSA and ECDSA signing keys. A CA with a post-quantum, Ed25519 or composite key is therefore not expected to be able to sign OCSP responses; CRLs are produced with the fork and are not affected by this limit, although they are not covered by tests.
</div>

<div className="lm-diff-ins lm-diff-block">
  Server-side key generation in the DMS (the EST `serverkeygen` operation) generates only RSA and ECDSA keys.
</div>
