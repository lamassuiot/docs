# Revocation lists (CRL) (/docs/pr-preview/pr-60/platform/pki/crl)



<span id="crl-service" />

A CRL is an issuer-signed list of revoked certificates. This guide is for an operator publishing lists and an integrator using them locally. You need the issuing CA certificate, its <del className="lm-diff-del">SKI</del><ins className="lm-diff-ins">CA ID</ins> and access to the published endpoint. The client must maintain a current copy: offline operation still requires refreshing evidence.

<div className="lm-diff-ins lm-diff-block">
  CRL settings [#crl-settings]
</div>

The <del className="lm-diff-del">VA role stores </del><ins className="lm-diff-ins">CRL settings of a CA store the </ins>configuration and metadata <del className="lm-diff-del">for the</del><ins className="lm-diff-ins">of its</ins> latest <del className="lm-diff-del">list published for a CA’s SKI</del><ins className="lm-diff-ins">published list. Each CA has its own settings, keyed by its CA ID — even when two CAs share a key: they share the SKI, not the CRL</ins>. Generation requires a usable issuer key; do not assume an imported CA without a key has an available CRL.

The signer must be an existing certificate with the `cRLSign` key usage and the same subject and public key as the CA. Certificates from before a reissue qualify. A delegated signer is not supported: a certificate with the CA’s subject but a different key is rejected.

When a CA is reissued and the <del className="lm-diff-del">role’s </del>signer is the superseded CA certificate, the VA moves the signer to the new certificate — provided it carries `cRLSign` — and republishes the CRL. If the signer is any other certificate with the CA’s subject and key, it is deliberately left unchanged; the previous certificate then cannot be deleted while the <del className="lm-diff-del">role uses</del><ins className="lm-diff-ins">settings use</ins> it, and to retire it you update the signer with `PUT`.

  <Callout type="warn" title="Cases in which the role can no longer be edited">
    When a CA is deleted, its VA role is kept and cannot be removed through the API. If no other CA with the same SKI remains, the role can be read but any `PUT` returns 404, and the renewal job logs a warning on every cycle because it no longer finds the CA. The API offers no way out; it can only be fixed by editing the database. If another CA with that SKI remains, the role is still editable (see [CAs that share a key](#cas-that-share-a-key)). Adjust validity and signer before deleting the CA.

    A CA whose certificate lacks `cRLSign` cannot generate its CRL or edit its role (400 error). Since 4.0 the VA requires this usage. Check before importing with `openssl x509 -noout -ext keyUsage` and, if it is missing, obtain a certificate for the same CA and key that includes it and set it as the signer with `PUT`. After reissuing a CA, also check the key usage of the new certificate: it may not keep the original’s usages, and without `cRLSign` the role keeps its previous signer.

    `PUT` always validates the signer, even when the request does not change it. If the stored signer is no longer valid, no field of the role can be modified, not even the validity, until a valid one is set.
  </Callout>
</div>

CAs that share a key [#cas-that-share-a-key]

<del className="lm-diff-del">The VA identifies each CRL by the CA’s SKI, and the SKI is derived from its key. Two CAs with the same key have the same SKI and share a single VA role and a single CRL. This happens when a CA is created on an existing KMS key, or when a CA is imported whose certificate declares an SKI already in use. Lamassu takes the SKI of an imported certificate as-is and does not check that it corresponds to its public key. The first CA creates the role and the others keep it</del><ins className="lm-diff-ins">Since 4.0.0, each CA publishes its own CRL even when its key is shared: two CAs with the same key have the same SKI, but each has its own CRL settings and its own list, signed by a certificate with that CA’s identity</ins>.

<del className="lm-diff-del">The certificates of all of them point to `/crl/{ski}`, but the published list has the first CA as issuer and only includes its revocations. A verifier compares the CRL issuer with the issuer of the certificate it validates (RFC 5280, §6.3.2) and rejects the list if they differ. Depending on its policy, the certificate is blocked (</del>*<del className="lm-diff-del">hard-fail</del>*<del className="lm-diff-del">) or accepted even though it is revoked (</del>*<del className="lm-diff-del">soft-fail</del>*<del className="lm-diff-del">). Revocations of the secondary CAs do not appear in any list</del><ins className="lm-diff-ins">Certificates issued from now on carry `/crl/<ca-id>` distribution points, so each CA’s certificates resolve to its own list. Certificates issued before the upgrade keep their `/crl/<ski>` distribution points: that URL keeps resolving to the settings the upgrade migrated, and always serves the list of the CA that owned that SKI when the upgrade ran. It is never rebound to a CA created later with the same key. The migrated list lists both URLs in its </ins>*<ins className="lm-diff-ins">Issuing Distribution Point</ins>*<ins className="lm-diff-ins"> (OID `2.5.29.28`), so a verifier that compares the IDP with the CDP of the certificate accepts either form</ins>.

  If the first CA is deleted, CRL generation for the remaining one fails because the configured signer no longer matches a CA with that name. Until the role’s signer is updated to a certificate of the remaining CA, the last published list keeps being served until it expires (7 days by default).
</div>

</div>

Periodic and automatic regeneration [#periodic-and-automatic-regeneration]

The VA scheduled job checks <ins className="lm-diff-ins">the CRL settings of </ins>every <del className="lm-diff-del">role</del><ins className="lm-diff-ins">CA</ins> on each run and requests a new list when either of these conditions is met:

* **The list is about to expire:** the remaining validity of `latest_crl` is less than the interval between job runs. This condition always applies and cannot be disabled.
* **The refresh interval has elapsed:** the time since the issuance of the latest published CRL reaches `refresh_interval`. Setting `refresh_interval` to `0` disables only this condition; the list is still regenerated when it is about to expire.

Setting `refresh_interval` to `0` therefore does not freeze regeneration. With the default 7-day validity and an hourly job, a CRL is renewed up to an hour before it expires even if `refresh_interval` is `0`.

The job frequency is set in Helm with `services.va.job.crl.frequency` (default `0 * * * *`) and accepts a duration (`1h`) or a cron expression. A cron expression is converted into a constant interval equal to the time left until its next firing when the service starts, so it is not aligned with the clock. Keep `validity` well above that interval: with a shorter validity, the list is regenerated on every cycle.

If generation fails (for example, because <del className="lm-diff-del">of a role without a CA or an invalid signer</del><ins className="lm-diff-ins">the CA cannot be resolved or the signer is invalid</ins>), the job logs the warning <del className="lm-diff-del">`something went wrong while calculating CRL for CA <ski>`</del><ins className="lm-diff-ins">`something went wrong while calculating CRL for CA <ca-id>`</ins> and retries on the next cycle. There is no other renewal path until the cause is fixed, and the last published list keeps being served until it expires. All of this depends on working jobs, storage and signing.

<div className="lm-diff-ins lm-diff-block">
  Settings whose `status` is `ARCHIVED` are skipped: nothing regenerates their CRL.
</div>

With `regenerate_on_revoke`, the event handler requests a new CRL upon revocation or reactivation from `CertificateHold` to `ACTIVE`. This happens after the status change and has its own failure paths: if generation fails (for example, because of an invalid signer), the event is retried and, once retries are exhausted, moves to the failed-events queue. If the issuing CA has no <del className="lm-diff-del">VA role</del><ins className="lm-diff-ins">CRL settings</ins>, there is no CRL to regenerate: the event is acknowledged without retry, the VA logs a warning, and nothing appears in the failed-events queue. Confirming revocation does not establish that the new CRL is already published or that all clients have downloaded it.

Compare CRL numbers and timestamps before and after a change. Monitor expired lists and generation failures; clients must apply policy when current evidence is unavailable.

CRL contents [#crl-contents]

Each entry contains serial number, revocation time and reason. The generator queries certificates in `REVOKED` state for the selected CA. A reactivated certificate disappears when the list is recalculated; an earlier downloaded copy retains its contents.

The list contains a critical *Issuing Distribution Point* (OID `2.5.29.28`) with configured distribution URLs. Check that your client interprets this extension and that it matches the list’s scope. If rejected, investigate format and scope; ignoring a critical extension is not successful validation.

Public download endpoint [#public-download-endpoint]

The VA service exposes <del className="lm-diff-del">`GET /crl/{subject_key_id}`</del><ins className="lm-diff-ins">`GET /crl/{id}`</ins> without management authorization. Use the **issuing CA’s** <del className="lm-diff-del">SKI</del><ins className="lm-diff-ins">ID</ins>, not the end-entity certificate’s <del className="lm-diff-del">SKI</del><ins className="lm-diff-ins">ID</ins> or serial<ins className="lm-diff-ins">. Certificates issued before the 4.0.0 upgrade carry `/crl/<ski>` URLs with the SKI of the CA key; that form keeps resolving</ins>. First inspect the certificate’s CDP:

```bash
openssl x509 -in device.crt -noout -text
```

Replace the following URL with the CDP URL and review exposure in [Deployment](/docs/deployment/self-hosted/networking):

<div className="lm-diff-final">
  ```bash
  CRL_URL='http://pki.example.com/crl/REPLACE_WITH_CDP_ID'

  curl --fail --show-error --silent --max-time 15 \
    "$CRL_URL" -o ca.crl.der

  openssl crl -inform DER -in ca.crl.der \
    -outform PEM -out ca.crl.pem

  openssl crl -in ca.crl.pem -noout \
    -issuer -lastupdate -nextupdate -crlnumber

  openssl crl -in ca.crl.pem -noout -text
  openssl crl -in ca.crl.pem -noout -verify -CAfile issuer.pem
  ```
</div>

<div className="lm-diff-merged">
  ```bash lmdiff="-+============"
  CRL_URL='http://pki.example.com/crl/REPLACE_WITH_ISSUER_SKI'
  CRL_URL='http://pki.example.com/crl/REPLACE_WITH_CDP_ID'

  curl --fail --show-error --silent --max-time 15 \
    "$CRL_URL" -o ca.crl.der

  openssl crl -inform DER -in ca.crl.der \
  ```

</div>

You need OpenSSL 3.x and `issuer.pem` containing the direct issuer’s certificate. An accepted signer certificate has the same subject and public key as the CA, so this signature check also works when the <del className="lm-diff-del">role points</del><ins className="lm-diff-ins">settings point</ins> to an earlier certificate for that CA and key. Require a valid signature, current timestamps and the expected issuer. For a root that issues directly:

```bash
openssl verify -CAfile roots.pem -CRLfile ca.crl.pem \
  -crl_check -purpose sslclient device.crt
```

`roots.pem` contains deliberately trusted roots. For intermediates, add `-untrusted intermediates.pem` before the `device.crt` argument. `-crl_check` checks the end-entity certificate’s revocation against the local list; it does not download other lists or establish the status of the whole chain. A complete chain check needs the corresponding CRLs and a policy requiring them.

The test should accept an allowed certificate absent from the list and reject it with `certificate revoked` after publishing and using the list containing its serial.

From the interface [#from-the-interface]

The CA view lets you inspect and download the available list. Compare version, issuer and timestamps with the copy downloaded from the public endpoint. The CA’s VA settings also let you select the CRL signer: the certificate picker only offers certificates that have a private key and carry the `cRLSign` key usage. If a configured signer’s certificate cannot be resolved, the interface shows `Unknown Certificate (Serial: X)` or `Certificate details unavailable (Serial: X)`. Diagnose differences using [PKI troubleshooting](/docs/platform/pki/troubleshooting).
