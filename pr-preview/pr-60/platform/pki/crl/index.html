Revocation lists (CRL)

Generate and distribute signed lists to validate certificates offline.

68 cambios en esta página

A CRL is an issuer-signed list of revoked certificates. This guide is for an operator publishing lists and an integrator using them locally. You need the issuing CA certificate, its SKICA ID and access to the published endpoint. The client must maintain a current copy: offline operation still requires refreshing evidence.

VA role and per-CA configuration

CRL settings

The VA role stores CRL settings of a CA store the configuration and metadata for theof its latest list published for a CA’s SKIpublished list. Each CA has its own settings, keyed by its CA ID — even when two CAs share a key: they share the SKI, not the CRL. Generation requires a usable issuer key; do not assume an imported CA without a key has an available CRL.

The signer must be an existing certificate with the cRLSign key usage and the same subject and public key as the CA. Certificates from before a reissue qualify. A delegated signer is not supported: a certificate with the CA’s subject but a different key is rejected.

When a CA is reissued and the role’s signer is the superseded CA certificate, the VA moves the signer to the new certificate — provided it carries cRLSign — and republishes the CRL. If the new certificate lacks cRLSign, the VA keeps the previous signer and logs a warning. If the signer is any other certificate with the CA’s subject and key, it is deliberately left unchanged; the previous certificate then cannot be deleted while the role usessettings use it (the API rejects it withreturns 409 certificate is in use), and to retire it you update the signer with PUT.

Cases in which the role can no longer be edited

When a CA is deleted, its VA role is kept and cannot be removed through the API. If no other CA with the same SKI remains, the role can be read but any PUT returns 404, and the renewal job logs a warning on every cycle because it no longer finds the CA. The API offers no way out; it can only be fixed by editing the database. If another CA with that SKI remains, the role is still editable (see CAs that share a key). Adjust validity and signer before deleting the CA.

A CA whose certificate lacks cRLSign cannot generate its CRL or edit its role (400 error). Since 4.0 the VA requires this usage. Check before importing with openssl x509 -noout -ext keyUsage and, if it is missing, obtain a certificate for the same CA and key that includes it and set it as the signer with PUT. After reissuing a CA, check the key usage of the new certificate: if it lacks cRLSign, the VA keeps the previous signer and logs a warning, so the lists keep being signed by the superseded certificate until you fix the usage.

PUT always validates the signer, even when the request does not change it. If the stored signer is no longer valid, no field of the role can be modified, not even the validity, until a valid one is set.

Cases in which the settings can no longer be edited

Deleting a CA keeps its CRL settings, and they cannot be removed through the API. What happens next depends on when the CA was deleted:

  • The 4.0.0 upgrade migration archives the settings of the CAs that had been deleted before the upgrade. Their status is ARCHIVED and their ca_id is legacy-<ski>: the last CRL keeps being served, but it is never regenerated, any PUT returns 409, and there is no API way back to ACTIVE.
  • A CA deleted while running 4.0.0 leaves ACTIVE settings. The last CRL keeps being served, but once it expires nothing regenerates it: the renewal job logs something went wrong while calculating CRL for CA <ca-id> on every cycle because it can no longer resolve the CA. The options can still be edited while the signer is unchanged; changing the signer fails, because there is no CA left to match it.

Adjust validity and signer before deleting a CA.

PUT validates the signer only when the request changes it. If the stored signer is no longer valid, the other options can still be edited, but the CRL cannot be regenerated until a valid signer is set.

CAs that share a key

The VA identifies each CRL by the CA’s SKI, and the SKI is derived from its key. Two CAs with the same key have the same SKI and share a single VA role and a single CRL. This happens when a CA is created on an existing KMS key, or when a CA is imported whose certificate declares an SKI already in use. Lamassu takes the SKI of an imported certificate as-is and does not check that it corresponds to its public key. The first CA creates the role and the others keep itSince 4.0.0, each CA publishes its own CRL even when its key is shared: two CAs with the same key have the same SKI, but each has its own CRL settings and its own list, signed by a certificate with that CA’s identity.

The certificates of all of them point to /crl/{ski}, but the published list has the first CA as issuer and only includes its revocations. A verifier compares the CRL issuer with the issuer of the certificate it validates (RFC 5280, §6.3.2) and rejects the list if they differ. Depending on its policy, the certificate is blocked (hard-fail) or accepted even though it is revoked (soft-fail). Revocations of the secondary CAs do not appear in any listCertificates issued from now on carry /crl/<ca-id> distribution points, so each CA’s certificates resolve to its own list. Certificates issued before the upgrade keep their /crl/<ski> distribution points: that URL keeps resolving to the settings the upgrade migrated, and always serves the list of the CA that owned that SKI when the upgrade ran. It is never rebound to a CA created later with the same key. The migrated list lists both URLs in its Issuing Distribution Point (OID 2.5.29.28), so a verifier that compares the IDP with the CDP of the certificate accepts either form.

If the first CA is deleted, CRL generation for the remaining one fails because the configured signer no longer matches a CA with that name. Until the role’s signer is updated to a certificate of the remaining CA, the last published list keeps being served until it expires (7 days by default).

Sharing an SKI between CAs blocks the upgrade: the migration aborts and names the SKIs. To detect the problem before upgrading, compare the SKI of the CAs in the inventory: two with the same SKI are affected. To fix it, create a CA with its own key and reissue its certificates; those already issued keep the old URL and are not corrected until reissued.

Periodic and automatic regeneration

The VA scheduled job checks the CRL settings of every roleCA on each run and requests a new list when either of these conditions is met:

  • The list is about to expire: the remaining validity of latest_crl is less than the interval between job runs. This condition always applies and cannot be disabled.
  • The refresh interval has elapsed: the time since the issuance of the latest published CRL reaches refresh_interval. Setting refresh_interval to 0 disables only this condition; the list is still regenerated when it is about to expire.

Setting refresh_interval to 0 therefore does not freeze regeneration. With the default 7-day validity and an hourly job, a CRL is renewed up to an hour before it expires even if refresh_interval is 0. Because the job runs on its own schedule, refresh_interval is honored only as precisely as the job frequency allows.

The job frequency is set in Helm with services.va.job.crl.frequency (default 0 * * * *) and accepts a duration (1h) or a cron expression. A cron expression is converted into a constant interval equal to the time left until its next firing when the service starts, so it is not aligned with the clock. Keep validity well above that interval: with a shorter validity, the list is regenerated on every cycle.

If generation fails (for example, because of a role without a CA or an invalid signerthe CA cannot be resolved or the signer is invalid), the job logs the warning something went wrong while calculating CRL for CA <ski>something went wrong while calculating CRL for CA <ca-id> and retries on the next cycle. There is no other renewal path until the cause is fixed, and the last published list keeps being served until it expires. All of this depends on working jobs, storage and signing.

Settings whose status is ARCHIVED are skipped: nothing regenerates their CRL.

With regenerate_on_revoke, the event handler requests a new CRL upon revocation or reactivation from CertificateHold to ACTIVE. This happens after the status change and has its own failure paths: if generation fails (for example, because of an invalid signer), the event is retried and, once retries are exhausted, moves to the failed-events queue. If the issuing CA has no VA roleCRL settings, there is no CRL to regenerate: the event is acknowledged without retry, the VA logs a warning, and nothing appears in the failed-events queue. Confirming revocation does not establish that the new CRL is already published or that all clients have downloaded it.

Compare CRL numbers and timestamps before and after a change. Monitor expired lists and generation failures; clients must apply policy when current evidence is unavailable.

CRL contents

Each entry contains serial number, revocation time and reason. The generator queries certificates in REVOKED state for the selected CA. A reactivated certificate disappears when the list is recalculated; an earlier downloaded copy retains its contents.

The list contains a critical Issuing Distribution Point (OID 2.5.29.28) with configured distribution URLs. Check that your client interprets this extension and that it matches the list’s scope. If rejected, investigate format and scope; ignoring a critical extension is not successful validation.

From the interface

The CA view lets you inspect and download the available list. Compare version, issuer and timestamps with the copy downloaded from the public endpoint. The CA’s VA settings also let you select the CRL signer: the certificate picker only offers certificates that have a private key and carry the cRLSign key usage. If a configured signer’s certificate cannot be resolved, the interface shows Unknown Certificate (Serial: X) or Certificate details unavailable (Serial: X). Diagnose differences using PKI troubleshooting.
