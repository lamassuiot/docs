Install Lamassu with Helm

Use the Helm workflow when you need explicit control over identity, databases, messaging, certificates, storage and upgrades. For an evaluation environment where the script can make those choices for you, use Fastlane.

Before you begin

Prepare the platform services that are deliberately outside the Lamassu chart:

  • a Kubernetes 1.24+ cluster and Helm 3.2+
  • a reachable PostgreSQL server and a role allowed to create databases and schemas
  • a reachable RabbitMQ broker and credentials
  • Kubernetes Secrets in the release namespace holding the PostgreSQL and RabbitMQ credentials (and SMTP credentials when SMTP authentication is required) — the chart reads credentials from Secrets and rejects inline values (see Credentials in Kubernetes Secrets)
  • an OIDC provider, normally Keycloak, with a realm/tenant and client for Lamassu
  • Envoy Gateway 1.8+ and a GatewayClass
  • cert-manager 1.14+ (only for the default tls.type: certManager mode); for trusted TLS, either a trusted issuer or a Kubernetes TLS Secret
  • a StorageClass and an external traffic design

The chart defaults to a GatewayClass named eg. Change gateway.className if your platform team uses another name.

What Helm does with PostgreSQL

You provide the PostgreSQL server. The chart's pre-install job connects with the supplied credentials, creates the required pki, authz and wfx databases and service schemas, runs migrations, and applies services.authz.bootstrap.

The chart has no Helm dependencies that install PostgreSQL, RabbitMQ, an OIDC provider, Envoy Gateway or cert-manager.

Do not add gateway.addresses by default. Leave address assignment to the load-balancer implementation unless your network design requires a specific Kubernetes-side VIP. The public IP of an upstream NAT gateway or reverse proxy does not belong in this value.

If Keycloak is external and already has its own reachable URL, point the OIDC settings at it and omit the /auth entry from gateway.extraRouting.

If your values file still carries the legacy gateway JWT validation settings — auth.oidc.apiGateway.jwks, auth.authorization.rolesClaim or auth.authorization.roles.admin — remove them. The migration guide charts/lamassu/CHANGELOG/3.8.0->4.0.0.md documents their removal with no compatibility aliases, and values.schema.json rejects the leftover blocks instead of silently ignoring them. The replacements are services.authz.jwkUrl and services.authz.bootstrap, already shown in the example above.

The chart runs workloads as 65532:65532 with the RuntimeDefault seccomp profile and no capabilities. It creates a dedicated ServiceAccount and does not mount its token by default. Ensure mounted volumes are accessible to that identity.

Credentials in Kubernetes Secrets

The chart reads the PostgreSQL, AMQP and SMTP credentials from Kubernetes Secrets in the release namespace. Reference them with existingSecret plus the usernameKey and passwordKey data keys; inline username and password values are removed and rejected by values.schema.json.

The Secrets must exist before you install or upgrade: the pre-install and pre-upgrade migration job connects to PostgreSQL with the PostgreSQL Secret, and the service containers read the AMQP and SMTP credentials when they start.

  • postgres.existingSecret (default lamassu-postgres) and amqp.existingSecret (default lamassu-amqp) are always required.
  • services.alerts.smtp_server.existingSecret is empty by default, which means SMTP without authentication. Set it, together with its key names, only when your SMTP server requires authentication.
  • Each services.authz.credentials entry names its database and uses the global PostgreSQL Secret — postgres.existingSecret with its configured key names — unless the entry sets its own existingSecret.

Changing a Secret's contents does not roll the pods that consume it: the services read the credentials when they start. Restart the affected pods after rotating a credential.

For production, manage the Secrets with the External Secrets Operator (ESO), which the chart does not install. The charts/lamassu/README.md in the Helm repository documents a complete working example in its Secret management section: installing external-secrets 0.20.2, a test ClusterSecretStore, the ExternalSecret resources and the wait before installing the chart. Its Fake provider is for testing only — replace it with your provider's configuration for anything beyond a throwaway environment; AWS Secrets Manager, Vault, Azure Key Vault, GCP Secret Manager and other providers are documented at external-secrets.io.

Only these credentials moved into Secrets: other values, such as connector and crypto-engine settings, are still configured through the values file.

TLS with an existing Secret

Create a Secret containing tls.crt and tls.key, then reference it. The Secret must already exist before installing: in external mode the chart renders no cert-manager resources and never creates this Secret.

AMQP TLS (AMQPS)

amqp.tls: true selects AMQPS in every event-bus configuration block. The default port stays 5672 and does not change automatically when TLS is enabled, so set amqp.port to the broker's TLS listener, commonly 5671.

With no CA Secret configured, the event-bus clients use the system-trusted CAs. To trust a private CA, create a Secret in the release namespace containing the CA certificate in PEM format and set amqp.ca.secretName (and amqp.ca.certificateKey if the data key is not ca.crt).

For brokers that require mutual TLS, create a Secret containing the client certificate and private key and set amqp.client.secretName (with amqp.client.certificateKey and amqp.client.privateKeyKey if the data keys are not tls.crt and tls.key).

The chart mounts configured Secrets read-only into every AMQP-consuming workload: the CA certificate under /etc/lamassu/amqp/ca and the client certificate and key under /etc/lamassu/amqp/client. The mounted file names are always ca.crt, tls.crt and tls.key — the certificateKey and privateKeyKey values rename only the Secret data keys, never the on-disk paths. The client private key is mounted with restrictive permissions (defaultMode: 0440; the CA volume uses 0444), which works because the chart adds fsGroup to the pod security context when amqp.client.secretName is set — the chart's default pod security context already sets fsGroup: 65532 for every service pod, so this top-up applies only when an explicit podSecurityContext without fsGroup was overridden and an AMQP client Secret is configured — and it uses the container runAsGroup (default 65532) when fsGroup is not already set.

Both Secret options require amqp.tls: true: values.schema.json rejects a non-empty secretName when tls is false, rejects unknown keys and rejects data-key names outside ^[A-Za-z0-9._-]+$. The referenced Secret must exist in the release namespace or the consuming pods fail to start.

The AMQP client loads certificates at startup, so restart the consuming pods after updating either Secret. Changing any amqp value rolls the consuming pods through the checksum/config annotation, but a change to Secret content alone does not trigger a rollout.

Set the AMQP port before upgrading

Per the migration guide charts/lamassu/CHANGELOG/3.8.0->4.0.0.md: in 3.8.0 amqp.tls was not applied and event-bus clients used plaintext AMQP; from 4.0.0, amqp.tls: true switches them to AMQPS. Set amqp.port to the broker TLS listener before upgrading, or set amqp.tls: false to keep plaintext AMQP. amqp.tls: false sends the broker credentials and all event-bus traffic in cleartext.

Device event stream (SSE)

services.deviceManager.sseEnabled (default true) controls whether Device Manager serves its device-event stream over Server-Sent Events (SSE). With the default, the chart renders a dedicated gateway rule for the device-events endpoint with an 11-minute request timeout, because the Gateway's default request timeout is too short for these streams, which the service keeps open for up to about ten minutes. Device Manager calls that are not SSE requests keep the Gateway's default timeout.

Set it to false to disable the stream: the chart then renders sse_enabled: false in the Device Manager configuration and omits the gateway rule, and SSE requests to the device-events endpoint fail. See Device events in the 3.8.0 to 4.0.0 upgrade guide.

Provision the first administrator

There is no implicit superuser. Create the role or group expected by services.authz.bootstrap in the OIDC provider and assign it to at least one administrator before exposing Lamassu.

The pre-install and pre-upgrade job applies the bootstrap idempotently: existing principals are preserved and missing grants are added.

Validate access before exposing the platform

Test both an authorized identity and a denied identity. If no token matches an active bootstrap principal, nobody can administer the PKI.

See Access control for the principal and policy model.

Experimental dashboard terminal (optional)

The dashboard includes an experimental browser terminal for working with devices. It is disabled by default; enable it in the values file:

Enabling the terminal requires external authorization: set auth.externalAuthorization.enabled: true and auth.externalAuthorization.failOpen: false. The chart refuses to render the release otherwise, because the terminal's WebSocket endpoint would then be exposed through the Gateway without external authorization.

Only identities granted the preloaded "Terminal Network" policy can open terminal sessions. See Access control for how policies are assigned.

Note that even with the terminal enabled, pods inside the cluster can still reach the UI service directly unless network policies restrict that access — the external authorization applies to traffic entering through the Gateway.

Upgrading Lamassu

Version-specific upgrade steps live in charts/lamassu/CHANGELOG/ in the Helm repository. The chart also ships an optional pre-upgrade Job that migrates existing CA private keys into the KMS engine configured for the release. It is off by default (migrations.caToKms.enabled: false) and is only needed when upgrading from a version prior to 3.7.0.

While the flag is enabled, every helm upgrade creates the <chart fullname>-ca-to-kms-migration Job (lamassu-ca-to-kms-migration for release lamassu); a fresh install does not create it. Its hook weight is -10, so it runs before the other pre-upgrade hooks: the authorization bootstrap configuration (weight -4) and the database-migration Job (weight -3).

The Job consumes the same KMS service configuration the chart renders into the KMS ConfigMap, including the engines from services.kms.cryptoEngines, and runs the migration tool defined in migrations.caToKms.image. It mounts that configuration read-only at /etc/lamassuiot/config.yml from the ConfigMap key config, so configure the destination engine in your values before the upgrade that performs the migration.

The Job resolves its configuration through a projected volume with two optional sources: the release-scoped <chart fullname>-kms-config (lamassu-kms-config for release lamassu, prod-lamassu-kms-config for release prod) and the legacy unscoped kms-config created by chart versions before release-scoped naming. The legacy configuration remains authoritative while it is still present, and the release-scoped one is used once the legacy one is gone. Both sources are optional, so a missing ConfigMap never leaves the upgrade pod in ContainerCreating.

Keep migrations.caToKms.enabled: true for the upgrade that performs the migration, then remove the flag from your values once the migration completes; it defaults to false.

Production decisions

Before going live, review:

  • backup and recovery for PostgreSQL and persistent volumes
  • a production KMS engine; the default filesystem engine is not an HA design
  • shared VA storage before increasing VA replicas
  • managed OIDC roles and removal of evaluation credentials
  • a trusted TLS issuer or externally managed certificate
  • resource requests, replicas, autoscaling, disruption budgets and placement
  • SMTP, observability and alert delivery
  • the version upgrade guides and migration notes in charts/lamassu/CHANGELOG/ before every upgrade, including the optional CA-to-KMS migration hook described above

The complete values reference is maintained in charts/lamassu/VALUES.md in the Helm repository.
