# Authentication and trust (/docs/pr-preview/pr-84/platform/iot-fleets/est/bootstrap-identity)



This guide connects the DMS administrator with device manufacturing and integration. Before requesting an operational identity, the client must authenticate the EST server and establish entitlement to request the intended ID.

Initial server trust [#initial-server-trust]

Install a previously verified root, chain or pin through a trusted channel: manufacturing, approved configuration or authenticated distribution. It enables TLS and server-name verification before downloading `/cacerts`.

Your only trust proof cannot come from the same unauthenticated server. The EST server TLS certificate, bootstrap certificate and operational identity issuer may belong to different hierarchies.

Bootstrap credential [#bootstrap-credential]

With `CLIENT_CERTIFICATE`, the device presents its initial certificate and proves key possession through TLS. The DMS validates it against admission CAs. The validator receives one leaf credential: configure and test the direct issuer for the simple case; sending more intermediates does not establish delivery to the service.

Check dates, matching certificate/key and revocation before provisioning. A credential shared across equipment identifies that shared credential, not an individual device.

Initial mTLS validation does not by itself compare bootstrap CN with the requested CSR CN. If a requester should only request its own `Device ID`, add a control binding credential to ID, such as the combined webhook, and test a request with another CN. Certificate re-enrollment does compare its CN to the CSR; subsequent checks use the registered active identity.

Modes per operation [#modes-per-operation]

Select the four modes independently for enrollment and re-enrollment in [DMS](/docs/platform/iot-fleets/est/configuration#authentication-per-operation). Renewal credentials depend on that block; do not assume the bootstrap is always used or the webhook disappears.

An administrative OIDC token is not a native EST mode. A webhook may interpret an agreed credential header; that service then performs authorization. In NO\_AUTH, sending a token does not add DMS authentication.

Webhook contract [#webhook-contract]

The DMS sends operation context to the configured service. Method comes from configuration; agree the contract before selecting POST or PUT. Authorization wait defaults to 10 seconds, replaced by a configured positive timeout. The DMS verifies the receiver certificate unless `insecure_skip_verify` is enabled in the webhook config (verification is on by default) and does not follow redirects, so the configured URL must be the final one. The authorization response must be JSON of at most 1 MiB. With Lamassu-to-webhook authentication configured over `http://`, the API key or bearer token travels in cleartext, and mTLS has no effect because no TLS handshake takes place, so the client certificate is never presented; prefer `https://`. Configure those options in the [webhook settings](/docs/platform/iot-fleets/est/configuration#external-webhook-settings) of the DMS guide.

Example body:

```json
{
  "csr": "BASE64_OF_PEM_CSR",
  "aps": "DMS_ID",
  "device_cn": "est-device-001",
  "http_request": {
    "headers": { "X-Enrollment-Credential": "REDACTED" },
    "url": "/.well-known/est/DMS_ID/simpleenroll"
  }
}
```

`csr` is **base64 of PEM**, unlike the EST body, which is base64 of DER. `http_request` contains URL and first header entries from available HTTP context. This body does not include an `operation` field; distinguish enroll and reenroll through the path and configured policy.

The webhook should verify credential, its relationship to `device_cn`, DMS, operation and admission policy. Forwarded headers are not themselves trusted evidence. **Lamassu-to-webhook authentication** is a separate relationship configured in the server’s HTTP client.

Continuation requires a successful HTTP response and JSON:

```json
{ "authorized": true }
```

A bodyless `204` does not satisfy the contract. Denial, transport error, uninterpretable response or timeout abort authorization. Combined mode validates the certificate first, then queries the webhook. See the [webhook specification](/docs/api-reference/enroll-reenroll-webhook).

Revocation and checks [#revocation-and-checks]

The DMS first looks up the presented certificate in Lamassu; certificates it issued and manages are checked against their stored status. External certificates are checked through their OCSP servers and then their CRL distribution points. By default, unverifiable revocation is a rejection, not an acceptance: a certificate that is not managed by Lamassu and lists no OCSP or CRL endpoint is rejected unless `allow_unverifiable_revocation` is set in that operation's block (see [Authentication per operation](/docs/platform/iot-fleets/est/configuration#authentication-per-operation)).

A certificate that does list endpoints is held to a stricter standard, with or without the option: unreachable endpoints, stale or invalid evidence, or an inconclusive (unknown) status reject the certificate. The evidence must be fresh (`thisUpdate` not in the future, `nextUpdate` not passed, and an answer without `nextUpdate` accepted only while it is less than about 24 hours old) and OCSP responses must be signed by the certificate's issuer itself or by a delegated responder that carries the `id-kp-OCSPSigning` EKU and is within its validity. A revoked verdict is honored regardless of its age. Each OCSP or CRL request has a 10-second timeout.

Downloaded CRL distribution points are cached in memory by the DMS Manager, keyed by their URL, so concurrent enroll and re-enroll operations share a single download. A cached list is reused for at most `crl_cache.max_ttl` (1 hour by default) and never past its own `nextUpdate` — or, when the list has none, up to about 24 hours after `thisUpdate` under the freshness rule above. Reading a cached list does not extend its life, and its signature is verified against the certificate's issuer on every use. A list that is stale, larger than `crl_cache.max_size_mb` (256 MB by default) or that failed to download is not cached; the next operation downloads it again. The cache is a DMS Manager service configuration shared by all DMSs, not a per-DMS option, and it applies to CRL distribution points only — OCSP responses are never cached. Both settings are keys of the `crl_cache` section in the DMS Manager configuration file (`max_ttl` as a duration such as `10m`, `max_size_mb` as an integer); an unset or `0` value uses the default, and a negative value stops the service at startup. The cache cannot be switched off: to shorten the window in which a newly published revocation stays unseen, lower `max_ttl`. The Lamassu Helm chart does not expose `crl_cache` as a value, so a Helm deployment runs with the defaults unless you change the rendered DMS Manager configuration. Lamassu-managed certificates are unaffected: they are checked against their stored status and never reach the CRL path.

One caveat remains: a signed Good OCSP response or CRL captured before a revocation keeps validating until its `nextUpdate` (up to about 24 hours without `nextUpdate`). A revocation published in a newly issued external CRL can additionally take up to the caching window — `crl_cache.max_ttl`, 1 hour by default — to become visible, on top of the responders' own publication pace. Revocation propagates to devices at the pace the responders publish evidence, not at the moment of revocation.

Test an allowed certificate, an incorrect one, another CN, webhook denial, timeout and re-enrollment under its own policy. Keep results and schedule bootstrap credential retirement where appropriate. Continue with [EST client](/docs/platform/iot-fleets/est/configuration).
