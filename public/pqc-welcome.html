Why now

Today's devices will still be in the field in the quantum era.

Device certificates last for years, and the devices that hold them are hard to replace. If a future quantum computer breaks a signature algorithm, the whole fleet would have to re-enroll. Issuing post-quantum or composite certificates today, and serving a TLS endpoint that accepts them, lets you validate the fleet against that risk before it becomes urgent.

Key exchange

"Harvest now, decrypt later"

Traffic recorded today can be decrypted tomorrow. That threat already exists, and a key exchange with ML-KEM addresses it.

Signatures

Lifetime sets the clock

Signatures are not exposed to that attack. The urgency comes from how long certificates and devices last, not from recorded traffic.

Window in which a cryptographically relevant quantum computer could arrive. Its date is uncertain.

Five codebases carry PQC from the device to the CA.

      Related certificates · RFC 9763
      
      Migrate without breaking: bind the PQ certificate to the classical one.
      
      
      During the migration, the device holds two certificates. The new one carries the id-pe-relatedCert extension with the hash of the classical one, so a relying party knows that both identify the same entity.

      Current status
      
        Ready for pilots, not yet for production.
        
      
        PQC support lives in development branches and in forks of Go and Traefik, not in the upstream projects or in the standard Lamassu images. These are its known limitations.
        
    
        
    
        
      
        
        StandardsPrivate composite TLS code points; no Brainpool or Ed448.
        
          
          
        • The composite TLS signature schemes use private-use code points (0xFE00–0xFE0E): they interoperate only with peers built from the same fork or with an aligned hybrid-provider.
          • 
          
        • RFC 10073: the implementation passes its test vectors, but it has not had a full conformance assessment. The two Brainpool variants and Ed448 are missing.
          • 
          
        • The composite RSA PKCS#1 v1.5 variants cannot sign the TLS handshake. SLH-DSA has no TLS signature scheme.
          • 
          
        • The related-certificate request attribute has not been checked against other implementations of RFC 9763.
          • 
        
        
      
        
      
        
        KeysOnly the filesystem and software engines: no HSM or cloud KMS yet.
        
          
          
        • PQ, composite and Ed25519 keys work only with the filesystem and software engines.
          • 
          
        • Vault KV2 and AWS Secrets Manager announce support and then fail at creation. AWS KMS, Azure and PKCS#11 do not support them.
          • 
          
        • Engines developed outside the Lamassu repository must implement the new CryptoEngine methods.
          • 
        
        
      
        
      
        
        CA and validationOCSP does not work with PQ CAs; EST has no tests with PQ keys.
        
          
          
        • OCSP responses cannot be signed by PQ, Ed25519 or composite CAs. CRLs use the fork, but have no tests with these keys.
          • 
          
        • Issuance profiles cannot allow or deny PQ algorithms. Key strength is computed only for RSA and ECDSA.
          • 
          
        • serverkeygen (EST) generates only RSA and ECDSA keys. There are no EST enrollment tests with PQ keys.
          • 
          
        • A CA with an SLH-DSA or composite key cannot be imported. The backend issues the related-certificate extension but does not evaluate it.
          • 
        
        
      
        
      
        
        DashboardBrowser-generated SLH-DSA keys map identifiers 2 to 12 incorrectly.
        
          
          
        • For SLH-DSA keys generated in the browser, identifiers 2 to 12 do not match the selected parameter set. Create SLH-DSA keys with the KMS.
          • 
          
        • Key type names are not the same on every screen. There is no experimental notice and no translation.
          • 
        
        
      
        
      
        
        DeploymentNon-upstream forks, mutable tags, no renewal of PQ certificates.
        
          
          
        • Everything depends on forks of Go and Traefik that are not upstream, and the proxy image has a mutable tag.
          • 
          
        • The Traefik → Envoy hop does not verify certificates. The installer's PQ certificates last 365 days and are not renewed.
          • 
          
        • The chart uses fixed names: one release per namespace. The installer needs Linux and runs helm install, not upgrade.
          • 
          
        • The KMS OpenAPI specification does not reflect the new key types yet.
          • 
        
        
      
        
      
        
        PQ scopeOnly the device ↔ Traefik hop.
        
          
          
        • Traefik terminates the post-quantum TLS and opens a second, classical connection to Envoy Gateway. Envoy never sees a post-quantum handshake.
          • 
          
        • Lamassu implements no post-quantum KEX of its own: the hybrid groups are those of the Go 1.27 standard library.
          •

        We extended crypto/x509 and crypto/tls with post-quantum signatures.
        
          
        
          
        
            
        Go 1.27 forkBranch release-branch.go1.27. We have maintained PQC support since Go 1.25 and 1.26, and we update the fork with each release.
        
            
        Underlying algorithm implementationsML-DSA and ML-KEM: Go's official ones (crypto/mldsa and the standard library's hybrid groups). SLH-DSA: Cloudflare CIRCL, vendored.

        crypto/x509
        
              
          
                
        • Composite ML-DSA signatures. CompositePublicKey and CompositePrivateKey (crypto.Signer), 15 CompositeAlgorithm values, PKCS#8, certificates, CSRs and CRLs.
          • 
                
        • SLH-DSA in X.509. 12 PureSLHDSA… algorithms for parsing and verifying.
          • 
                
        • Related certificates (RFC 9763). CreateBoundCertificate, VerifyRelatedCertificate and the relatedCertRequest attribute.
          • 
              
        
            
        
            
        
              
        crypto/tls
        
              
          
                
        • 15 composite signature schemes for TLS 1.3, tested with mutual authentication.
          • 
                
        • Private-use code points 0xFE00–0xFE0E, because IANA has not assigned any yet.
          • 
                
        • KEX unchanged from upstream: X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024 and MLKEM1024.
          • 
              
        
            
        
          
        
          
        
            
        
              
        Validation: the composite signatures pass the test vectors of RFC 10073 Appendix E for the 15 algorithms implemented, with and without context.
        
              
        Distribution: the multi-architecture image ghcr.io/lamassuiot/golang-pqc (tags go1.27 and latest), with the toolchain in /usr/local/go-pqc. The backend requires go 1.27.3.

        The KMS and the CA manage PQ and PQ/T identities with the same API.
        
          
        
            
        KMS
        Generates and holds ML-DSA, SLH-DSA, composite and Ed25519 keys. For now only in the filesystem and software engines: software-protected keys.
        
            
        Post-quantum CAs
        PQ and PQ/T root and subordinate CAs. ML-DSA, SLH-DSA and composite keys work as CA keys, not only as leaf keys. Algorithms can be mixed in a hierarchy.
        
            
        Issuance through the API
        The same REST endpoints for all three families. Only key_metadata changes: bits carries the parameter set.
        
            
        Sign and verify
        MLDSA_{44,65,87}_PURE, SLHDSA_PURE, COMPOSITE_MLDSA_{RSA,ECDSA,ED25519}_PURE and Ed25519_PURE.
        
            
        Revocation
        CRLs are signed with the fork and are expected to work, although they have no tests. OCSP responses cannot be signed by a PQ CA yet.

        ImprovementWhat it does
        
              
                
        Several certificates per hostUpstream keeps one per set of names. The fork keeps them all (ECDSA, ML-DSA, composite) and picks one per client according to its signature_algorithms. Try it in the simulator.
        
                
        TLS options on Gateway API listenersReads traefik.io/tls-options on the listener (HTTPS, and TLS in Terminate mode). Without it the KEX groups and mTLS cannot be controlled, and devices that need mTLS fail.
